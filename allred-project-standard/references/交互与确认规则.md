# 交互与确认规则

Use this reference only when a visible user decision or consequential authorization may be required. Shared execution behavior belongs in `references/核心执行流程.md`.

## Goal

Low interruption is not no communication. Keep the user oriented, but do not ask them to manage Codex's research, benchmark selection, capability search, file discovery, technical plan, or routine verification.

```text
用户描述 -> Codex 检查和形成草案 -> 必要时一次关键决策 -> 连续执行 -> 证据汇报
```

## Question Budget

- Clear scope and safe local action: ask `0` questions.
- Standard task with product ambiguity: one consolidated card with `1-4` related user-owned decisions.
- Deep/long-term task: one scope gate; another question is allowed only when named new evidence creates a blocker or a consequential action needs separate authorization.
- Put useful non-blocking uncertainty under `待确认但不阻塞` with a stated default.
- Never repeat a question that the current message or an approved named draft already answered.

Visible `grill-me` is not the default. Use internal challenge questions, remove anything Codex can inspect, merge dependent choices, and expose only decisions that change the result. Enter a visible deep sequence only when explicitly requested or when high-consequence ambiguity cannot be safely compressed.

## Decision Ownership

| User owns | Codex owns |
| --- | --- |
| intended user, product behavior, business priority | local inspection and benchmark hierarchy |
| real/simulated evidence meaning and acceptable data boundary | source feasibility and evidence-state analysis |
| desired delivery experience and real operating constraints | feasible technical path and dependency fit |
| write authority, cost, credentials, external/device actions | read-only preflight and smallest safe plan |
| acceptance meaning and final priority | measurable criteria and verification method |

Do not ask the user to choose `小/中/复杂`, whether to check Skills, whether Codex should find a benchmark, or whether to create a technical plan.

## Product Decision Gate

Open this gate only when alternatives materially change product behavior, current scope, evidence meaning, delivery, cost, ownership, maintenance, or acceptance.

First show a short draft:

```text
当前理解：
- 已确认：
- 基于资料判断：
- 仍是假设：
- 待确认但不阻塞：
```

For one decision, use a numbered list. For multiple related decisions, use a stable named draft and one approval item:

```text
范围草案 V1：
- 本轮目标：
- 功能/任务：
- 输出：
- 本轮不做：
- 验收：

请确认：
1. 按范围草案 V1 继续（推荐）。
2. 我修改部分内容。
3. 只保留方案，不执行。
4. 暂停。
```

When independent decisions must remain separate, use `D1`, `D2`, `D3` and let the user reply `D1=...`. Do not use bare `1` both as “approve all” and as a decision identifier.

## Approval Scope And Traceability

An answer approves only the exact card or named draft it references.

- route approval does not approve invented features
- scope approval does not approve installation, Git, deployment, upload, credentials, shared writes, or device actions unless listed
- replying `1` approves only content visibly inside that option or its named draft
- recommendations outside the approved item remain hypotheses/future work

Track current-scope basis internally:

| Mark | Basis |
| --- | --- |
| `U` | explicit user statement |
| `E` | inspected file/tool/log/source evidence |
| `D` | approved decision card |
| `H` | hypothesis or optional recommendation |

Every current-round behavior, stored state, output, write action, and acceptance condition needs `U`, `E`, or `D`. `H` stays outside current scope. Quantitative acceptance targets also need provenance; do not invent arbitrary counts.

## Consequential Authorization Gate

Use a distinct authorization immediately before an unapproved consequence:

- destructive/shared/original-data write
- dependency, Obsidian, plugin, or system installation
- credentials, paid service, external upload, publication, deployment
- Git commit/push/merge when not already requested
- device/system command, calibration write, or other irreversible action

Name the target, exact action, consequence, verification, and rollback. Authorization for one action does not authorize the next.

Use this compact structure:

```text
【动作级授权】
- 目标和版本：
- 来源/许可/兼容性：
- 将执行：
- 将修改：
- 验证：
- 回退：
- 明确不授权：
```

Do not use a generic command such as `npm install` or `pip install -r requirements.txt` as the whole authorization. Resolve the exact dependency names/versions, lock or environment changes, and rollback first.

## Start Confirmation Without Duplication

A substantial new build may need a prominent start gate, but it must be the same gate as scope approval when read-only preflight introduces no new product decision.

For a non-trivial new project, use one combined `【开始开发前确认】` or `【开始执行前确认】` after all read-only preflight. It approves the named scope and starts work in the same reply. Skip it only when the user already approved an equivalent displayed named scope and explicitly authorized start. For an exact safe local modification in an existing project, do not add this gate. Include concrete files/commands after preflight; never ask the user to approve `待确认后列出`.

If the user says `继续`, `按照建议修改`, `按这个范围开始`, or equivalent wording and it clearly refers to the displayed scope, start. Do not ask again.

## Progress Communication

During inspection or execution, report concise checkpoints:

- what is being checked or changed
- what evidence was found
- whether scope, assumption, or risk changed
- what verification comes next

Updates are not approval requests. Continue while work remains inside the authorized boundary.

## Reset, Exit, And Drift

- `前面的会话不参考`: discard carried assumptions, keep the current message.
- `刚才的选择作废`: reset the active decision flow, not the whole project.
- `停止询问`, `够了，先总结`, `退出 grill-me`: stop non-blocking questions immediately, summarize, and continue already authorized work. This is not a pause command.
- `退出新手模式`: keep project and stage, change only explanation style.
- explicit `停止`, `暂停`, or `取消`: stop the relevant action and report file state.

When drift is detected: pause, restate the confirmed goal, show the mismatch and evidence, recommend the smallest correction, and ask only if that correction changes a user-owned decision.
