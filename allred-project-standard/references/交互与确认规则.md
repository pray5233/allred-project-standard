# 交互与确认规则

Use this reference across every Allred mode when Codex must communicate uncertainty, request decisions, or obtain authorization before a material action.

## Interaction Goal

The desired experience is:

```text
用户先描述 -> Codex 先理解和检查 -> 一次呈现关键决策 -> 用户快速确认 -> 持续反馈 -> 执行
```

Low interruption is not no communication. Do not disappear into benchmark research, architecture work, setup, or implementation while silently choosing product direction.

## Question Budget

Question count depends on consequence, not a fixed limit.

- Ask no question when the answer is available from project files or the user's current message.
- Use one compact card containing 1-4 related decisions for a normal task.
- A complex or long-term round may contain more decisions only when they are tightly related and cannot be safely deferred.
- Ask a separate follow-up only when the previous answer exposes a new blocker.
- Put useful but non-blocking unknowns under `待确认但不阻塞` and state the default assumption.
- Do not ask implementation details before the current scope needs them.

Use internal `grill-me` thinking to explore scope, risk, delivery, validation, and handoff. Remove factual questions Codex can inspect, merge dependent questions, and expose only user-owned decisions. Enter a visible deep-question sequence only when the user explicitly requests `grill-me` or the risk cannot be compressed safely.

## Decision Round Compression

Before every visible question round, list the user-owned decisions that are already knowable from the current message, inspected materials, and completed research. Ask them together instead of revealing them one at a time.

- A material/initial-idea checkpoint may come first because its answer changes what Codex can inspect.
- After that checkpoint, a normal new project should usually need one direction/definition card and one consolidated scope/delivery card before start confirmation. This is a guideline, not a hard cap.
- Every additional round must be caused by new evidence, a contradiction, or a decision that could not reasonably have been known earlier. State that cause briefly.
- Do not walk through search input, output format, refresh trigger, schedule, runtime, and geography as separate single-question cards when they are already known to be relevant.
- Do not bundle different dimensions into one option. `按预设品牌搜索` describes the search target; `手动点击更新` and `每天自动运行` describe the trigger/schedule. Track and confirm them separately.
- If two answers conflict, show the conflict and ask for one reconciliation decision. Never let a later answer silently overwrite an earlier one.
- For a bounded normal task, expose no more than 1-4 user-owned decisions in the consolidated card. Do not turn every field, state, rule, or lifecycle stage into its own D-item.
- When several related business rules need approval, write the complete proposal as a stable named artifact such as `范围草案 V1` or `字段与状态草案 V1`. Use one D-item to approve, modify, or reject that whole artifact. The draft must be visible in the same response and must not change silently later.

Internally keep a small decision ledger: `confirmed`, `still blocking`, `deferrable`, and `conflicting`. A question is useful only when its answer changes the next evidence check, current scope, delivery, risk boundary, or acceptance.

## Decision Ownership

Do not ask the user to manage Codex's method. Keep these responsibilities distinct:

| User-owned decision | Codex-owned work |
| --- | --- |
| product identity, intended user, current scope, visible behavior | search the benchmark hierarchy and recommend the closest comparable path |
| real versus simulated evidence and acceptable source/data boundary | inspect candidate sources and report actual evidence states |
| desired delivery experience and real operating constraints | inspect feasible technical forms, capabilities, dependencies, and packaging implications |
| write authority, cost, credentials, external actions, irreversible risk | perform read-only preflight and draft the smallest safe implementation path |
| acceptance meaning and business priority | propose measurable criteria from user requirements and observed evidence |

Do not show generic method questions such as `由我寻找参考 / 你指定参考 / 不使用参考`, `是否检查已有 Skill`, or `选择小中复杂`. The user may volunteer a benchmark or method, but absence of one means Codex follows the default hierarchy internally. Ask only when candidates create a real user-owned tradeoff.

## Opening Direction Checkpoint

After understanding the rough requirement, ask early if one choice changes the value of the project. Typical examples:

- real data/source validation versus simulated UI prototype
- app/tool implementation versus plan-only
- local/desktop versus shared web delivery
- user-specified benchmark versus Codex-selected basis
- read-only analysis versus writing to original/shared systems

For public-information search, monitoring, AI summarization, or report generation, never treat `暂无资料` as permission to replace real acquisition with simulated data. A simulated prototype validates interaction only.

Example:

```text
我理解你想做____。现在真正影响方向的是首版怎么验证：
1. 用少量真实/公开来源验证核心能力（推荐）。
2. 先做模拟数据界面，只验证操作流程。
3. 先整理来源和规则，暂不开发。
4. 只出方案，不开发。

请回复数字，也可以直接修改方向。
```

## Approval Scope

Interpret every answer against the exact question that produced it.

- choosing a validation route approves only that route
- approving a benchmark search does not approve whichever product features Codex discovers
- approving a current-round scope does not authorize installation, deployment, publication, Git operations, credentials, shared writes, or device/system actions unless listed
- replying `1` approves only the recommendations visibly included in that card
- text placed before or after the numbered card is not approved by `1` unless the card explicitly identifies that exact draft, version, or list as the item being approved
- a field list, failure-state list, schema, acceptance behavior, or output structure is approved only when it is inside the card or inside the exact named draft referenced by the approved D-item

After a route decision, check whether the product identity is still missing before research. A missing monitored subject, target user, data/evidence boundary, or runtime meaning can be a blocker even when the route is confirmed. Resolve tightly related blockers in one compact card; do not smuggle them into the start-development card.

## Decision Card Format

First present Codex's draft:

```text
当前理解：
- 已确认：
- 基于资料判断：
- 仍是假设：
- 待确认但不阻塞：
```

Then show only decisions that change scope, risk, user-visible behavior, data credibility, write boundary, delivery, validation, owner, or handoff.

For one decision, use an ordinary numbered list.

For several decisions, avoid ambiguous bare numbers:

```text
关键决策卡：
| 编号 | 决策 | 推荐默认 | 影响 |
| --- | --- | --- | --- |
| D1 | 本轮范围 | ... | ... |
| D2 | 数据边界 | ... | ... |
| D3 | 验收方式 | ... | ... |

回复方式：
1. 全部按推荐确认（推荐）。
2. 我修改部分决策，例如：D1=只做导入和汇总，D2=只读公开来源，D3=用3个样例验收。
3. 先补资料，不确认。
4. 暂停。
```

Do not reuse `1` both as “approve all” and as a decision identifier. Say explicitly when multiple selections such as `1 4` are allowed. Interpret every selected item; do not silently keep only the first.

## Decision Traceability Gate

Before moving a product behavior into the current scope, track its basis internally:

| Source | Meaning |
| --- | --- |
| `U` | explicitly stated by the user |
| `E` | observed in a file, tool result, rendered view, log, or authoritative source that Codex actually inspected |
| `D` | explicitly approved in a decision card |
| `H` | Codex hypothesis or optional recommendation |

Every current-round feature, delivery choice, persistent setting, data rule, write behavior, and acceptance condition needs at least one `U`, `E`, or `D` source. `H` items stay under `待讨论` or `后续保留` until approved.

Quantitative acceptance targets also need provenance. Do not recommend an arbitrary count such as `至少 20 条结果` before source/sample evidence shows that the number is relevant and achievable. Prefer quality criteria first: relevance, traceability, required-field accuracy, failure-state distinction, and successful operation in the confirmed environment. Add a count only when it comes from `U`, `E`, or an explicitly approved experiment target.

Do not treat these as implementation-only details when they change user-visible behavior or stored state:

- desktop versus web versus command line delivery
- remembering a user-selected folder or preference
- automatic cleanup, retention, retry, refresh, notification, or scheduling
- normalization, deduplication, inferred fields, extra worksheets, or generated summaries
- accounts, permissions, storage location, migration, or background services

When a draft contains several recommendations, either put the complete draft in one numbered scope decision or give it a stable label such as `范围草案 V1`. State exactly what replying `1` approves. Unnumbered suggestions cannot silently enter the start-confirmation card.

Before showing the start-confirmation card, compare it line by line with the approved card or named draft. Do not first introduce fields, empty/error states, extra sheets, normalization, retention, retry, or other visible behavior in the start card, even when the behavior seems standard.

## Progress Communication

During read-only research or implementation, keep the user oriented:

- what is being checked
- what was learned
- which decision or acceptance criterion it supports
- whether any assumption changed

Progress updates are not approval requests. Continue while the work stays inside the confirmed scope.

Before research likely to take more than about one minute, state what will be checked and which confirmed decision it supports. During a longer check, provide a useful update about every minute or at a meaningful checkpoint, whichever comes first. Do not wait several minutes and then reveal that Codex selected the product scope or architecture in the background.

## Start Confirmation

Use a prominent confirmation card before:

- a substantial new app/tool build
- a scope-expanding feature
- a long-term round that changes project artifacts or conclusions
- shared/original data writes, dependency installation, packaging, deployment, device/system action, or other consequential mutation

Do not require a second ceremonial approval for a narrow edit or fix when the user has already explicitly authorized the exact scope. A reply such as `按照这个方案修改`, `继续`, or `开始开发` counts only when it clearly refers to a previously shown scope.

Perform read-only preflight first if needed. The card must contain concrete planned files and commands, or say `无需创建/修改文件` / `无需运行命令`. Never ask the user to approve `待确认后列出`.

The start-confirmation card confirms an already-defined scope; it is not a requirement-discovery tool. Every user-facing feature in the card must be traceable to a user statement, inspected material, or an explicitly approved decision. Put optional ideas that lack that basis under `后续保留/待讨论`, not in the current scope.

For a new App or tool, do not replace the prominent gate with a quiet sentence such as `开始做之前，我复述一遍`. Use the `【开始开发前确认】` heading and explicitly state that no code or file mutation has started. The visual gate should be unmistakable even to a beginner scanning the conversation.

Immediately before showing the card, run the traceability gate across every line. If a concrete file or command is still unknown, continue read-only preflight instead of replacing it with a generic module name. If the preflight cannot determine it without another product decision, ask that decision before the card.

For software:

```text
【开始开发前确认】
我还没有开始写代码。确认后才会按下面范围创建/修改文件和运行命令。

本轮目标：
使用对象：
输入/现有资料：
功能和输出（只列已确认内容）：
交付形态：
验收标准：
本轮不做但后续保留：
明确不做：
仍然基于假设：
计划创建/修改：
计划运行命令：
不触碰内容：
回退/检查点：

请确认是否有改动或遗漏：
1. 确认，开始开发（推荐）。
2. 我先修改范围。
3. 只保留方案，不开发。
4. 暂停。
```

For analysis, documentation, Skill/process work, or long-term technical execution, change the title to `【开始执行前确认】` and replace coding language with the actual action.

## Reset, Exit, And Correction

Distinguish:

- `前面的会话不参考` or `历史内容不参考`: discard carried-over conversation assumptions, but keep the current message as the new requirement.
- `刚才的选择作废` or `当前方案重来`: reset the active decision flow.
- `停止询问`, `够了，先总结`, `退出 grill-me`: stop questioning, summarize confirmed items and assumptions, then offer the next action.
- `停止`, when ambiguous: ask whether to stop questioning, pause execution, or cancel the task.
- `退出新手模式`: keep the project and stage, switch only the interaction style.

When the user says the process is too slow or asks fewer questions, immediately produce a draft and one compressed decision card. When the user says there was no communication, add an early direction checkpoint and useful progress updates; do not respond by restoring a long serial questionnaire.

If Codex detects drift:

1. pause the drifting action
2. state the confirmed goal
3. state the mismatch and evidence
4. recommend the smallest correction
5. ask only if the correction changes a user-owned decision
