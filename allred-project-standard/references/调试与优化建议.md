# 调试与优化建议

This is the maintainer design record for `allred-project-standard`. Runtime behavior belongs in `SKILL.md` or routed references; executable expectations belong in `references/Skill测试验收.md`.

## Architecture Decision: 2026-08-24 Superpowers-Lite Integration

Problem: the Skill had strong behavior coverage but repeated low-interruption, start-confirmation, stop, execution, and output rules across the entrypoint and stage references. Adding Superpowers as another mandatory workflow would increase questions, duplicate design/plan documents, and slow clear tasks.

Decision:

- use `references/核心执行流程.md` as the single owner of routing-to-verification behavior
- retain only two user gate types: product decision and consequential authorization
- use Fast, Standard, and Deep lanes selected from evidence, never user-selected size labels
- reuse context inspection, root-cause debugging, blocker stops, bounded execution, and fresh verification from Superpowers as internal principles
- do not require Superpowers invocation, brainstorming approval, worktrees, subagents, per-task commits, or batch feedback; do not use TDD/Red-Green as the execution order
- stage references contain only route-specific behavior
- `allred记忆` and `allred笔记` remain exact-trigger adapters after verified execution state

Acceptance:

- clear task has zero ceremonial questions
- normal projects concentrate currently knowable decisions and avoid duplicate gates; no fixed interaction quota applies
- exact approved scope is not confirmed twice
- debugging has evidence and a hypothesis before repair; three failed hypotheses trigger architecture review
- completion claims have fresh evidence
- existing activation, beginner, long-term, benchmark, source, evidence, write-boundary, and release parity behavior remains covered

## Current Architecture Decision

Date: 2026-08-20

Problem:

- `SKILL.md` had grown to more than 600 lines.
- new-project and tuning references each approached 800 lines.
- interaction, confirmation, classification, benchmark, output, and stop rules were duplicated across modes.
- each real-world complaint added another global rule, increasing contradiction and context cost.
- project level was still inferred too quickly from project type.
- “暂无资料” could still lead to a simulated result that changed the user's actual goal.
- low-interruption behavior could become either serial questioning or silent autonomous design.

Benchmark:

- local `skill-creator` guidance: concise discovery, progressive disclosure, one owner per rule, behavior-first tests
- workspace Benchmark-First policy: define the problem first, use local/official/external search order, record comparability and measurable acceptance
- observed user tests of new-project, beginner, online-information, and long-term flows

Decision:

1. Keep `SKILL.md` as a lightweight activation, routing, and invariant layer.
2. Centralize question compression, progress communication, numbered replies, and start confirmation in `references/交互与确认规则.md`.
3. Centralize benchmark selection, capability inspection, `find-skills`, and expert Skill policy in `references/开发依据与能力复用.md`.
4. Keep stage-specific diagnosis and examples in stage references.
5. Replace label-first project grading with evidence dimensions and a separate current-round strategy.
6. Ask no generic “是否调用专家 Skill” question unless invocation materially changes tools, scope, cost, or side effects.
7. Use realistic behavior tests; do not validate exact generated wording.
8. Keep the source Skill and public release package byte-equivalent for shared files.

Deliberate differences:

- Allred remains more explicit than a generic coding Skill because it trains non-developers to distinguish evidence, scope, delivery, and acceptance.
- A prominent start confirmation remains for substantial new builds and consequential writes.
- Narrow, explicitly authorized edits do not require duplicate confirmation.
- External benchmarks are optional when local or official evidence is already sufficient, but a stated development basis is required for non-trivial design.

Acceptance metrics:

- entrypoint stays within the validator line budget
- no active reference/template is orphaned
- one rule has one primary owner
- beginner mode does not imply small-project classification
- no real-data goal silently becomes a simulated product
- normal decisions are compressed into one card
- meaningful progress communication appears before long background work
- exact scoped approval is not asked twice
- source and release package remain synchronized

Consequences:

- maintainers must edit the owning reference instead of adding another copy.
- some historical wording examples are removed; Git history remains the source for old versions.
- behavior changes should add or update one realistic regression scenario.
- the validator checks structure and routing but cannot prove conversation quality by itself.

## Tuning Loop

Use this loop after a real test:

1. save the prompt and actual first responses
2. identify the first point where behavior diverged
3. classify the cause: trigger, routing, ownership, missing evidence, bad default, over-questioning, silent decision, confirmation, or validation
4. locate the single owning file
5. make the smallest structural correction
6. run static checks and one old plus one new behavior case
7. sync release files
8. record the result here only when it changes architecture or a reusable rule

## Failure Guide

| Symptom | Likely cause | Preferred correction |
| --- | --- | --- |
| too many questions | facts and decisions not separated | inspect facts; compress user decisions |
| no communication | “low interruption” interpreted as silent autonomy | add early direction checkpoint and progress updates |
| simulated App replaces real goal | “暂无资料” treated as product permission | require route choice and label simulation limits |
| project level feels arbitrary | level selected by title or feature count | use evidence dimensions and explain strategy impact |
| beginner project becomes simplistic | interaction style mixed with complexity | classify them independently |
| same approval requested twice | direct scoped authorization not recognized | treat explicit approval of displayed scope as confirmation |
| heavy expert workflow appears | availability mistaken for necessity | reuse method; invoke only when requested/justified |
| new feature mixed with Bug | stage routing skipped | classify and fix failed commitment first |
| UI “done” without evidence | code/build used as visual proof | inspect rendered target flow |
| source and release differ | manual sync omitted | compare hashes after every release-scoped change |

## Release Discipline

The installable Skill lives in the source directory. The public release copy is a distribution mirror, not a second design source.

- run the validator in both locations
- update README only when user-facing invocation or workflow changed
- commit/tag/push only when explicitly requested

## Validation Architecture: Independent Test And Check Groups

Observed first-round result on 2026-08-20:

- 12 simulated scenarios covered new project, beginner, public monitoring, shared data, bounded tools, debugging, new features, UI, acceptance, long-term work, and Skill improvement
- the independent check group scored the run 41/100 and blocked release
- four P0 causes were found: hidden fixture answers treated as inspected evidence, unapproved decisions entering start cards, unsupported source-preflight claims, and Skill refactor scope chosen before preflight

Architecture decision:

- separate test-group-visible prompts from a checker-only oracle
- expose file/source/screenshot results only as recorded tool events after inspection
- judge raw transcripts independently and record the first divergent turn
- require feature/delivery/persistence/write behavior to trace to user input, actual evidence, or an approved decision
- validate manifest coverage deterministically with `scripts/check_behavior_manifest.ps1`; never treat that static check as behavioral proof
- run changed P0 cases with `scripts/run_behavior_eval.ps1`; record infrastructure failures separately from Skill behavior
- rerun the failed case and adjacent module cases after each correction

Deliberate difference from ordinary unit tests: generated wording is not matched exactly. The release gate evaluates decisions, evidence, authorization, side effects, progress, and verification. Any unresolved P0 blocks release regardless of total score.

## Architecture Decision: Dynamic Contract And Assumption-First Alignment

Date: 2026-08-24

Problem:

- fixed project cards and domain examples were beginning to control unrelated projects
- Codex could read many relevant rules yet still miss the highest-impact ambiguity, then repair scope through V1/V2/V3 fragments
- repeated reference reads and lifecycle-style questions increased latency
- adding a rule such as `厂家池必须先定义` would fix one transcript while weakening generality

Users and constraints:

- beginners and experienced users starting Apps, office tools, data workflows, device analysis, existing-project changes, or long-term work
- low interruption, no mandatory TDD, no mandatory subagents, no automatic Git, and no domain-specific questionnaire in the core
- clear existing work should remain zero-question; ambiguous new work should normally fit one correction round plus one complete start gate

Benchmarks inspected:

| Source/version | Comparable pattern | Reuse | Deliberate difference |
| --- | --- | --- | --- |
| GSD `bdcaab2c752d`, 2026-05-31, archived MIT | `assumptions` mode reads evidence first, presents confidence-ranked assumptions, and asks only for corrections | assumption-first alignment, confidence, interaction cap | no subagent requirement, no persistent planning system, no per-project mode setting |
| GitHub Spec Kit `27f50f7e6b61`, 2026-08-21, MIT | clarify/checklist/analyze are optional gates for meaningful ambiguity; what/why stays separate from technical plan | optional ambiguity gate and pre-build consistency lint | no mandatory spec/plan/tasks artifact chain for ordinary Allred work |
| OpenSpec `f1b521dffac3`, 2026-08-21, MIT | lightweight agreement layer and delta specs for one change | complete current contract plus change-delta reasoning | contract may stay in conversation; no required `openspec/` structure |
| Agent OS `cae8e664fb59`, 2026-05-05, MIT | phases are skippable; later versions removed verification/documentation bloat and duplicate context loading | conditional phases, read ledger, rely on frontier model for generic planning | retain Allred's fresh final verification and permission gates |
| Anthropic Skills `3b3fad96af16`, 2026-08-21 | progressive disclosure and behavior evals; do not universalize one observed failure | small entrypoint, conditional references, cross-domain evals | follow local Codex Skill validator and release layout |
| Superpowers `b36e0829c6d0`, 2026-08-12, MIT | context-first design, explicit approval, consistency self-review | inspect first, contract lint, evidence before claims | no one-question-at-a-time flow, per-section approval, TDD, forced commits, worktrees, or mandatory heavy path |

Selected architecture:

```text
generic core
-> dynamic project contract
-> evidence-backed assumptions with confidence
-> impact/ownership filter
-> compact correction surface
-> complete replacement scope
-> execution and fresh verification
```

The contract uses generic slots such as outcome, workflow, working set, output, evidence, delivery, boundary, and acceptance. Slots are internal and are never automatically converted into questions. Domain references contribute evidence risks only when routed.

Acceptance metrics:

- fixed domain decision cards are absent from the generic path
- a visible decision is user-owned, high-impact, unresolved, and not safely inspectable
- an ambiguous `App` does not silently become web, desktop, or local HTML
- a user correction invalidates dependent assumptions only, then produces one full replacement scope before mutation
- cross-domain equivalent prompts preserve decision topology without leaking domain nouns
- unchanged references are not read twice in one task without a freshness reason
- existing exact work remains zero-question and new ambiguous work normally stays within two decision rounds

## Architecture Correction: Approval Envelope And Effect Ledgers

Date: 2026-08-24

Observed generic failure in the first dynamic-contract walkthrough:

- one numeric answer selected a delivery form but unrelated recommendations were later treated as approved
- feasibility evidence and product authorization were not separated strongly enough
- a local tool promised persistence while its write boundary named source files only
- the start card grouped behavior but did not keep an exact promise-to-proof ledger

Root cause:

- the contract used one state for assumptions/recommendations and allowed evidence to enter current behavior
- approval options did not name the exact envelope they converted to active scope
- write boundaries focused on development-time files rather than runtime and external effects

Correction:

- replace the old assumption state with `U/E/R/D/X`
- only `U` and `D` authorize user-visible behavior, delivery, persistence, write authority, and acceptance meaning
- `E` proves facts/feasibility; `R` remains pending; `X` stays outside scope
- each numeric answer maps to a stable named approval envelope and converts only listed `R` items to `D`
- every start envelope lists development-time, runtime, and external/system effects plus command effects and rollback
- each independently promised behavior receives a proof method, validation environment, and evidence state

Testing policy:

- new checks are generic invariants, not keyword detectors for a past transcript
- partial approval, evidence-only feasibility, runtime persistence, change deltas, multi-axis coverage, dependency effects, and exact existing work are tested independently
- business nouns may change without changing approval semantics or test expectations

## Architecture Correction: Recommendation Admission And Progressive Gate

Date: 2026-08-24

Observed generic failures in the second walkthrough:

- approval was precise, but optional convenience behavior could still enter the contract simply because it was approvable
- source/coverage summaries used names rather than reproducible identifiers and allowed ambiguous combined cell states
- self-contained packaging did not fully disclose runtime-pack downloads and cache isolation commands
- a fully explicit start card became too long for beginner interaction

Correction:

- admit an `R` only when it serves an approved outcome, proven risk, or required testability/operability/recovery/safety
- send unrelated convenience and speculative future behavior directly to `X`
- compare each replacement contract with the approved contract and label unchanged `U/D`, technical `E`, new `R`, and removed `X`
- require exact evidence identifiers, version/date, tested input/query, observed fields/status, limits, and gaps
- assign one state per coverage cell; put qualifications in notes
- disclose SDK, runtime/target packs, provider endpoint, lock behavior, environment overrides, caches, generated files, and offline boundary for packaging/restore commands
- present one concise user-facing summary while keeping the versioned technical record Codex-owned and inspectable

Generic acceptance:

- explicit non-goals never return as recommendations
- portal names or grouped source labels cannot support scope claims
- `候选/缺口` and other combined cell states fail validation
- self-contained packaging is never called network-free without observed cached prerequisites
- technical detail is complete in the Codex execution record before mutation and does not require a second approval turn

## Architecture Correction: User Confirmation Versus Codex Execution Record

Date: 2026-08-24

Observed UX failure:

- the technically complete confirmation still exposed contract IDs, state codes, source matrices, SDKs, runtime packs, package endpoints, environment variables, commands, caches, file paths, and test mechanics to a beginner
- the user was effectively asked to approve Codex-owned implementation mechanics
- safe source/environment investigation used an unnecessary early direction gate before the final start confirmation

Correction:

- user confirmation contains only product behavior, use experience, data handling, important limitations, non-goals, acceptance, and significant effects in plain language
- exact evidence, files, commands, dependencies, caches, mutation ledgers, rollback, and acceptance mechanics belong to the Codex execution record
- the execution record is prepared before mutation but is not a user approval artifact
- any hidden `R` or consequential effect invalidates the record and must be promoted to the user or action-level gate
- safe read-only inspection proceeds with provisional reversible assumptions unless a user-owned choice is required to make that inspection meaningful, safe, or proportionate
- technical method/file-layout changes update the execution record and continue without approval when product behavior and significant effects are unchanged

UX acceptance:

- beginner confirmation is short, business-readable, and free of internal workflow/evaluation terminology
- the user never chooses a framework or approves SDKs, commands, caches, or source-code paths
- important installation, data transmission, external/shared write, deployment, device/system, cost, or destructive effects remain visible
- final confirmation follows stable scope and is not duplicated after safe read-only preflight
- every preselected visible item is named with its evidence basis; counts and generic default labels do not define user scope

## Live Regression: Transport Success Without Semantic Relevance

Date: 2026-08-24

Fresh isolated live test:

- no historical conversation or previous source conclusions were loaded
- six Bing RSS queries returned HTTP 200, valid XML, expected fields, and 10 items each
- representative titles were unrelated Japanese character dictionaries, Wikipedia/travel pages, and did not match the confirmed industrial-product subject or category

Failure:

- transport, parsing, schema, and count could be misreported as a usable automatic-search path
- a desktop App could receive an update button even though its only programmatic search route returned irrelevant content

Correction:

- add a semantic relevance gate comparing actual result samples with subject/entity aliases, information intent, language, region, and traceability
- record semantic state separately as relevant, mixed, irrelevant, or unknown
- reject irrelevant/wrong-language sources even when transport and parsing pass
- when no core source is suitable for proof, stop before development confirmation and present evidence-honest alternatives without mutation

Generic acceptance:

- HTTP 200, parse success, schema, and count never prove business usefulness by themselves
- representative sample titles/IDs are recorded before source acceptance
- no fake update/search scope is created after core-source failure

- `不要这么麻烦，列出整体的培训目录，对应每个目录生成培训文档即可` rejected the complex route and approved only an output shape
- Codex instead treated it as approval for eight invented modules, Markdown-only output, 180 minutes, removal of safety content, and immediate file creation
- verification checked file count, headings, prompt blocks, and total minutes but never reconciled content with the user's desired curriculum

Generic root cause:

- complexity evidence was allowed to select the complex deliverable
- artifact-shape authorization was allowed to select business/curriculum content
- existing files and official documentation were treated as curriculum authority
- low-interruption rules lacked a mandatory content-alignment point for document packages whose contents were still undefined
- structural artifact checks were mistaken for outcome acceptance

Correction:

- distinguish simple package, existing-material audit, and complete training system before detailed research or design
- perform only a lightweight filenames/index inventory until the outcome is aligned
- disclose that the complete-system route is complex; never select it from file volume alone
- require user-backed learner group, must-teach content, deliverables/format, material duration constraints, and explicit exclusions before file generation
- interpret simplification as rejection of unapproved complexity
- treat `目录 + 文档` as output shape only; present one complete proposed curriculum and obtain one content approval before writing
- when the user supplies an exact curriculum and direct execution scope, ask zero duplicate questions
- verify every generated module against the approved curriculum; file count, headings, minutes, and placeholder scans are supporting checks only

Regression coverage:

- V75: broad training request discloses complexity choices before curriculum design
- V76: simplified directory/document request cannot authorize topics, omissions, duration, or format
- V77: exact outline executes directly without overcorrecting into another questionnaire

## V0.6.0 Interaction Model: Adaptive Concentrated Interview

Date: 2026-08-24

Problem:

- continuous visible `grill-me` gathered useful information but created excessive waiting and too many round trips
- the later hard limits on questions, decisions, and rounds reduced waiting but forced Codex to fill user-owned gaps, causing repeated poor outcomes
- information discovery and approval decisions were treated as one small card even though they have different purposes and depths
- tests encoded 45 efficiency cases with 90 numeric `max_decision_turns` and `expected_authorization_gates` fields, reinforcing the wrong target

Decision:

- remove every generic question-count, decision-count, and interaction-round quota
- separate information discovery, product/business decisions, and consequential authorization
- run deep internal challenge before visible interaction
- batch all independent questions that are meaningful at the current evidence state
- ask dependent questions only after the parent answer, new evidence, contradiction, or consequence makes them relevant
- allow as many concentrated rounds as the dependency graph and consequence require
- require every new round to identify its newly created value
- preserve no-ceremony and no-duplicate rules for exact work without converting them into numeric budgets

User response format:

- use stable question IDs for concentrated discovery when useful
- allow shorthand, all-recommended answers, selective custom answers, and explicit deferral
- show impact and recommendation for true decisions; do not present factual discovery as approval
- combine stable final scope and start authorization when possible, while preserving separate consequential action gates

Testing changes:

- remove all 90 hard-count fields from the behavior manifest
- manifest rejects reintroduction of those fields
- V78 verifies a broad ambiguous task can ask enough currently independent questions in one concentrated packet without a four-item cap
- V79 verifies a parent answer may justify another concentrated dependent round
- V77 verifies exact complete scope still executes without a duplicate questionnaire

Acceptance:

- interaction quality is judged by information coverage, batching, dependency order, decision value, user control, and absence of repetition
- the number of questions or rounds is descriptive evidence only, never a release pass/fail threshold

## V0.7.0 Architecture: Gray Areas, Typed Questions, And Decision Coverage

Date: 2026-08-25

Problem:

- v0.6.0 removed fixed interaction quotas but still lacked a user-controlled way to choose discussion breadth when many optional gray areas existed
- concentrated questions did not have a stable usability contract, so why-now, evidence/guess, recommendation, impact, and reply syntax could disappear between cases
- approved decisions could disappear between conversation, execution, and acceptance without a deterministic reconciliation signal

Benchmarks checked:

- Addy Osmani `interview-me`, current GitHub source checked 2026-08-25: explicit hypothesis/guess, user correction, intent restatement; rejected its one-question-at-a-time loop and numeric confidence stop
- GitHub Spec Kit `clarify`, current GitHub source checked 2026-08-25: impact x uncertainty prioritization, standalone questions, why-it-matters; rejected its fixed five-question and sequential limits
- Open GSD `gsd-core`, current GitHub source/config checked 2026-08-25: prior-context loading, assumptions mode, discussion gray areas, decision coverage gates; rejected the full phase/worktree/subagent runtime as an Allred dependency
- Tessl scenario evaluations, official docs checked 2026-08-25: baseline-versus-skill scenario testing; retained as external evaluation, not runtime behavior

Ownership:

- `动态项目契约.md` owns the internal Gray-Area Map, orthogonal state fields, dependencies, stop coverage, and U/E/R/D/X translation
- `交互与确认规则.md` owns visible topology selection, discussion-area UI, typed Q/D semantics, question packet fields, clarification behavior, compact replies, and user stop handling
- `Codex执行记录.md` owns Approved Scope Ledger, Decision Coverage Ledger, Promise mapping, and execution evidence
- `validate_decision_coverage.ps1` owns deterministic structural reconciliation; it does not claim to prove conversation truth or evidence freshness by itself

Deliberate behavior:

- gray-area selection appears only when the user asks to select discussion breadth or optional areas clearly outnumber current blocking areas
- a clear exact task skips map, interview, and duplicate scope gates
- `Q` collects information; `D` approves a product/business decision; consequential authorization stays separate
- discussion-area selection authorizes discussion only
- an assumption draft is non-executable and requires later item confirmation
- questions contain six logical fields but may compress visually
- clarification leaves the current D/Q open
- stopping questions explicitly lists assumptions and continues the already authorized safe subset unless the user also pauses
- every approved scope row maps to a target and at least one decision-specific Promise before closure

Test and review protocol:

- test groups cannot read Oracle, optimization history, or other group output
- audit groups receive only fixed raw transcripts plus Oracle
- first-round audit failures remain unedited evidence; correction reruns failed and adjacent cases
- no P0 failure may be hidden by aggregate score

Measured acceptance evidence:

- behavior manifest: 88 cases, 72 P0, including V80-V88 for gray maps, typed packets, clarification, stop behavior, decision coverage, discovery gaps, and acceptance-rule gaps
- final focused interaction regressions: V78 and V79 both Pass after independent audit; no hard failure remained
- V80-V84 final audit: 5 Pass; V85-V88 final audit: 4 Pass with 24/24 assertions
- deterministic decision coverage validator rejects missing active decisions, closed-but-unverified decisions, and generic Promise collapse; valid and fully verified records pass
- source structure, manifest, route-context budget, decision coverage, PowerShell 7, Windows PowerShell 5.1, official quick validation, release parity, install, and upgrade checks are release gates
- Codex CLI runtime smoke remains infrastructure evidence only when the model endpoint times out; it is never counted as behavior Pass
