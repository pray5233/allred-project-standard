# 调试与优化建议

## 设计对标记录

- 对标来源：本地 `grilling` Skill。
- 可参考原因：它专门用于对计划、决策和想法进行追问，强调一次只问一个问题、给出推荐答案、事实由 Codex 自己查、决策由用户确认。
- 本 Skill 借鉴内容：追问前先形成共同理解，关键决策逐项确认，用户确认前不进入执行。
- 本 Skill deliberate difference：面向公司项目开发培训，问题必须改成编号选项，推荐项放在 `1`，并按项目级别区分本轮开发范围、总功能范围和后续范围。
- 验收指标：触发后先获取或复述用户的需求概述，再请求并分析相关资料，之后选择需求梳理方式；开始开发 App/工具前必须复述功能需求并询问是否有改动或遗漏；每个关键问题有编号选项；用户只回复数字也能继续；不会把本轮不做误判为总功能取消；不会强迫小项目拆第一版。
- 分级问法改进依据：本地 `skill-creator` Skill。采用主文件保留关键规则、详细分级问法放入 `references/项目级别问法.md` 的结构，避免主 Skill 过重。
- 本轮改进依据：继续采用 progressive disclosure。首次触发样例、项目类型问题库、本轮验收复盘放入 references；验收卡放入 templates；主 `SKILL.md` 只保留何时使用和关键停止规则。
- 新手模式改进依据：触发词只在主 `SKILL.md` 做分流，详细流程放入 `references/新手模式.md`，避免主流程臃肿。新手模式是贯穿项目全程的交互层，不是只用于新建工程；但不能因为文件名、培训主题或目标用户里出现 `新手` 就误触发。必须支持 `退出新手模式 / 切换标准模式 / 按标准流程` 等退出词。
- 需求梳理改进依据：`grill-me` 只用于完善用户已经提出的需求，不用于替用户定义产品。触发词后如果没有项目描述，应先请用户用一两句话描述需求；如果已经有描述，应先复述理解，请用户补充相关资料或说明资料位置，资料分析和用户确认后再进入需求梳理。
- 需求梳理退出机制依据：本地 `grilling` Skill 的原始退出点是“达到共同理解并由用户确认”，但没有明确停止词。Allred 需要增加 `停止追问`、`够了`、`先总结`、`进入计划`、`按当前理解推进` 等退出触发词，并在退出后先输出总结和下一步选项，不直接进入开发。
- 开发前功能复述改进依据：来自实际新项目测试中的跑偏风险。复用 `grilling` 和 Allred 既有的“用户确认前不执行”方法，但把确认内容从抽象计划具体化为使用对象、输入、功能、输出、交付形态、验收、暂不做和假设。验收指标是开始创建或修改 App/工具文件前，必须询问功能是否有改动或遗漏，并等待用户确认。
- 项目中途模式改进依据：借鉴本地成熟阶段型 Skill，但只复用方法和验收纪律，不默认依赖外部 Superpowers。功能调试对标 `systematic-debugging`，新增功能对标 `test-driven-development` 和 `prd-generator`，界面优化对标 `frontend-testing-debugging` 和 `redesign-existing-projects`，验收收尾对标 `finishing-a-development-branch` 与本地验收卡。
- 专家 Skill 调用策略：新增 `references/专家Skill调用策略.md`。原则是用户明确点名时尊重指定；Allred 触发时先做阶段分流；新手和小项目默认轻量复用方法；中型项目询问；复杂项目、多次失败、严格测试、前端渲染验证或正式收尾时建议调用专家 Skill。
- 测试验收策略：新增 `references/Skill测试验收.md` 和 `templates/Skill测试验收记录.md`。用静态结构检查 + 新对话行为测试验收 Skill，不只依赖脚本。

## 建议在新对话中测试

测试小项目建议开新对话。

原因：

- 新对话能验证 Skill 是否会自然触发。
- 旧对话上下文太多，可能掩盖 Skill 的真实效果。
- 新项目流程本来就应该从项目启动卡开始。

## 观察是否成功触发

成功表现：

- 先获取或复述用户自己的需求概述，不直接用 `grill-me` 替用户定义功能
- 在非平凡新项目中，先请求用户加入样例文件、历史表格、截图、流程说明或现有模板
- 有资料时先分析资料，再询问事实无法回答的决策问题
- 暂无资料时记录假设、缩小本轮范围，并提高验证要求
- 资料分析或确认暂无资料后，再确认项目级别
- 如果明确触发 `新手模式`、`allred新手新项目`、`allred新手项目`、`新手项目`，进入新手模式
- 不因 `新手员工`、`新手培训`、`给新手使用` 等目标用户或内容描述误触发新手模式
- 新手模式启动后，后续功能调试、新增功能、界面优化和验收复盘继续使用新手交互方式
- 用户说 `退出新手模式`、`切换标准模式`、`按标准流程` 等词时，退出新手模式但不重启项目
- 如果触发 `继续项目`、`项目调试`、`功能调试`、`新增功能`、`界面优化`、`本轮验收`，先进入项目阶段分流，不应强行走新项目启动流程
- 先确认开发策略：小项目默认直接实现全部明确功能，中型项目让用户选择，复杂项目第一版先行
- 先确认使用者电脑环境和交付形态，不默认普通员工电脑有开发工具
- 根据小项目、中型项目、复杂项目采用不同问法深度
- 先选择需求梳理方式
- 询问具体软件设计需求时给出编号选项，推荐项默认为 1
- 先确认开发依据/对标方式
- 不强制用户必须找外部对标，允许用户指定对标、Codex 查找、公司经验或 AI 初稿
- 先检查已有能力
- 能正确决定专家 Skill 调用方式：未调用/轻量复用/完整调用
- 能解释桌面 App、网页版、免安装文件工具、脚本工具的适用条件和代价
- 使用 `grill-me` 思路做需求梳理，但只在已有需求概述基础上补问
- 用户说 `停止追问`、`够了`、`先总结`、`进入计划`、`按当前理解推进` 等词时，停止继续追问
- 退出需求梳理后输出退出总结和下一步选项，不直接开发
- 明确区分总功能、本轮开发范围、本轮暂不开发但总功能保留
- 使用功能分层展示或后续开发路线图，让用户看懂哪些是现在做、哪些是后续保留
- 本轮范围制定后，询问用户是否合理、是否需要新增、删减或重新选择开发策略
- 开始创建或修改 App/工具文件前，先复述使用对象、输入、功能、输出、交付形态、验收方式、暂不做和假设
- 复述后询问用户功能是否有改动或遗漏，用户确认后才进入开发
- 本轮完成后，使用验收卡复盘，不把“能运行”直接当成“已交付”
- 验收时检查是否能在目标使用环境运行
- 能把反馈分成 Bug、优化、新功能、移除
- 项目类型明确时，使用对应问题库提出更贴近场景的问题
- 发现问得过重、范围扩大或缺少验证时，主动自我纠偏
- 输出任务分解
- 输出关键指标
- 输出证据等级
- 输出写入边界
- 最后才给本轮开发计划
- 不直接开始写代码

## Skill 本身如何测试验收

详细测试方法见 `references/Skill测试验收.md`，测试记录可用 `templates/Skill测试验收记录.md`。

最小验收分两步：

1. 静态结构检查：
   - `SKILL.md` 有有效 frontmatter
   - 主文件引用的 reference/template 都存在
   - 触发词覆盖新项目、新手、继续项目、调试、新增功能、界面优化、验收复盘
   - 旧版澄清方式名称、旧版英文 question-mode 写法、旧版 grill 后确认字段无残留
   - 新项目流程包含资料收集与分析 reference
   - Stop Rules 覆盖错误阶段、直接开工、缺少验证、专家 Skill 过度调用

2. 新对话行为测试：
   - 用 `Skill测试验收.md` 里的 T1-T13 作为 P0 用例
   - 每个用例只判断可观察行为，不要求逐字一致
   - 全部 P0 通过，且 P1 最多两个失败，才算本轮 Skill 更新通过

推荐每次改完后至少跑这三个冒烟测试：

```text
allred新项目
```

```text
继续项目
客户问题跟踪工具现在能打开，但导入后有几行没有识别。
```

```text
allred功能调试
请调用 systematic-debugging，按钮点了没反应。
```

期望：

- 第一个提示词不会让 Codex 发明项目或直接写代码
- 第二个提示词进入功能调试而不是新项目启动
- 第三个提示词尊重专家 Skill 指定，同时保留 Allred 的范围和验收控制

## 项目阶段分流测试

使用下面的提示词测试：

```text

期望表现：

- 应优先判断为功能调试，而不是重新做新项目启动
- 应询问复现步骤、样例文件或现有证据
- 不应直接加新功能或重做方案

```

期望表现：

- Codex 应判断为新增功能
- 应询问进入本轮还是后续路线图
- 应先定义验收标准和原有功能回归检查
- 不应直接修改代码

```text

```

期望表现：

- Codex 应判断为界面优化
- 应先确认目标用户和目标操作流程
- 应诊断现有界面问题，再做小范围优化

- 不应展开复杂架构、多 owner、完整交接、长期路线图细节
- 如果功能明确、风险低，应允许本轮直接实现全部明确功能
- 最多问少量必须决策的问题后，给简版本轮计划

中型项目测试：

```text
新项目
我想做一个客户问题跟踪工具，后续销售、售后、技术都可能用，但第一版先给售后内部用。
```

期望表现：

- Codex 应按中型项目处理
- 应询问开发策略：直接实现全部明确功能、先做第一版迭代、或先整理方案
- 如果用户已说“第一版先给售后内部用”，应把它作为本轮范围
- 应输出任务分解、关键指标和写入边界

复杂项目测试：

```text
按项目开发标准流程
我想做一个连接真实设备并生成检测结论的软件。
```

期望表现：

- Codex 应按复杂项目处理
- 应明确设备/系统写入边界、owner、证据等级、回退方案和检查点
- 不应在没有用户确认前操作真实设备或共享系统

## 开发策略选择测试

小项目直接实现测试：

```text
allred新项目
我想做一个文件重命名工具，规则已经明确，只要预览后确认再执行。
```

期望表现：

- Codex 应允许本轮直接实现全部明确功能
- 不应强制拆成第一版和第二版
- 仍需确认输入、输出、写入边界和验收方式

中型项目策略测试：

```text
新项目
我想做一个内部问题跟踪工具，功能大概清楚，但以后可能会扩展到多个部门。
```

期望表现：

- Codex 应询问开发策略
- 推荐可根据风险选择：低风险时直接实现全部明确功能，需求不确定时先做第一版
- 不应替用户默认把所有功能都放入第一版

## 新手电脑环境测试

使用下面的提示词测试：

```text
allred新项目
我想给普通办公室同事做一个 Excel 清单整理工具，他们电脑上可能没有 Python、Node，也不会用命令行。
```

期望表现：

- Codex 应确认使用者电脑环境为普通办公电脑或受限电脑
- 不应默认用 Python 脚本、Node 项目或本地开发服务器作为最终交付方式
- 应优先建议免安装文件工具、单 HTML、Excel/模板，或明确需要打包的桌面 App
- 如果选择桌面 App，应把打包和目标电脑验证纳入本轮范围

## App 和网页版选择测试

使用下面的提示词测试：

```text
新项目
我想做一个客户问题跟踪工具，不确定做成桌面 App 还是网页版。
```

期望表现：

- Codex 应先问使用人数、是否共享数据、是否需要权限、是否能部署服务器、是否离线处理本地文件
- 多人共享、统一数据时可推荐网页版
- 单机处理本地文件、离线使用、无服务器维护条件时可推荐桌面 App 或免安装文件工具
- 不应只因为“看起来高级”就推荐网页版

## 首次触发测试

使用下面的提示词测试：

```text
allred新项目
我想做一个 Excel 清单整理工具。
```

期望表现：

- Codex 第一轮不应直接写代码
- 应能识别为小项目候选
- 应给出编号选项，推荐项为 `1`
- 语气应清楚、轻量，不应一上来输出完整复杂项目文档

## 项目类型问题库测试

使用下面的提示词测试：

```text
新项目
我想做一个客户设备和问题反馈跟踪表。
```

期望表现：

- Codex 应识别为客户设备/问题跟踪类
- 本轮追问应围绕未关闭问题、负责人、设备状态或记录链路
- 不应只问泛泛的“你的目标是什么”

## 本轮验收复盘测试

使用下面的提示词测试：

```text
本轮已经能生成表格了，但有些行没识别出来，另外我想加一个自动发送提醒。
```

期望表现：

- `有些行没识别出来` 应归类为 Bug 或未通过项
- `自动发送提醒` 应归类为新功能，默认放入后续路线图
- Codex 应先问下一步是修 Bug、优化、规划第二版，还是整理交接
- 不应直接把新功能混进 Bug 修复

## 总功能和本轮范围测试

使用下面的提示词测试：

```text
新项目
我想做一个项目进度周报工具，长期希望能整合多个部门清单，但第一版只想先用 Excel 文件生成周报。
```

期望表现：

- `整合多个部门清单` 进入总功能范围
- `用 Excel 文件生成周报` 进入本轮开发范围
- 本轮暂不做的内容被标记为后续保留，而不是从项目中删除
- 本轮计划只围绕当前策略展开
- 本轮计划后必须询问用户是否确认
- 后续功能要用路线图展示开发条件和验证方式

## 开发依据选择测试

使用下面的提示词测试：

```text
allred新项目
我想做一个内部资料目录工具，暂时没有明确对标，可以先按 AI 方案出本轮方案。
```

期望表现：

- Codex 不应强制要求用户提供外部对标
- Codex 应确认开发依据为 `AI 初稿`
- Codex 应明确标注关键假设
- Codex 应缩小本轮范围，并提高验证要求
- 本轮验证后，应提醒是否需要补充对标或继续按实测结果迭代

## 常见问题和修正方法

| 问题 | 可能原因 | 优化方式 |
| --- | --- | --- |
| 没触发 Skill | description 触发词不够明确 | 在 description 中加入用户常说的原话 |
| 一上来写代码 | Stop Rules 不够强 | 强化 `Do not start implementation until the user confirms the plan.` |
| 一上来用 grill-me 定义功能 | 没有先获取用户需求概述 | 先让用户自由描述需求，或先复述已有描述，再做需求梳理 |
| 用户说够了还继续追问 | 缺少退出触发词 | 增加 `停止追问 / 够了 / 先总结 / 进入计划 / 按当前理解推进` 等退出机制 |
| 退出追问后直接开发 | 退出后的下一步闸门不清 | 先输出需求梳理退出总结，再进入开发前功能复述和计划确认 |
| 有粗略需求后直接追问功能 | 没有资料入口 | 先请求样例文件、历史表格、截图、流程说明或现有模板 |
| 用户已提供资料但还问事实问题 | 没先读资料 | 先分析本地文件，再只问资料无法回答的决策问题 |
| 暂无资料还按完整方案开发 | 没记录假设和风险 | 标注未验证假设，缩小本轮范围，提高验证要求 |
| 继续项目被当成新项目 | 没有阶段分流 | 先问或判断项目阶段，再读取对应 reference |
| 调试时猜着改 | 没有复现和根因证据 | 使用 `功能调试.md`，先复现、定位、单假设修复 |
| 新增功能直接开工 | 没有范围和验收闸门 | 使用 `新增功能.md`，先判断本轮/路线图/记录 |
| 界面优化变成重做项目 | 没有目标流程和视觉证据 | 使用 `界面优化.md`，先诊断再小范围优化 |
| 专家 Skill 调用过重 | 没有区分轻量复用和完整调用 | 使用 `专家Skill调用策略.md`，新手和小项目默认轻量 |
| 用户点名专家 Skill 但未使用 | 缺少用户显式指定优先规则 | 用户明确点名时优先尊重，同时保留 Allred 范围控制 |
| Skill 更新后不知道是否变好 | 只凭感觉测试 | 使用 `Skill测试验收.md` 和 `Skill测试验收记录.md` 做固定用例验收 |
| 问题太多 | grill 步骤太重 | 要求先给推荐答案，只问必须由用户决策的问题 |
| 用户不知道如何回答 | 问题太开放 | 改成编号选项，推荐项放在 `1`，允许用户只回复数字 |
| 把本轮范围限制成总功能 | 没有区分总功能和本轮范围 | 增加 `总功能范围 / 本轮开发范围 / 本轮暂不开发但总功能保留` |
| 用户看不懂总功能和本轮范围区别 | 只用抽象文字解释 | 改用 `总功能地图 / 本轮开发范围 / 后续开发路线图 / 明确移除` 四层展示 |
| 本轮范围定完后直接开工 | 缺少确认闸门 | 增加本轮范围确认问题，让用户选择确认、新增、删减或重新选策略 |
| 已有计划后直接做 App | 缺少开发前功能复述 | 开发前复述功能需求，询问是否有改动或遗漏，用户确认后再开发 |
| 只确认范围但没确认功能细节 | 范围确认太抽象 | 复述使用对象、输入、功能、输出、交付形态、验收方式、暂不做和假设 |
| 小项目被强行拆第一版 | 仍把第一版当成所有项目的默认流程 | 小项目默认直接实现全部明确功能，只确认本轮范围和验收 |
| 小项目被问得太重 | 项目级别没有控制问法深度 | 按 `references/项目级别问法.md` 使用小项目轻量流程 |
| 复杂项目问得太轻 | 只按小工具方式推进 | 升级为复杂项目，补齐 owner、边界、证据、回退和检查点 |
| 新手触发后仍走完整流程 | 没有先分流到新手模式 | 使用 `references/新手模式.md`，第一轮只问一个低门槛问题 |
| 新手模式被误触发 | `新手` 出现在目标用户、培训主题或文件内容中 | 只有明确 `新手模式 / allred新手项目 / 新手项目` 或项目已记录为新手模式时才触发；歧义时先问 |
| 用户退出新手模式后仍按新手问法 | 缺少退出机制 | 支持 `退出新手模式 / 切换标准模式 / 按标准流程`，切换后继续当前阶段 |
| 新手项目后续调试变成专业流程 | 新手模式只用于启动阶段 | 把新手模式作为交互层，覆盖调试、新增、界面优化和验收 |
| 新手模式先问技术栈 | 没有屏蔽开发术语 | 先问输入、输出、电脑能打开什么、交付形式，不问框架/数据库/部署 |
| 新手项目没有升级提醒 | 新手模式缺少升级规则 | 遇到多人共享、权限、设备、真实系统、长期维护时提示升级标准流程 |
| 新手电脑跑不起来 | 默认用户有开发环境 | 增加运行环境确认，普通办公电脑默认不依赖 Python、Node、Git、命令行 |
| App/网页选择混乱 | 没有确认交付形态和维护条件 | 使用 `references/运行环境与交付形态.md` 做选择 |
| 只在开发机能运行 | 验收没有覆盖目标使用环境 | 在本轮验收卡中检查目标使用环境 |
| 网页版没有部署条件 | 忽略服务器、账号、备份和 owner | 选择网页版前确认部署、权限、数据存储和维护责任 |
| 桌面 App 没有打包验证 | 只验证源码运行 | 桌面 App 必须测试打包产物和普通用户电脑 |
| 首次触发输出不稳定 | 缺少开场样例 | 使用 `references/首次触发示例.md` |
| 项目类型问题太泛 | 没有按场景追问 | 使用 `references/项目类型问题库.md` |
| 本轮完成后直接加功能 | 缺少验收复盘 | 使用 `templates/本轮验收卡.md` 和 `references/本轮验收与复盘.md` |
| 新功能被当成 Bug | 反馈未分类 | 先分类 Bug、优化、新功能、移除，再决定下一步 |
| Codex 没有主动纠偏 | 缺少自检提示 | 使用 Self-Correction 中的编号纠偏提示 |
| 强制用户找外部对标 | 把 benchmark 理解得太窄 | 改成开发依据选择，允许用户指定、Codex 查找、公司经验或 AI 初稿 |
| AI 初稿被当成验证方案 | 没标注假设和风险 | 明确写出 `AI 初稿 / 关键假设 / 更小第一版 / 更严格验证` |
| 输出太空 | 模板缺少字段 | 补充项目启动卡、指标表、交接卡字段 |
| 忘记确认开发依据 | workflow 顺序不够醒目 | 把开发依据选择放在 Required Workflow 前半段 |
| 忘记检查已有能力 | 没明确 find-skills 或本地工具检查 | 增加 Skills、插件、MCP、脚本、库检查清单 |
| 对小任务太重 | 没有项目分级 | 增加 small / medium / complex 分级 |
| 证据等级混乱 | 参考说明不够具体 | 增加例子：猜测、静态分析、离线验证、实机验证、产品闭合 |
