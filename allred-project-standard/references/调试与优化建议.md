# 调试与优化建议

This is the maintainer design record for `allred-project-standard`. Runtime behavior belongs in `SKILL.md` or routed references; executable expectations belong in `references/Skill测试验收.md`.

## Current Architecture Decision

Date: 2026-08-20

Problem:

- `SKILL.md` had grown to more than 600 lines.
- new-project and tuning references each approached 800 lines.
- interaction, confirmation, classification, benchmark, output, and stop rules were duplicated across modes.
- each real-world complaint added another global rule, increasing contradiction and context cost.
- project level was still inferred too quickly from project type.
- “暂无资料” could still lead to a simulated result that changed the user's actual goal.
- low-interruption behavior could become either serial questioning or silent autonomous design.

Benchmark:

- local `skill-creator` guidance: concise discovery, progressive disclosure, one owner per rule, behavior-first tests
- workspace Benchmark-First policy: define the problem first, use local/official/external search order, record comparability and measurable acceptance
- observed user tests of new-project, beginner, online-information, and long-term flows

Decision:

1. Keep `SKILL.md` as a lightweight activation, routing, and invariant layer.
2. Centralize question compression, progress communication, numbered replies, and start confirmation in `references/交互与确认规则.md`.
3. Centralize benchmark selection, capability inspection, `find-skills`, and expert Skill policy in `references/开发依据与能力复用.md`.
4. Keep stage-specific diagnosis and examples in stage references.
5. Replace label-first project grading with evidence dimensions and a separate current-round strategy.
6. Ask no generic “是否调用专家 Skill” question unless invocation materially changes tools, scope, cost, or side effects.
7. Use realistic behavior tests; do not validate exact generated wording.
8. Keep the source Skill and public release package byte-equivalent for shared files.

Deliberate differences:

- Allred remains more explicit than a generic coding Skill because it trains non-developers to distinguish evidence, scope, delivery, and acceptance.
- A prominent start confirmation remains for substantial new builds and consequential writes.
- Narrow, explicitly authorized edits do not require duplicate confirmation.
- External benchmarks are optional when local or official evidence is already sufficient, but a stated development basis is required for non-trivial design.

Acceptance metrics:

- entrypoint stays within the validator line budget
- no active reference/template is orphaned
- one rule has one primary owner
- beginner mode does not imply small-project classification
- no real-data goal silently becomes a simulated product
- normal decisions are compressed into one card
- meaningful progress communication appears before long background work
- exact scoped approval is not asked twice
- source and release package remain synchronized

Consequences:

- maintainers must edit the owning reference instead of adding another copy.
- some historical wording examples are removed; Git history remains the source for old versions.
- behavior changes should add or update one realistic regression scenario.
- the validator checks structure and routing but cannot prove conversation quality by itself.

## Tuning Loop

Use this loop after a real test:

1. save the prompt and actual first responses
2. identify the first point where behavior diverged
3. classify the cause: trigger, routing, ownership, missing evidence, bad default, over-questioning, silent decision, confirmation, or validation
4. locate the single owning file
5. make the smallest structural correction
6. run static checks and one old plus one new behavior case
7. sync release files
8. record the result here only when it changes architecture or a reusable rule

## Failure Guide

| Symptom | Likely cause | Preferred correction |
| --- | --- | --- |
| too many questions | facts and decisions not separated | inspect facts; compress user decisions |
| no communication | “low interruption” interpreted as silent autonomy | add early direction checkpoint and progress updates |
| simulated App replaces real goal | “暂无资料” treated as product permission | require route choice and label simulation limits |
| project level feels arbitrary | level selected by title or feature count | use evidence dimensions and explain strategy impact |
| beginner project becomes simplistic | interaction style mixed with complexity | classify them independently |
| same approval requested twice | direct scoped authorization not recognized | treat explicit approval of displayed scope as confirmation |
| heavy expert workflow appears | availability mistaken for necessity | reuse method; invoke only when requested/justified |
| new feature mixed with Bug | stage routing skipped | classify and fix failed commitment first |
| UI “done” without evidence | code/build used as visual proof | inspect rendered target flow |
| source and release differ | manual sync omitted | compare hashes after every release-scoped change |

## Release Discipline

The installable Skill lives in the source directory. The public release copy is a distribution mirror, not a second design source.

After a release-scoped change:

- sync added, changed, and removed files
- compare relative file lists and hashes
- run the validator in both locations
- update README only when user-facing invocation or workflow changed
- commit/tag/push only when explicitly requested

## Behavior Correction: Public-Monitoring Second Turn

Observed test:

- user requested a beginner App for automatic industry-market updates with no prepared materials
- Codex correctly asked whether to validate real sources, use simulated UI, organize sources, or produce a plan
- after the user replied `1`, Codex treated route approval as permission to invent four industries, select data providers, choose React/Vite, add auto-refresh/favorites/filters/responsive UI, and present a development confirmation card

Root cause:

- route approval boundary was not explicit
- the generic public-monitoring question bank allowed Codex to draft features before the monitored subject was known
- source feasibility, product benchmark, runtime delivery, and confirmation provenance were not separated

Correction:

- added `references/公开信息监测项目.md` as the single owner for this domain
- require a minimum validation definition after real-source route selection
- monitored subject has no AI default
- first proof defaults to one subject, one to three relevant sources, manual trigger, and traceable raw results
- React/Vite localhost is labeled a development proof until runtime delivery is confirmed
- browser-exposed credentials require explicit test-only labeling and a formal-delivery migration path
- start-development cards may only repeat traceable, previously confirmed product behavior
- added T5A and T5B regression cases

## Validation Architecture: Independent Test And Check Groups

Observed first-round result on 2026-08-20:

- 12 simulated scenarios covered new project, beginner, public monitoring, shared data, bounded tools, debugging, new features, UI, acceptance, long-term work, and Skill improvement
- the independent check group scored the run 41/100 and blocked release
- four P0 causes were found: hidden fixture answers treated as inspected evidence, unapproved decisions entering start cards, unsupported source-preflight claims, and Skill refactor scope chosen before preflight

Architecture decision:

- separate test-group-visible prompts from a checker-only oracle
- expose file/source/screenshot results only as recorded tool events after inspection
- judge raw transcripts independently and record the first divergent turn
- require feature/delivery/persistence/write behavior to trace to user input, actual evidence, or an approved decision
- validate manifest coverage deterministically with `scripts/check_behavior_suite.ps1`; never treat that static check as behavioral proof
- rerun the failed case and adjacent module cases after each correction

Deliberate difference from ordinary unit tests: generated wording is not matched exactly. The release gate evaluates decisions, evidence, authorization, side effects, progress, and verification. Any unresolved P0 blocks release regardless of total score.

Final loop result:

| Round | Cases/results | Score | Release gate |
| --- | --- | ---: | --- |
| 1 | 12 cases: 0 Pass, 2 Partial, 10 Fail | 41 | blocked by four P0 causes |
| 2 | 12 targeted cases: 9 Pass, 2 Partial, 1 Fail | 83 | blocked by an invented UI edit event |
| 3 | full 28-case coverage: 21 Pass, 7 Partial, 0 Fail | 87 | behavior P0 cleared; execution/test events incomplete |
| Final regressions | 28 Pass, 0 Partial, 0 Fail | 100 | behavior gate passed |

The final regressions explicitly separated read, decision, edit, and verification events; completed exact-approval execution paths; read `skill-creator` before Skill edits; verified source/release parity in the Skill-improvement scenario; and confirmed a broad UI redesign only after a comparable local benchmark and measurable pilot scope were selected.

## Behavior Correction: Broad Market-Information Blind Test

Observed real blind test after `v0.2.0-rc1`:

- a beginner requested a jointed-arm measurement-machine market-information search tool
- after the user reported no materials, Codex moved through separate cards for development basis, search input, output, refresh trigger, office environment, and geography
- `按预设品牌搜索` was mixed with `定期搜寻`, then silently changed to manual refresh in a later turn
- source research was described as complete without a source-state table or coverage boundary
- the final confirmation introduced preset brands, filters, sorting, deduplication, failure labels, and fields that were not explicitly approved
- the start gate used a quiet summary instead of the prominent development-confirmation heading and omitted concrete files, commands, and rollback

First structural divergence: the broad phrase `市场信息` was expanded into a product/specification field set before the user chose whether the goal was product records, news/events, seller/price information, or another category.

Correction:

- broad product labels now require a product-identity outcome before feature drafting
- `暂无资料` no longer approves sample data or an AI-invented first version
- all currently knowable decisions are compressed before each visible question round
- search target/input, trigger, schedule, output, evidence scope, and delivery remain separate tracked dimensions even when shown in one card
- conflicting answers require explicit reconciliation rather than silent overwrite
- public-source claims require named source states and cannot turn a target geography into a coverage claim
- feature-count labels such as search + organize + filter + export cannot alone justify medium classification
- a new App/tool must use the prominent start-development gate and only traceable, previously approved behavior
- added P0 regression case V29 with staged source and project-preflight evidence

## Behavior Correction: Six-Scenario Grouped Regression

Expanded blind-test set dated 2026-08-20:

- V29: the original beginner market-information wording for a jointed-arm measurement-machine tool
- V30: a laser methane detector market-information tool with a clearer initial idea
- V31: a bounded Excel order/shipment follow-up tool
- V32: an existing-project filtered Excel export feature
- V33: a read-only long-term log-analysis round
- V34: a fixed-source weekly update table for an office Windows computer

Independent test groups saw only operational instructions and staged events. Independent check groups saw the Oracle afterward. The loop found and corrected:

1. lifecycle stages becoming visible questions
2. product fields and failure states outside the approval envelope
3. implementation mismatch being returned to the user instead of resolved internally
4. acceptance claims exceeding the exact test event
5. a neutral material checkpoint smuggling a small-version strategy
6. long-term read-only analysis pausing for duplicate approval
7. a test fixture that itself injected the duplicate approval it was meant to detect

Final behavior evidence:

| Round | Result | Main action |
| --- | --- | --- |
| 2 | 2 Pass / 2 Partial / 2 Fail | fix approval scope, evidence reconciliation, capability mismatch, and long-term review depth |
| 3 | 3 Pass / 2 Partial / 1 Fail | require named scope drafts and promised-item acceptance accounting |
| 4 | 2 Pass / 3 Partial / 1 Fail | neutralize beginner opening, enforce exact ledger rows, and use active long-term continuation |
| 5 | V29/V30/V31/V32/V34 Pass; V33 fixture disputed | all P0 new-project and acceptance cases passed |
| 6 | V33 Pass, 7/7 assertions, 0/5 hard failures | remove synthetic duplicate approval from the fixture |
