# 项目级别与本轮策略

Use this reference when project complexity or the current-round strategy is unclear.

Do not classify by project name, “App”, number of requested features, or user proficiency alone. Classify after reading available materials and defining the problem.

State the result as the current control recommendation, not an irreversible label. Reassess after material inspection, runtime/ownership confirmation, or a change in consequence. Prefer `当前建议按复杂项目控制` over `这个项目就是复杂项目` while key evidence is still missing.

Complexity communication must name the evidence-backed drivers and their concrete user impact: what must be clarified, inspected, sequenced, or verified differently. A generic warning that the idea may become a large or company-level system does not satisfy this requirement.

## Three Independent Judgments

| Judgment | Purpose | Values |
| --- | --- | --- |
| Interaction style | how much explanation the user needs | beginner / standard / experienced |
| Full-project complexity | how much control the complete project requires | small / medium / complex |
| Current-round strategy | what to do now | complete bounded scope / validated slice / plan or evidence first |

A beginner can own a complex project. A complex project can have a small current round. A medium project may implement all clear functions when its scope is bounded and validation is credible.

## Evidence Dimensions

Assess each dimension from evidence, not a mechanical feature count:

| Dimension | Lower complexity | Higher complexity |
| --- | --- | --- |
| Workflow scope | one bounded input-process-output loop | several interacting workflows or changing rules |
| Data/system impact | sample or local copied data | original/shared/production data, devices, business systems |
| Uncertainty | real samples and acceptance are known | core feasibility, source credibility, rules, or validation is unknown |
| Integration/runtime | one known local environment | APIs, logins, hosting, packaging, scheduling, hardware, cross-platform |
| Users/ownership | one user, reversible use | multiple roles/departments, permissions, audit, handoff |
| Failure consequence | easy rollback, low cost | affects delivery, quality, safety, customers, or final conclusions |
| Maintenance | one-off or owner is clear | repeated operation, monitoring, updates, long-term ownership |

Critical signals override a simple-looking UI: device/system writes, sensitive or shared data, source credibility, scheduled automation, multiple owners, hard rollback, safety/customer commitments, or conclusions requiring live evidence.

## Complexity Result

Use the lightest level supported by the evidence:

- **Small:** bounded workflow, low consequence, known inputs/outputs, reversible writes, and one-pass validation.
- **Medium:** repeated use, multiple modules or workflows, packaging/public sources/configuration, one-team maintenance, or moderate uncertainty.
- **Complex:** any critical signal, several compounding medium risks, or a result that cannot be responsibly accepted with local sample validation alone.

Do not automatically classify every public-information tool as complex. A fixed-source manual-refresh proof may be medium; scheduled multi-source monitoring with credibility, deduplication, AI conclusions, multi-user reports, and long-term ownership is complex.

Do not infer `medium` from a surface feature count such as search + organize + filter + export. If source access, credibility, coverage, runtime, or maintenance is not yet evidenced, keep full-project complexity provisional and select a validated slice or evidence-first strategy. The current slice may be small even when the eventual system is complex.

## Strategy Selection

Choose strategy from uncertainty and risk, not merely the level label:

1. **Complete the bounded scope:** use when all requested functions are clear, low risk, and testable in one round.
2. **Build a validated slice:** use when feasibility, rules, delivery, source quality, or user workflow must be proven before expansion.
3. **Plan or collect evidence first:** use when materials, authority, runtime, owner, security, or acceptance cannot yet support implementation.

Do not force small or clear medium projects into artificial “version 1/version 2” splitting. Do not attempt the entire product scope when critical uncertainty remains.

## Classification Card

Codex should draft this card from evidence:

```text
项目分级证据：
- 交互方式：
- 完整项目复杂度建议：
- 支持证据：
- 关键风险：
- 仍是假设：
- 建议本轮策略：
- 为什么可以一次完成 / 为什么先验证一部分：
- 分级对流程的实际影响：
```

Ask for confirmation only when the classification changes scope, cost, delivery, required evidence, or approval gates. Include it in the next compact decision card instead of creating a separate level questionnaire.

## Level Effects

| Level | Minimum control | Avoid |
| --- | --- | --- |
| Small | compact scope, input/output, write boundary, one acceptance check | architecture ceremony, large roadmap, unnecessary handoff |
| Medium | task breakdown where useful, key metrics, delivery validation, regression check | assuming every function belongs in one release |
| Complex | validated slice, risk/owner/evidence/write boundaries, rollback/checkpoints, handoff | unbounded full implementation or simulated evidence presented as closure |

## Reclassification

Reclassify when new materials reveal integrations, shared writes, multiple owners, serious consequences, or easier validation. Explain the evidence and adjust only the controls affected; do not restart the whole project.
