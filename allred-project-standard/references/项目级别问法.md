# 项目级别问法

Use this reference when the project level is unclear or when drafting the startup conversation.

The goal is to keep small projects light while still giving medium and complex projects enough structure.

Core rule:

- Small projects: directly implement all clear, low-risk functions in the current scope.
- Medium projects: ask the user to choose direct full implementation, first-version iteration, or plan-only.
- Complex projects: require a first version before expanding into the full product scope.
- Beginner or ordinary office users: choose a delivery mode that does not assume Python, Node.js, Git, terminal use, admin permission, or a local server.

## Level Decision Question

If the user has not clearly described the project level, ask:

```text
这个项目按哪个级别启动？
1. 小项目（推荐）：一个工具、一个流程、一个明确输出，本轮可直接做完明确功能。
2. 中型项目：多个文件/模块，后续会反复使用，需要任务分解和关键指标。
3. 复杂项目：涉及多人、设备、系统、真实业务流程或较强证据链，需要完整计划、交接和检查点。

请回复数字，也可以直接写自定义判断。
```

Use `1` as the recommended default unless the user has already described medium or complex risk.

## Small Project

Small projects usually have one user, one input path, one processing flow, and one clear output.

Examples:

- rename or organize files
- convert one type of document
- generate one Excel summary
- make a small single-purpose app
- clean one exported list

Use a lightweight flow:

1. confirm goal
2. confirm input
3. confirm output
4. confirm what not to change
5. confirm runtime environment and delivery mode
6. confirm current-scope validation

Default strategy: direct implementation of all clear functions.

Default delivery for beginner small projects: no-install file tool, single HTML, Excel/template, or packaged app only when packaging is included.

Ask at most 3 must-decide questions before drafting the current-scope plan.

Good small-project question:

```text
本轮范围怎么定？
1. 直接实现全部明确功能（推荐）：功能少、风险低，本轮做完并验收。
2. 先跑通一个最小闭环：适合输入或规则还不确定。
3. 先整理完整功能清单，暂不开发。

请回复数字，也可以直接写自定义要求。
```

Do not expand small projects into architecture design, broad plugin research, database design, multi-owner handoff, or complex evidence chains unless the user asks or the risk appears.

Do not force small projects into "第一版/第二版" splitting when the complete requirement is clear and can be validated in one pass.

Required output:

- compact startup card
- runtime environment
- delivery mode
- current development scope
- minimal validation method
- current-scope confirmation question

## Medium Project

Medium projects usually involve multiple files, multiple functions, repeated use, or future maintenance.

Examples:

- internal tracking table tool
- repeatable office automation workflow
- small app with import, edit, export, and history
- project weekly report generator
- knowledge directory with search and update workflow

Use a standard flow:

1. confirm target user and repeated workflow
2. choose development strategy
3. confirm runtime environment and delivery mode
4. choose development basis
5. inspect existing skills, plugins, scripts, templates, and files
6. separate total scope and current scope according to the chosen strategy
7. decompose tasks
8. define key metrics
9. define write boundaries
10. confirm current-scope plan

Good medium-project question:

```text
这个中型项目采用哪种开发策略？
1. 直接实现全部明确功能（推荐：功能清楚、风险低时）。
2. 先做第一版，再逐步迭代（推荐：需求不确定或多人使用时）。
3. 先整理完整方案，暂不开发。

请回复数字，也可以直接写自定义策略。
```

Recommend dynamically:

- recommend direct full implementation when functions are clear, data is simple, target user is one person or one team, and delivery can be validated on the user's computer
- recommend first-version iteration when multiple roles, shared data, unclear rules, uncertain delivery mode, packaging, or future expansion is involved
- recommend plan-only when sample data, runtime environment, owner, hosting, or security is unclear

Good medium delivery question:

```text
这个工具更适合怎么交付给使用者？
1. 免安装文件工具/单 HTML/模板（推荐：普通办公电脑最稳）。
2. 桌面 App/可执行文件（适合频繁本地使用，但需要打包验证）。
3. 网页版工具（适合多人共享，但需要服务器、账号和维护）。
4. 脚本/命令行工具（适合熟练用户或后续由 IT 包装）。

请回复数字，也可以直接写自定义交付方式。
```

Required output:

- startup card
- development strategy
- runtime environment
- delivery mode
- development basis
- task breakdown table
- key metrics
- validation plan
- write boundaries
- current-scope confirmation question

## Complex Project

Complex projects usually involve real devices, production data, multiple departments, live systems, long-running ownership, or high cost if wrong.

Examples:

- device-connected measurement or testing software
- cross-department operational tracker
- system integration
- workflow that writes to shared records
- project with multiple Codex tasks or multiple owners

Use the full standard:

1. confirm authority and owner
2. confirm system/device boundaries
3. confirm runtime environment, deployment environment, and delivery mode
4. choose development basis and record gaps
5. inspect existing capabilities before adding anything
6. define total scope, first version/current scope, future roadmap, and removed scope
7. decompose into owner-safe tasks
8. define evidence level for each conclusion
9. define rollback and checkpoints
10. produce handoff card
11. ask for explicit confirmation before implementation

Good complex-project question:

```text
这个项目哪个环节必须人工确认后才能继续？
1. 涉及真实设备、真实系统或共享数据写入的步骤（推荐）。
2. 涉及最终结论、项目 tracker 或对外交付说明的步骤。
3. 每个阶段完成后都需要人工确认。

请回复数字，也可以直接写自定义边界。
```

Required output:

- full startup card
- first-version/current-scope plan
- runtime and delivery plan
- risk list
- owner and handoff plan
- evidence level
- write boundaries
- rollback plan
- checkpoint plan
- current-scope confirmation question

## Escalation And Downgrade Rules

Start with the lighter level when the project is genuinely narrow and low risk.

Escalate from small to medium when:

- more than one workflow is required
- future repeated use is expected
- multiple files or modules are needed
- the user asks for maintenance, history, configuration, or packaging

Escalate to complex when:

- real devices, live systems, shared trackers, or production data are involved
- multiple owners or departments must coordinate
- a wrong result could affect delivery, quality, safety, or customer commitments
- validation requires real workflow evidence, not only sample files

Downgrade when:

- the requested result is only a draft, prototype, or one-off helper
- the current scope can be validated with one sample input and one output
- the user explicitly wants a lightweight first pass

When the level changes, explain why and ask for confirmation before expanding the process.
