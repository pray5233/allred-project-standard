# 非软件项目模式

Use this reference for substantial training, policy, knowledge-base, bid/tender, contract, inspection, quality-record, and other document-heavy internal work. It adds artifact and review controls to the shared Allred workflow; it does not create or require `allred-company-context`.

## Route Boundary

Route here when the work has multiple source files, reusable deliverables, formal review, compliance requirements, durable versions, repeated use, or material business consequences.

This is the primary route even when the non-software work is a new project. Do not stack the software-oriented `new-standard` route on top. Shared core phases already provide route, evidence, decision, execution, and verification behavior.

Do not activate the full route for:

- a simple factual answer
- a trivial wording correction with exact scope
- mechanical filename or formatting work that already follows an approved template
- ordinary document creation that needs only the relevant Word, spreadsheet, presentation, or PDF Skill

Use `开始执行前确认`, not `开始开发前确认`, unless software is actually part of the approved deliverable. `第一版` means the first approved issue/draft/teaching package, not an App or MVP.

## Shared Evidence Contract

Build these slots from the user's request and inspected materials; they are not a fixed questionnaire:

| Slot | Meaning |
| --- | --- |
| purpose and audience | who will use, read, approve, teach, submit, sign, or rely on the result |
| authoritative sources | exact files, templates, clauses, standards, records, dates, versions, and owners |
| deliverables | editable source, review copy, comparison, index, checklist, courseware, response matrix, or record |
| lifecycle state | draft, under review, approved, issued/submitted/signed, superseded, or archived |
| protected boundary | originals, approved/signed documents, raw records, customer material, shared folders, and official systems |
| review authority | who may approve content, legal/commercial commitments, policy obligations, or quality conclusions |
| acceptance | source traceability, completeness, readability, format, calculation, approval, and target-use checks |

Every consequential statement needs source provenance or an explicit user-approved assumption. A template proves format, not that its example facts apply. An older approved file proves historical state, not permission to overwrite it.

The number and depth of source files may support a complexity assessment, but do not authorize a full redesign, extra deliverables, or a particular issue strategy. State the scope consequence before choosing a complex path.

## Source And Document State

Record exactly one current lifecycle state per artifact:

| State | Allowed treatment |
| --- | --- |
| Draft | edit inside the authorized copy and retain source provenance |
| Under review | make requested changes or comments without claiming approval |
| Approved | preserve the approved version; create a new controlled draft for proposed changes |
| Issued/submitted/signed | read-only unless an explicitly authorized replacement/amendment process exists |
| Superseded | retain traceability to the replacing version |
| Archived | do not silently reactivate or rewrite |

Do not infer state from a filename alone. Check visible approval/signature/version evidence or label the state unknown. Never remove blanks, comments, exceptions, conflicting source statements, or missing signatures merely to make a document look complete.

## Artifact And Tool Routing

Use the existing specialist capability for the actual artifact:

- Word or editable document: document Skill with render-and-review when layout matters
- spreadsheet or tabular record: spreadsheet Skill with formula, value, and workbook-structure checks
- slides or courseware: presentation Skill with rendered slide review
- PDF source or final output: PDF Skill with page rendering and extraction checks
- Obsidian or durable project memory: only the explicit `allred笔记` or `allred记忆` route

Allred owns scope, evidence, approval, version, and acceptance. The specialist Skill owns file mechanics. Do not install a new tool when an available capability or approved office format already works.

## Training Project

Derive from evidence:

- intended learners,岗位/experience range, prerequisites, and actual work scenarios
- observable learning outcomes rather than a list of topics
- existing source materials, tool versions, examples, and what is already taught
- course sequence, instructor notes, learner handouts, exercises, sample files, and assessment
- duration and delivery constraints only when they affect the design

Separate `content coverage` from `learning proof`. A polished Word/PPT file does not prove that an employee can perform the task. Acceptance may include a practice task, expected evidence, scoring or pass criteria, and a pilot/reader review. Do not invent company positions, software permissions, or internal procedures that are not in the provided sources.

## Training Alignment Gate

A broad request such as `给员工做 Codex 培训` does not yet define the curriculum. Before detailed research, curriculum design, or file creation, distinguish these outcomes in plain language:

1. simple document package: the user supplies or approves the topics; Codex organizes a directory and writes the corresponding documents
2. existing-material audit: Codex analyzes supplied courses and recommends what to retain, revise, add, or remove
3. complete training system: audiences, levels, core/elective routes, instructor materials, exercises, assessment, pilot, and maintenance

This outcome choice is the parent decision for a training project. Resolve it before projecting route-specific gaps into the shared Gray-Area Map. If the user already supplied an exact curriculum and execution scope, skip both the map and training interview and execute the focused route.

Do only a lightweight inventory first: locate the likely training folder, read its index/README and filenames, and report that relevant material exists. Do not deeply read every handout or research a complete official curriculum before the intended outcome is known.

If the user has not selected the outcome, explicitly say that the complete-system route is materially more complex and will introduce more decisions and deliverables. Recommend the smallest route matching the user's words; do not default to the complete route merely because many files are available.

Before generating a curriculum or training files, establish from the user or an explicitly approved source outline:

- intended learner group
- must-teach content or the business tasks learners must perform
- desired deliverables and editable/final format
- any fixed duration or delivery setting that constrains content
- content explicitly deferred or excluded

Audience and content are separate. `公司员工` does not determine whether the course should teach App basics, Git, Skills/MCP, automation, project development, safety, or another topic.

Existing training files and official product documentation are evidence and candidate inputs. They may correct factual errors or reveal options, but they do not decide curriculum priority. In particular, Codex must not decide without approval:

- a core-versus-elective split
- what the first phase will not teach
- course duration or module count
- a pass score or mandatory-error rule
- pilot group size
- Markdown instead of Word/PPT/PDF
- removal of safety, governance, extension, or advanced topics

When the user says `不要这么麻烦`, discard unapproved complexity and restate the simplified outcome. If they ask for a directory plus documents but have not defined the topics, show one complete proposed directory with each topic's source/basis and ask for a single content confirmation before writing files. Do not treat the simplification request as approval of Codex-invented module names or omissions.

When the user supplies an exact audience, topic list, exclusions, output format, and asks to generate the files, proceed without another curriculum questionnaire. Inspect only the sources needed for those topics and verify each generated module against the approved outline.

## Policy And Procedure

Establish:

- policy owner and approval authority
- applicability, roles, terms, mandatory steps, exceptions, escalation, and records retained
- current approved version and proposed-draft boundary
- effective date, revision history, superseded document, and communication/training needs when supplied

Separate source obligations from recommended wording. Do not create a mandatory duty, approval power, disciplinary consequence, retention period, or legal claim from model preference. Produce a controlled draft and change summary; only the authorized human process can approve or issue it.

## Knowledge Base

Inspect existing indexes, folders, links, note ownership, duplicates, source-of-truth documents, and update conventions before creating structure.

- update an existing entry when it already owns the subject
- keep source links, status, owner, last-reviewed date, uncertainty, and superseded relationships
- distinguish source documents from summaries and inferred guidance
- keep project repositories or official records authoritative for their own facts
- do not create a parallel Obsidian vault, memory tree, or taxonomy without explicit scope

Reader retrieval and source traceability are acceptance criteria. Note count or folder neatness alone is not success.

## Bid And Tender

Start from the exact tender package, addenda, response template, deadline/version, qualification evidence, technical/commercial source files, and submission instructions.

Build a requirement-compliance matrix with one row per independently verifiable requirement:

| Requirement ID/source | Exact requirement | Response/evidence | Owner | State/gap |
| --- | --- | --- | --- | --- |

Do not invent qualifications, certificates, customer cases, staffing, delivery dates, parameters, prices, warranties, deviations, or contractual commitments. Mark unsupported items as gaps with an owner. A complete-looking document cannot pass when mandatory evidence is missing. Final submission, upload, signature, sealing, pricing, and commitment approval remain explicit human/external actions.

## Contract

Identify exact versions of the draft, approved template, prior signed agreement, attachments, and requested review scope. Preserve signed and issued originals.

Check source-backed differences affecting parties, subject, quantity, price/tax, payment, delivery, acceptance, warranty, confidentiality, intellectual property, liability, termination, dispute handling, dates, signatures, and attachments only when relevant to the document. Do not manufacture missing terms or call wording legally valid, enforceable, safe, or approved.

Deliver a redline/difference table or controlled draft with source locations, unresolved blanks, conflicts, and required business/legal review. Automated review assists comparison; it does not replace authorized legal or commercial judgment.

## Inspection And Quality Record

Treat raw measurements and formally issued records as protected evidence. Establish when present:

- sample/product/batch/serial identity
- equipment and calibration status
- operator, date/time, environment, method, and standard/version
- raw readings, transformations, units, tolerances, calculations, and decision rule
- anomalies, missing fields, review/signature, and release state

Never fill a missing measurement, signature, calibration state, acceptance limit, or pass/fail conclusion by inference. Keep raw data unchanged, make transformations reproducible, and distinguish calculated output from approved quality disposition. A spreadsheet formula check does not prove instrument validity or authorize release.

## Controlled Execution

Before material creation or revision:

1. inspect the authoritative sources and current lifecycle state
2. record the requested output and protected boundary
3. identify gaps that affect truth, commitment, approval, or acceptance
4. expose unresolved user-owned decisions in concentrated cards; batch currently knowable items and split only on real dependencies
5. for training, confirm the curriculum/content map before generating a directory or course files unless the user already supplied an exact outline
6. use `【开始执行前确认】` for a substantial new package when the exact scope has not already been authorized
7. create a new draft/output rather than overwriting approved, signed, submitted, issued, archived, or raw evidence
8. preserve a version and source-to-output traceability record

Do not ask users to approve ordinary file mechanics. Surface external upload, submission, signature/seal, shared overwrite, formal issue, or other consequential effects separately.

## Review And Acceptance

Use a promise-by-promise ledger and distinguish:

- source completeness: required source material was actually read
- content completeness: every approved section/requirement is present or marked as a gap
- factual traceability: consequential facts and claims point to source evidence
- artifact quality: editable file, layout, formulas, links, numbering, and exports work
- reader/operator usability: a target reader can find, understand, or perform the intended task
- professional approval: required instructor, owner, legal, commercial, quality, or management review is complete or explicitly pending
- external completion: issue, submission, signature, upload, or system registration actually occurred when authorized

Render and inspect Word/PDF/slides when visual layout matters. Open and recalculate spreadsheets when formulas or workbook behavior matter. Never use “file generated successfully” as the sole acceptance evidence.

For training, also map every generated module to the approved curriculum item and verify that every must-teach item is covered. Structural checks such as file count, headings, uniform sections, total minutes, or placeholder absence do not prove content fit. Any omitted approved topic must be reported and corrected; any newly excluded topic must be user-approved.

When originals are protected, compare reproducible pre/post identity evidence such as SHA-256 hashes and report that evidence in the completion summary. When an exercise, checklist, form, or operator aid is promised, verify and report the fields needed to use it, such as task, evidence, and pass conditions; `可以打开` or a heading count alone is not usability evidence.
