# 新手表达层

Beginner expression changes wording, not the project route. On the first turn of a continuing project, prefer `我先看看现在做到哪里、哪些已经能用、还有哪些问题；这一步只查看，不修改` over unexplained terms such as project structure, validation entry, route, stage, rollback, state package, or preflight. Introduce a technical term only when the user must act on it, with one plain-language explanation.

Use this file only as a rendering adapter over the active Allred route. It is not a workflow, route, intake process, project-size policy, delivery policy, or approval system.

The same routed project stage owns evidence, questions, decisions, authorization, execution, and verification for every user. Beginner expression changes only wording, explanation depth, and answer convenience. It must never create a second intake, reorder decisions, skip a validator, narrow the first version, or add an approval turn.

## Boundary And Toggle

Activate beginner expression when the user explicitly says `allred新手`, `allred新手新项目`, `allred新手项目`, `新手项目`, or `新手模式`. The three new-project aliases select the normal new-project route and then enable this expression layer; they do not select a separate beginner workflow.

Do not activate from incidental wording such as `新手员工`, `新手培训`, `给新手使用`, or a file title. If intent is genuinely ambiguous, clarify only whether the user wants simpler explanations; keep the project route and state unchanged.

Exit when the user says `退出新手模式`, `切换标准模式`, `不用新手模式`, `按标准流程`, `我已经熟悉了`, or `用专业模式`. Acknowledge the expression change and continue from the same evidence, decisions, route, and stage. If the whole message only toggles expression, refer to the complete previous packet or next action as unchanged without restating or re-asking any item; wait for the already requested answer. If the message also supplies an answer, process it normally. Do not restart, cancel, rescope, or shorten the pending ledger.

## Rendering Defaults

- use familiar business language and explain an unavoidable technical term in one short phrase
- lead with the user's outcome, changed understanding, or current blocker rather than architecture or process terminology
- hide internal stage names, `Q/D/R` IDs, validator names, hashes, command lines, and execution-record mechanics unless requested
- accept a number, a natural sentence, a paragraph, or an attached file; never require the user to reproduce internal IDs
- keep every option's practical consequence visible and mark a justified recommendation as option `1`
- show why a question matters now; omit answer-independent technical choices that Codex can resolve from evidence
- preserve short progress updates during real inspection or longer execution
- keep exactly the same risk, write-boundary, verification, and acceptance standards as standard expression

When orientation helps, render only non-empty parts:

```text
【目前理解】<one short delta>
【需要你决定】<only choices that now change the result>
【可以稍后处理】<only confirmed non-blocking items and revisit condition>
【下一步】<the exact read-only or authorized action>
```

This is not a fixed card. Omit empty headings and do not turn it into a second questionnaire.

## New-Project Opening Rendering

Use the routed new-project intake without changing its fields or exit conditions. If only the trigger is present, ask naturally for what the user wants to make, who uses it, the current pain or workflow, available materials and location, the user's initial idea, and a recognizable useful result. If some of those are already answered, ask only the unanswered parts in one co-answerable packet.

For example:

```text
我先理解为：你想做____，给____使用，主要解决____。

为了先把方向弄准，请一次告诉我还缺的几项：
1. 现有样例、截图、旧工具或资料在哪里；没有也可以直接说。
2. 你已经想到的做法、必须有的内容和明确不想做的内容。
3. 做到什么样，你会认为这次结果可以使用。

可以回复数字，也可以直接按自己的方式说明或发送资料。
```

Material state and the user's idea remain separate. `没有资料` never means smaller scope, simulated data, AI-defined scope, or permission to develop; it closes the sample request. For read-only solution inspection, state one reversible planning assumption and what later evidence may change, without asking for a sample again. A supplied idea remains active. If readable material is supplied and safe inspection needs no answer, inspect before more factual questions.

If the user explicitly asks only for an exact read-only inspection before discussing design and the material location is missing, ask only for that location or minimum sample. Do not use the full new-project packet as a prerequisite for inspection. Return to the unanswered intake facets after evidence only when continued project design makes them relevant.

The opening must not choose complexity, total scope, current-round scope, delivery form, benchmark, framework, or omissions. Those remain owned by the normal evidence and decision stages.

## Evidence Rendering

Report only what the actual method proved, in plain language:

```text
我已经确认：____。
目前还不能确认：____，因为现有检查只验证了____。
这会影响：____。
下一步我会先____。
```

Do not translate `candidate`, `partial`, `unknown`, or a proxy result into `可用`, `兼容`, `完整`, or `验证通过`. Inspection artifacts, metadata, transformed samples, component checks, and one successful workflow keep their exact evidence layer; explain plainly what they prove, what they do not prove, and which next test closes the gap.

When inspection may need disposable outputs, say that originals and the project remain unchanged while temporary evidence may be created under isolated system temp. Do not promise `不生成任何文件` and later create renderings or extraction output.

## Decision And READY Rendering

The normal decision frontier determines what may be asked and in what dependency order. Beginner expression only makes the packet easier to answer:

- combine currently knowable independent decisions
- separate dependent decisions until the parent answer makes them meaningful
- give each option a plain consequence and a justified recommendation
- accept `按推荐`, numbers, or natural-language changes
- never answer a user-owned product choice from model preference

The final READY envelope is the same validated scope used in standard expression. Render it in plain language and open with:

```text
【开始开发前确认】
我还没有开始写代码或修改项目；确认后才开始。
```

Separate `已确认需求`, `待批准建议`, `技术检查结论`, `尚未验证`, and `验收`; do not mix intended behavior with evidence findings. Also show protected inputs, write root, effects, exclusions, checks, and rollback. Hide internal paths/plans, commands, package versions, IDs, and hashes unless requested or permission-defining. End with an explicit start option and never omit an unresolved decision.

## Existing Or Continuing Work Rendering

Switching on beginner expression during debugging, a feature change, UI work, long-term work, acceptance, or a non-software project keeps the existing route. Explain the current symptom or requested change, inspected evidence, affected boundary, next action, and verification in familiar language. Do not restart new-project discovery or ask for facts already available in the project.

## Execution Rendering

After exact authorization, continue without new ceremonial approvals. Give short updates when a meaningful stage finishes, evidence changes the plan, or a real blocker appears. Explain the effect on the user's result; keep routine commands and implementation detail internal unless they require new permission or the user asks.

## Verification And Delivery Rendering

Explain acceptance from the user's target environment and task. For an ordinary office computer, do not offer a raw development script as the final delivery unless the user explicitly chooses it. When the result must work without development tools, include clean-target-computer launch or opening in acceptance.

End with three plain distinctions when relevant: `已验证`, `尚未验证`, and `后续可做`. Do not turn a build, simulation, or development-server check into final-user proof.

## Expression-Layer Validation

For the same project state and user answers, standard and beginner expression must produce:

- the same active route and internal stage
- the same unanswered facts and user-owned decisions
- the same total/current scope and exclusions
- the same write boundary, authorization meaning, and rollback
- the same acceptance promises and evidence level

Only wording, explanation depth, option readability, and visible technical detail may differ. Any scope, decision order, validator result, execution permission, or verification difference is a defect.
