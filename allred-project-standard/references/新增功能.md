# 新增功能

Use this reference when the user asks to add a feature to an existing project.

## Benchmarks

Primary benchmarks:

- `test-driven-development`: define the expected behavior before changing production code.
- `prd-generator`: clarify problem, target user, scope, and success metrics.

Reuse:

- acceptance criteria before implementation
- small testable behavior units
- explicit in-scope and out-of-scope
- success metrics tied to user value
- verification after implementation

Adaptation for company projects:

- do not require a full PRD for small office tools
- do not force strict automated TDD when the project has no test framework and the user did not ask
- still create at least one concrete manual or sample-data acceptance check before coding

## First Response

```text
我先按新增功能模式处理。新增功能不会默认直接塞进本轮，需要先判断它是本轮必须做、下一轮做，还是只是备选想法。

这个新增功能放在哪里？
1. 放入下一轮路线图（推荐）：先保证本轮已承诺功能稳定。
2. 加入本轮开发：同步调整本轮范围和验收标准。
3. 先只记录，不开发。
4. 这个其实是 Bug，不是新增功能。

请回复数字，也可以直接写自定义安排。
```

If the current scope is already closed and the feature is small, option `1` may be changed to "加入下一轮本轮启动" depending on context. Still ask for confirmation.

## Feature Flow

1. Classify:
   - Bug: promised behavior failed.
   - Optimization: existing behavior works but is inconvenient.
   - New feature: new capability not promised in current scope.
   - Replacement: changes how an existing feature should work.

2. Clarify user value:
   - who uses it
   - what problem it solves
   - input and output
   - how the user will know it works

3. Decide scope:
   - current round
   - next round roadmap
   - total function map only
   - removed/not wanted

4. Check impact:
   - existing data format
   - UI or workflow
   - delivery mode
   - target user environment
   - old feature regression risk
   - write boundaries

5. Define acceptance:
   - one normal case
   - one edge case
   - original feature regression check
   - user-facing evidence

6. Before implementation, restate the feature requirement:
   - user
   - input
   - new behavior
   - output
   - existing behavior that must not regress
   - validation
   - out-of-scope items

7. Ask whether anything changed or was missed. Implement only after confirmation.


## Stop Rules

Stop and ask before continuing when:

- feature changes the current-scope promise
- feature conflicts with the delivery mode or target computer environment
- feature requires a new dependency, server, database, account, or permission
- feature changes data format used by existing users
- feature mixes with an unresolved Bug
- user says "顺便" but the work changes scope or validation
- implementation starts before the feature requirement is restated and confirmed

## Mode Test Prompts

```text
新增功能
现在能生成 Excel 了，再加一个按负责人筛选。
```

Expected:

- classify as new feature
- ask whether it enters current round or roadmap
- define acceptance criteria before implementation
- include regression check for existing Excel generation

```text
再加一个自动发送提醒，另外现在有些行识别不出来。
```

Expected:

- classify row recognition as Bug
- classify auto reminder as New feature
- recommend fixing Bug first
- do not implement both together unless user confirms scope expansion
