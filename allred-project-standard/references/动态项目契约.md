# 动态项目契约

Use this reference for a new project, an ambiguous product change, or any task where user-visible behavior, evidence meaning, delivery, or acceptance is not yet stable. It is a decision engine, not a questionnaire or a mandatory document.

## Objective

Think broadly inside Codex and keep the user's correction surface small:

```text
用户意图和资料
-> 证据化项目契约
-> 内部假设与一致性检查
-> 只暴露高影响未决项
-> 完整范围确认
```

Do not encode a past domain example as a universal requirement. A manufacturer list, customer set, device inventory, source catalog, role model, or file set matters only when its boundary changes the current result.

## Contract Slots

Build only the slots relevant to the current task:

| Slot | Meaning |
| --- | --- |
| outcome | the observable problem solved and who benefits |
| core workflow | what the user does and what the system returns |
| working set | the objects, inputs, sources, records, devices, or users the workflow operates on |
| output | visible result, artifact, state change, or decision support |
| evidence | materials and observations that make the behavior credible |
| runtime/delivery | where it is built, how it is used, and what is formally delivered |
| boundaries | non-goals, original/shared data protection, permissions, cost, and external effects |
| acceptance | observable evidence that proves the promised result |
| total/current | total goal and current round only when separating them reduces real risk |

These slots are internal structure. Do not ask one question per slot and do not show empty fields.

## Provenance And Confidence

Track every material statement internally:

| Mark | Meaning |
| --- | --- |
| `U` | explicit user statement |
| `E` | inspected project, tool, source, or environment evidence |
| `R` | Codex recommendation or reversible assumption; not yet approved |
| `D` | user-approved decision |
| `X` | explicitly user-rejected, user-deferred, or user-approved outside the current round; requires exact `U/D` provenance |

Authorization rules:

- user-visible behavior, delivery, persistence, evidence meaning, write authority, and acceptance meaning enter active scope only through `U` or `D`
- `E` can prove feasibility, existing behavior, source state, or a technical constraint; it cannot authorize a new product behavior or side effect
- `R` may guide read-only preflight but cannot authorize mutation or be described as confirmed
- `X` remains outside active scope even when technically easy; create it only from an explicit `U/D` rejection, deferral, exclusion, or approved scope replacement
- an unapproved `R` never becomes `X` automatically; omit it or keep it visibly labeled as an unapproved suggestion

These state codes are internal or durable-record notation. In ordinary conversation, especially beginner mode, use plain labels such as `已确认`, `检查依据`, `推荐待批准`, and `已确认本轮不做`. Do not label an `R` as `本轮不做`, `暂缓`, `排除`, or `后续保留`. Show `R1/R2` identifiers only when they make partial approval or correction unambiguous.

Classify assumptions as:

- `Confident`: directly supported by current user input or strong project evidence
- `Likely`: best current interpretation with a safe, reversible default
- `Unclear`: alternatives materially change the product, evidence meaning, delivery, write boundary, or acceptance

Confidence is not a reason to display more text. Surface only assumptions whose correction matters.

## Assumption-First Alignment

Before asking the user:

1. extract all supplied facts, preferences, exclusions, and initial ideas
2. inspect the smallest relevant project/material/environment evidence
3. fill the contract with evidence-backed conclusions and `R` recommendations
4. identify contradictions and missing decisions
5. rank candidate decisions by impact, uncertainty, reversibility, evidence gap, and decision ownership
6. expose only the highest-impact user-owned items that remain unresolved

A visible decision must satisfy all of these:

- the user owns the meaning or consequence
- two credible alternatives would materially change the result
- current input and evidence do not already resolve it
- Codex cannot answer it through safe read-only inspection
- deferring it would create likely rework, false evidence, unsafe writes, or an invalid acceptance claim

If any condition is false, keep the work internal. A reversible technical default may remain internal. A recommended user-visible behavior stays `R` until an explicit approval envelope converts it to `D`.

## Recommendation Readiness Gate

Do not assemble a complete first-version product package until all of these are present:

- a user-supplied outcome and intended use/user, not only a broad product label
- material state and the smallest relevant inspection result, or an explicit record that materials are unavailable/deferred
- the user's initial idea, must-haves, or explicit instruction for Codex to propose alternatives from scratch
- an observable useful/acceptable result, even when its exact metric still needs a later decision

Missing readiness is an INTAKE/EVIDENCE gap, not permission to fill the contract from model preference. Ask the missing independent basis together. A first-version package, delivery recommendation, product-feature list, and READY envelope are forbidden until readiness passes.

While readiness is incomplete, use factual/open `Q` prompts rather than model-created product `D` options. Do not make the user choose a product route before Codex has read the available materials and understood the user's own first idea. Volunteered user decisions remain valid `U/D` input and need not be asked again.

For every visible `R`, record one exact source chain:

```text
R -> supporting U/D outcome -> supporting E risk or feasibility fact when applicable -> user-visible consequence
```

An `E` fact may require a technical method inside an already approved outcome. It does not choose a user-visible workflow, delivery experience, transmission permission, persistence rule, scope, or acceptance meaning. If two credible product consequences remain, expose that single axis in DECISION.

## Dynamic Decisions, Not Fixed Cards

Choose decision dimensions from the task. Possible dimensions include:

- user-visible workflow or behavior
- working-set boundary and how new items enter it
- real, simulated, inferred, or user-verified evidence meaning
- local, desktop, file-based, hosted, device, or other delivery experience
- persistence, sharing, ownership, and write authority
- current-round risk strategy and acceptance meaning

These are examples, not required rows. Do not reuse fixed `D1-D4` merely because an earlier project used them.

## Gray-Area Map

Before a substantial visible interview, build an internal map of unresolved areas. Use task-specific dimensions rather than a universal questionnaire.

| Field | Meaning |
| --- | --- |
| area ID | stable short ID such as `A`, `B`, or `DATA` |
| area | user-readable topic, not an internal method label |
| resolution | `confirmed`, `evidence-backed`, `unresolved`, or `conflict` |
| need/owner | `Codex research`, `user information`, `user decision`, or `consequential authorization` |
| timing | `blocking now`, `discuss now`, `discussion deferred`, or `not applicable` |
| basis | exact `U/E/D` support or the missing source |
| impact | what output, risk, cost, workflow, or acceptance changes |
| dependency | parent answer/evidence required before this area becomes meaningful; `None` when independent |

The internal map does not own a visible UI template. `references/交互与确认规则.md` owns when and how discussion-area selection is shown.

Selecting discussion areas authorizes discussion only. It does not approve a recommendation, exclusion, delivery form, feature, or mutation. An unselected area becomes `discussion deferred` only when it is non-blocking; it does not silently become `X` or `D`. A blocking area cannot be skipped by area selection: narrow or pause only the affected outcome.

Use direct concentrated questions instead of an area-selection step when the map is already small and readable. The map is a compression aid, not another mandatory ceremony.

Order discussion by dependency, not by a fixed lifecycle. Resolve parent areas before generating child options. After each response, update only affected areas and retain all still-valid answers.

Stop discovery when every material area for the current outcome is one of:

- confirmed by `U/D`
- evidence-backed for a Codex-owned technical conclusion
- represented by a concrete, non-executable assumption draft that the user subsequently confirmed
- explicitly deferred without making current execution false, unsafe, or untestable

Do not use a confidence percentage, question count, or turn count as the stop condition. If an unresolved area would invalidate the current outcome, it remains blocking regardless of interview length.

## Recommendation Admission Filter

An item may become `R` only when it satisfies at least one of these:

- it is necessary to deliver an explicit `U/D` outcome
- it resolves a demonstrated `E` risk, contradiction, evidence gap, or target-environment blocker
- it is required to make an approved behavior testable, operable, recoverable, or safe

Treat work or prerequisites that current `U/E/D` already establishes as completed as inherited baseline, not an open scope option. Do not ask whether to repeat, redo, re-teach, replace, or re-approve them unless new `U/E` shows a current gap, conflict, invalidation, or acceptance need. A hypothetical benefit from repetition is not enough to reopen the item.

For every visible `R`, keep an internal rationale: the supporting `U/E/D`, what changes if accepted, and what happens if excluded. `常见功能`, `以后可能有用`, `实现方便`, or `用户可以批准` is not sufficient. Optional convenience, unrelated polish, speculative export/filter/scheduling, and other nice-to-have behavior stays out of the contract and final handoff unless the user requests it. If preserving a useful option materially helps, keep it as `R/未批准建议`; never auto-classify it as deferred, excluded, or future work.

Approvable does not mean worth proposing. Prefer the smallest contract that fully satisfies the confirmed outcome and risks.

When a correction surface is needed, use a compact form. Label recommendations separately from confirmed scope:

```text
【项目方向确认】
- 已确认：...
- 检查依据：...
- 建议按以下方式处理：...
- 本轮不做：...

1. 批准当前方向，继续完善方案（推荐；不开始开发）。
2. 修改部分内容。
3. 只保留方案，不执行。
4. 暂停。
```

This direction card is not a start envelope. `按以上内容继续` approves only the listed direction/recommendations and advances to the next required stage; it does not authorize mutation.

Omit any section that adds no decision value. There is no fixed card-size or decision-count rule. Keep a card readable, batch all currently knowable related decisions, and split only when later choices depend on an unresolved parent answer.

## Approval Envelope

Every visible approval request maps to a stable internal contract and an explicit user-facing approval scope:

- name the exact `R` items, product behavior, side effects, or consequential actions included
- state whether approval only confirms direction or also authorizes implementation
- separate what remains unapproved from what the user explicitly deferred or excluded
- map every numeric response to one unambiguous envelope

Do not require a beginner to understand or approve internal contract IDs. In beginner mode, use plain language and keep the stable ID in the Codex execution record. Show item IDs only when partial approval cannot otherwise be stated unambiguously.

When the user approves an envelope, convert only the listed `R` items to `D`. Selecting one delivery option does not approve unrelated recommendations. `按推荐`, `1`, `继续`, or `开始` applies only to the immediately visible named envelope. It authorizes mutation only when that envelope is explicitly the complete READY scope and its selected option states that it approves the scope and starts execution.

An unapproved `R` does not automatically create another question or an `X` item. If the current goal remains coherent without it, omit it from the active contract and continue. Keep it as a visibly unapproved suggestion only when preserving the option materially helps the user. Ask again only when leaving it unresolved makes the approved outcome impossible, unsafe, or untestable.

A single combined contract/start gate may introduce clearly labeled `R` recommendations only after recommendation readiness passed, the decision stage was loaded, no earlier unresolved product decision remains, and read-only preflight supplies the required evidence. Option `1` must explicitly approve those recommendations and authorize the listed mutations. If an earlier contract was already approved, the final start gate may only repeat its `U/D` scope plus evidence-backed technical details; it cannot silently add another `R` item.

An early `continue`, direction approval, recommendation approval, sample upload, or conditional start phrase does not become READY authorization after later evidence arrives. When later evidence changes product meaning or significant effects, return only the affected item to DECISION and issue one replacement READY envelope.

When a later contract replaces an approved contract, show the delta explicitly:

- `保持不变 U/D`: approved behavior carried forward
- `检查后技术明细 E`: implementation facts/effects that do not change product meaning
- `新增待批准 R`: every new user-visible behavior, persistence rule, delivery consequence, evidence meaning, or acceptance meaning
- `移出本轮 X`: items the user explicitly removed or deferred in `U/D`

No new product item may appear under `保持不变` or plain `本轮功能` merely because it seems standard.

Before any final scope or handoff, provenance-check `暂缓/排除/不做/后续`: settled items need exact `U/D`. If none exist, say none are confirmed; never fill an empty category by inventing future work. Keep `已确认暂缓/排除 (U/D)`, `未决/证据缺口`, and `未批准建议 (R)` separate. Absence of approval means unresolved or omitted, not deferred. Model alternatives stay in the last group or are omitted; a bullet's heading controls its state.

Every active `U/D` item must survive translation into execution and acceptance. Record its stable ID in the Decision Coverage Ledger, name the implementation/document target, and link at least one Promise ID. A decision marked verified must point to fresh passing evidence. Do not close a record when an active decision disappeared between conversation, plan, artifact, and acceptance.

## Reproducible Evidence Record

Evidence used for scope, coverage, benchmark, dependency, environment, or completion must be reproducible at the granularity of the claim. Record as applicable:

- exact file path, source URL/provider ID, package/library ID, environment command, or device/configuration identifier
- version, date, timestamp, query/input, and command actually used
- observed fields/output/status and the evidence level it proves
- access, terms, permissions, rate, login, network, compatibility, or maintenance limits
- unresolved gap and what would be needed to raise the evidence level
- for search/query results: actual sample titles/IDs and semantic fit to subject, information intent, language, and region

A brand name, portal name, grouped phrase such as `等公开来源`, search snippet, or remembered result is not a reproducible record. A virtual walkthrough must label injected evidence as fixture/simulation and cannot later be reported as a live check.

For retrieval capabilities, response success is not outcome success. Do not infer useful search from HTTP status, parse success, schema, or count without checking returned content.

## Contract Consistency Lint

Before source research that depends on product meaning, before the final start gate, and after a material correction, check internally:

1. no two confirmed choices contradict each other
2. every current-round user-visible behavior, delivery, persistence rule, side effect, and acceptance meaning has `U` or `D` authorization
3. `E` has not been treated as product authorization and `R` has not been treated as confirmed
4. runtime constraints have not been treated as approval of a delivery form
5. a technical proof has not been described as the formal user experience
6. total goals, current scope, deferred work, and rejected work remain distinct
7. evidence granularity matches each coverage or completion claim
8. the Codex execution record supports the approved product scope; every user-relevant or consequential effect is also present in the user-facing confirmation

Resolve technical inconsistencies internally. Reopen a user decision only when the correction changes user-owned meaning.

## Mutation Ledger

Before mutation, identify all relevant effects rather than listing source files only:

| Layer | Examples |
| --- | --- |
| development-time writes | source, generated project files, lock files, `bin/obj/dist`, local test output |
| runtime writes | user settings, local database, logs, caches, exports, temp files, registry entries |
| external/system effects | dependency installation, network service, credentials, Git, upload, deployment, device/system changes |

For each active effect, name target path/system, lifecycle, owner, verification, and rollback. If the product promises persistence, a statement such as `只修改项目目录` is invalid unless all runtime data really stays there and that behavior is approved.

Documenting rollback does not automatically authorize deleting pre-existing user, shared, or external data. Automatic cleanup is limited to newly created scoped artifacts when that cleanup was included in the envelope. If rollback would delete or overwrite existing state, use the consequential authorization gate at action time.

For every planned command, record material effects when relevant:

- network access and exact provider/registry
- packages, versions, lock files, environment, or caches changed
- processes, ports, services, scheduled tasks, or system settings started
- generated files and cleanup/rollback

The exact command in the Codex execution record must show environment overrides used to contain effects. For restore, build, packaging, browser automation, or similar commands, inspect and record provider endpoints, package/runtime-pack versions or resolution rules, lock-file behavior, global versus isolated caches, generated directories, processes/ports, and offline behavior. A self-contained package may still download target/runtime packs; `无第三方依赖` does not prove the command is network-free.

Routine build caches may be Codex-owned technical effects, but they still need an accurate write boundary. Installation, system changes, external effects, or persistent user-visible storage require the appropriate approval.

## Acceptance Ledger

Keep each independent promise separate:

| Promise | Proof | Environment | Current evidence state |
| --- | --- | --- | --- |
| user-visible behavior | focused operation or rendered interaction | actual validation target | planned/verified/unverified |
| persistence/restart | write, close, reopen, reread | approved runtime path | planned/verified/unverified |
| source or data claim | exact sample and traceable evidence | real/simulated/offline/live | planned/verified/unverified |
| package/delivery | launch and core workflow | developer/target-like/clean target | planned/verified/unverified |

The start envelope names the planned proof. Completion reconciles fresh evidence against the same promises. A build or package file does not prove launch, persistence, source quality, target-computer compatibility, or usability unless that exact layer was observed.

For provenance-sensitive workflows, add acceptance rows for classification correctness, visible failure-state distinction, approved runtime paths, and no-touch boundaries when those promises are active.

## User Confirmation And Codex Execution Record

Separate three information layers:

### User Confirmation Layer

Always visible and written in the user's language. Include only:

- what will be built or changed
- how the user will use it
- what data is read, saved, changed, transmitted, or deliberately not retained
- current evidence-backed limitations and non-goals
- observable acceptance outcome
- the exact meaning of each response option

Name concrete initial working-set items, presets, roles, sources, templates, devices, or other visible defaults when they are part of the first delivered experience. Counts or generic phrases such as `两个候选`, `若干来源`, or `默认模板` are insufficient when the user would reasonably care which items are included.

### Important Effects Layer

Keep it in the same concise confirmation when the user needs informed consent. Translate effects into plain language, for example:

- connects to a named public/package service
- installs a named dependency or writes outside the project
- stores local settings/history/logs and where
- uploads, deploys, publishes, changes shared data, controls a device, or may incur cost
- rollback may delete or overwrite existing state

### Codex Execution Record

Codex-owned and not a user approval artifact. Prepare it before mutation with exact evidence IDs, files, commands, environment overrides, dependencies, caches, mutation ledger, rollback, and acceptance ledger. Keep it in working context or a versioned project record when durability helps. The user may inspect it, but ordinary execution must not require them to understand it.

The execution record may contain only technical `E` details that implement approved `U/D` scope. It cannot hide `R`, a user-visible behavior, or a consequential effect. If such an item appears, move it to the user confirmation or consequential authorization gate.

Use `templates/Codex执行记录.md` as the canonical serialization. When the record is durable, validate it with `scripts/validate_execution_record.ps1` before substantive mutation. Do not declare the record complete from a prose sentence or an ID alone.

Do not ask a second question to approve the execution record. A technical method or file-layout change that preserves product behavior and significant effects updates the execution record and continues without a new gate.

## Coverage Shape

Use a matrix only when a claim depends on multiple dimensions. Derive its axes from the contract instead of hard-coding a domain:

- object x capability
- role x permission
- input type x output behavior
- platform x workflow
- source x information category
- device/configuration x validation scenario

Each cell should state its actual evidence level or gap. Do not require a matrix for a one-dimensional bounded task.

Each matrix cell has exactly one current state such as `已验证`, `候选`, `缺口`, or `不适用`. Put qualifications in a separate note, for example `候选；官方来源仍是缺口`. Do not use ambiguous combined states such as `候选/缺口`.

## Change Delta And Full Replacement

When the user corrects one part:

1. identify which assumptions and decisions depend on it
2. invalidate only those dependent items
3. preserve unaffected confirmed content
4. redo only the necessary read-only preflight
5. before mutation, present one complete replacement contract or scope, not a chain of V1/V2/V3 fragments

A local correction should not restart discovery. A change from web to desktop, simulated to real data, local to shared use, or read-only to write behavior usually invalidates technical path and acceptance, but it does not erase unrelated user goals.

## Context Read Ledger

Prefer `scripts/get_route_context.ps1` for staged routes. Its output is extracted from the canonical references and is not a second policy owner. Record only additional full-file or out-of-route reads; do not reload unchanged material at every turn.

Within one task, remember which Skill references and project artifacts were already read. A linked reference means `read when needed`, not `read again`. Do not reread an unchanged file merely because another reference links to it. Reload only when:

- the file changed
- compaction or context loss makes the prior content uncertain
- a newly routed operation needs a section not previously inspected
- verification requires a fresh read of mutable evidence

This ledger applies to instructions as well as project files. Progressive disclosure should reduce latency, not multiply reads.

## Interaction Acceptance

- no fixed interaction-round or decision-item limit
- discovery questions are separated from approval decisions
- currently knowable independent questions are concentrated rather than serialized
- a later round is justified by an answer dependency, named new evidence, a true contradiction, or consequential authorization
- well-specified work skips repeated discovery and duplicate confirmation
- vague or complex work asks enough to establish the right result instead of silently filling user-owned gaps
- no domain term appears in the contract unless supplied by the user, observed in evidence, or explicitly labeled as an example
- no `R` recommendation is executed before its named approval envelope converts it to `D`
- a final combined gate may introduce a clearly labeled recommendation only when the same option explicitly approves it; it must never present that recommendation as already confirmed
