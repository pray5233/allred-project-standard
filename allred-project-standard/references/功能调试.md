# 功能调试

Use this reference when an existing project has a bug, unexpected result, failed test, broken interaction, wrong output, or user-reported malfunction.

## Benchmark

Primary benchmark: `systematic-debugging`.

Reuse:

- reproduce before fixing
- inspect evidence before proposing a fix
- identify root cause instead of patching symptoms
- test one hypothesis at a time
- make the smallest fix that addresses the cause
- verify the original problem and related flow after the fix

Do not automatically invoke external Superpowers or require their exact tooling unless the user explicitly asks and the environment allows it.

## Low-Interruption Rule

Debugging should not become a questionnaire.

- use one compact evidence card before inspecting or reproducing when evidence is missing
- if the user already provided files, screenshots, logs, errors, or steps, inspect them first instead of asking
- if evidence is incomplete but not blocking, put it under `待确认但不阻塞`
- do not ask about new features, refactors, frameworks, or delivery changes during bug diagnosis
- after the first answer, summarize the likely path and proceed with the smallest safe reproduction or evidence check

## First Response

If the user gave enough context, summarize the issue and ask for the first missing evidence.

```text
我先按功能调试模式处理。这里先不加新功能，先确认原承诺功能为什么没有按预期工作。

我当前理解：
- 出问题的功能：
- 实际结果：
- 期望结果：

先补一个关键证据：
1. 提供复现步骤（推荐）：我需要知道怎么稳定触发问题。
2. 提供样例文件/截图/日志。
3. 我先根据现有项目文件尝试复现。

请回复数字，也可以直接写自定义情况。
```

If the user only says "坏了" or "不对", ask:

```text
这个问题先按功能调试处理。请先确认问题表现：
1. 输出结果不对（推荐）
2. 程序报错或打不开
3. 按钮/交互没反应
4. 样式或界面显示不对
5. 其他，我直接描述

请回复数字，也可以直接写自定义表现。
```

## Debug Flow

1. Classify the issue:
   - Bug: promised current-scope behavior failed.
   - Data issue: input does not match known format.
   - Environment issue: target computer or dependency mismatch.
   - New requirement: user expects behavior that was not promised.
   - UI issue: rendered interface or interaction problem.

2. Reproduce:
   - exact input
   - exact steps
   - actual result
   - expected result
   - whether it happens every time

3. Gather evidence:
   - error message, console log, terminal output, screenshot, sample input/output, changed files, recent commits
   - for data tools: keep original files read-only and compare before/after output
   - for UI tools: use rendered page evidence when possible
   - for packaged tools: test the packaged artifact, not only source code

4. Find root cause:
   - trace where the bad value or broken state starts
   - compare against similar working code or previous version
   - identify the smallest cause that explains the symptom

5. Fix:
   - make one focused change
   - do not add features during bug fixing
   - avoid broad refactors unless root cause proves the structure is wrong

6. Verify:
   - original issue no longer reproduces
   - promised current-scope behavior still works
   - related nearby behavior still works
   - evidence level is updated

## Stop Rules

Stop and ask before continuing when:

- issue cannot be reproduced and no evidence is available
- requested fix is actually a new feature
- three small fix attempts fail
- the suspected root cause requires architecture or data model changes
- the fix touches shared systems, devices, production data, or original source files
- validation cannot be run on the target delivery form

## Mode Test Prompts

```text
项目调试
导入 Excel 后生成的汇总表数量不对。
```

Expected:

- classify as function debugging
- ask for sample input or reproduction steps
- do not add new features
- require validation against the same sample after fix

```text
功能调试
按钮点了没反应，顺便帮我加一个导出 PDF。
```

Expected:

- classify button issue as Bug
- classify export PDF as New feature
- recommend fixing Bug first
- ask whether PDF export goes to roadmap or current scope
