# 功能调试

Use when promised behavior fails, results are wrong, the app crashes, or a regression appears. Shared interaction and execution rules come from `references/核心执行流程.md`.

## Debug Contract

Do not add features or redesign architecture before locating the failing boundary.

```text
稳定复现 -> 收集证据 -> 工作/失败路径对比 -> 单一根因假设 -> 最小实验 -> 最小修复 -> 新鲜回归
```

## Evidence First

Inspect available reproduction steps, input, actual/expected result, error output, logs, screenshots, environment, recent diff, and related tests. Ask the user only for evidence that cannot be obtained locally and changes the next diagnostic step.

If the issue cannot be reproduced, do not invent a cause. Add safe observability, narrow the reproduction, or report the exact missing evidence.

## Hypothesis Discipline

- State one root-cause hypothesis and why the evidence supports it.
- Run the smallest experiment that can disprove it.
- Change one meaningful variable at a time.
- Fix the root cause, not a nearby symptom.
- Avoid bundled refactors and unrelated cleanup.
- After three failed hypotheses, stop and complete a read-only review of component boundaries, shared-state ownership/lifecycle, requirement assumptions, environment differences, and missing instrumentation/evidence before another fix.

Follow the debugging branch and no-TDD execution order in `references/核心执行流程.md`.

## User Gates

Routine local diagnosis and a narrow authorized fix need no extra confirmation. Ask only when the fix changes approved behavior, data/schema, dependency, delivery, write boundary, external system, device, or another consequential contract.

## Completion

Report:

```text
问题表现和复现：
根因与证据：
修复范围：
验证命令/结果：
仍未验证：
残余风险：
```

Do not claim a fix from code inspection alone. Rerun the original failure path and the narrow relevant regression checks.
