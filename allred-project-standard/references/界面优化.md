# 界面优化

Use this reference when the user wants to improve UI, layout, visual quality, interaction clarity, or ease of use in an existing app or page.

## Benchmarks

Primary benchmarks:

- `frontend-testing-debugging`: define target flow, inspect rendered UI, collect screenshot or interaction evidence.
- `redesign-existing-projects`: diagnose before fixing, make targeted upgrades, do not rewrite from scratch.

Reuse:

- identify the target user flow first
- diagnose visible problems before editing
- make focused changes in the existing stack
- verify rendered result, not just code build
- check interaction, console/logs, layout, and responsive behavior when applicable

Adaptation for company projects:

- prioritize ordinary employee usability over visual novelty
- keep operational tools dense, readable, and predictable
- avoid large redesigns unless the user explicitly asks
- validate that text, buttons, and outputs are understandable to the target role

## First Response

```text
我先按界面优化模式处理。这里不默认重做整个界面，先确认要让哪个操作更清楚、更快或更顺手。

这次界面优化的目标是什么？
1. 让主要操作更清楚（推荐）
2. 让页面更美观统一
3. 修复布局错位、遮挡、文字溢出等问题
4. 适配普通员工或移动端使用
5. 其他，我直接描述

请回复数字，也可以直接写自定义目标。
```

## UI Optimization Flow

1. Define target flow:
   - entry page
   - main user action
   - expected result
   - target user role

2. Capture current evidence:
   - screenshot or rendered view when possible
   - visible problem
   - user friction
   - console/log errors if UI is interactive

3. Diagnose:
   - hierarchy unclear
   - button action unclear
   - text too much or too small
   - layout overlap or clipping
   - missing empty/loading/error state
   - poor responsive behavior
   - inconsistent style with existing project

4. Choose optimization type:
   - clarity: labels, grouping, primary action, empty/error state
   - efficiency: fewer clicks, default values, table density, filters
   - visual polish: spacing, typography, colors, icons, alignment
   - responsiveness: desktop/mobile width, overflow, wrapping

5. Edit:
   - work with the existing tech stack
   - preserve existing behavior
   - avoid broad rewrite
   - avoid adding libraries unless necessary and approved

6. Validate:
   - page is not blank
   - main flow still works
   - no obvious console/runtime errors when applicable
   - no overlap, clipping, unreadable text, broken states
   - screenshot or manual evidence shows improvement

## Stop Rules

Stop and ask before continuing when:

- user wants a full redesign instead of targeted optimization
- design direction conflicts with existing product style
- UI change may change workflow or data meaning
- validation requires a browser/plugin/tool that is unavailable
- user requests visual changes without a target flow and the impact is unclear
- fixing UI would require rewriting core architecture

## Mode Test Prompts

```text
界面优化
这个工具页面不好用，按钮太乱。
```

Expected:

- ask for target operation or recommend focusing on main operation
- diagnose before changing
- do not rewrite whole app immediately
- validate interaction after changes

```text
UI 优化
表格在小屏幕上文字挤在一起。
```

Expected:

- classify as responsive/layout issue
- inspect rendered evidence if possible
- fix wrapping/overflow/table behavior
- verify desktop and small viewport when practical
