# 核心执行流程

This reference owns the shared workflow for every Allred project mode. Mode references contain only their differences.

## Objective

Keep engineering discipline internal and user interaction compact:

```text
路由定界 -> 读取证据 -> 内部方案 -> 必要决策 -> 连续执行 -> 新鲜验证 -> 交付沉淀
```

This is adapted from the strongest Superpowers patterns without importing its mandatory process chain. Allred does not require brainstorming for every task, spec approval, per-task commits, worktrees, subagents, or batch feedback checkpoints. TDD and Red-Green are not used as the execution order.

## Execution Lanes

Choose the lane from evidence; do not ask the user to select a level.

| Lane | Use when | User gates | Record depth |
| --- | --- | ---: | --- |
| Fast | exact scope, local/reversible change, known pattern | 0 | conversation + verification |
| Standard | non-trivial new project or material behavior choice | one combined gate after read-only preflight | execution contract; durable card when useful |
| Deep | long-term, cross-module, shared data, device/system, high consequence | 1 scope gate; later gates only if new evidence requires | checkpoint, evidence, handoff |

The lane may change after inspection. State why only when the change affects user expectations or authorization.

## Phase 1: Route And Bound

Determine:

- new project, feature, debugging, UI, acceptance, long-term continuation, or Skill improvement
- exact current outcome and non-goals
- project and write boundary
- whether the request is analysis-only, implementation, or external action

Do not restart an existing project through new-project discovery. Do not treat beginner interaction as reduced project complexity.

## Phase 2: Inspect Evidence

Read the smallest set that can establish the current truth:

1. user-provided materials and initial idea
2. current project state, source, tests, logs, prior decisions, and recent diff
3. local known-good implementation or workflow
4. official maintained reference when local evidence is insufficient
5. external benchmark only for an unresolved design gap
6. installed capability inventory before new dependencies or Skills

Do not ask factual questions that files or tools can answer. Do not claim a file, source, benchmark, or capability was inspected until the read/tool event completed.

## Phase 3: Build The Internal Proposal

Internally derive:

- problem, user, constraints, non-goals, success criteria
- selected basis/benchmark and deliberate differences
- total scope and current scope when separation is useful
- execution lane, file/write boundary, rollback/checkpoint
- narrow verification and target-environment validation
- decision ledger: `confirmed`, `blocking`, `deferrable`, `conflicting`

Do not expose method management as user questions. The user decides product meaning and risk boundaries; Codex selects technical method and verification by default.

## Phase 4: Open A User Gate Only When Needed

There are only two user gate types.

### Product Decision Gate

Use when valid alternatives materially change scope, visible behavior, evidence meaning, delivery experience, cost, ownership, or acceptance. Combine related choices in one card. A standard task normally needs at most one such card.

### Consequential Authorization Gate

Use immediately before an action involving destructive/shared writes, installation, credentials, cost, external upload, Git publication, deployment, device/system operation, or another irreversible consequence not already authorized.

Do not ask a second unchanged start question. A non-trivial new project uses one combined named scope/start gate after all read-only preflight. An exact user instruction referring to that already displayed scope authorizes it. An existing-project safe local change with exact behavior and acceptance normally proceeds without a gate.

## Phase 5: Create The Execution Contract

The contract may stay in the conversation for ordinary work. Persist it only for complex, long-term, shared, or handed-off work.

Include only what is needed:

- current objective and non-goals
- inputs and evidence basis
- output and user-visible behavior
- planned write/no-touch boundary
- verification and completion evidence
- rollback/checkpoint for consequential writes

Do not duplicate the same content into separate spec, design, plan, and memory documents. Add a separate decision record only when the decision is durable and reusable.

## Phase 6: Execute Continuously

- Make the smallest coherent change that advances the contract.
- Run narrow checks after each meaningful slice.
- Continue without approval while scope and risk remain unchanged.
- Give progress updates at meaningful checkpoints; updates are not questions.
- Do not introduce unrelated refactors, features, dependencies, or data writes.
- Stop when a real blocker appears; do not guess through it.

### Debugging Branch

1. reproduce or clearly establish the observed failure
2. collect logs, traces, diffs, inputs, and environment evidence
3. locate the failing boundary and compare with a working path
4. state one root-cause hypothesis and its evidence
5. run the smallest discriminating experiment
6. fix the root cause with the smallest compatible change
7. rerun the reproduction and relevant regression checks

Do not use TDD or Red-Green as the execution order. First analyze and discriminate the root cause, then implement, then add or run targeted regression checks according to risk. For a bug, retain a reproducible case when practical. If three distinct root-cause hypotheses fail, stop before a fourth patch and complete a read-only architecture review covering: component boundaries, shared-state ownership/lifecycle, requirement assumptions, environment differences, and missing instrumentation/evidence.

## Phase 7: Verify Before Claiming

Fresh evidence is mandatory before claims such as complete, fixed, usable, packaged, or ready.

1. identify the command, rendered check, device observation, or artifact that proves each promised item
2. run it now, not from memory
3. inspect exit status and relevant output
4. map evidence to the exact promised behavior
5. state unsupported items under `仍未验证`

For an acceptance request, reconstruct and show the exact promised-item ledger before the conclusion. If the approved scope cannot be found, report that acceptance is incomplete instead of substituting generic test/build status.

Passing a narrow test does not prove the target environment, live device, packaging, security, or full acceptance unless that exact layer was tested.

## Phase 8: Close Or Hand Off

Report:

- delivered result and changed boundary
- fresh verification evidence
- remaining gaps and risk
- rollback/checkpoint when relevant
- smallest next action

Use `allred记忆` and `allred笔记` only when explicitly triggered. Do not automatically create project memory, a personal Vault, commits, pushes, releases, or deployments.

## Efficiency Acceptance

- clear Fast-lane task: 0 decision questions
- normal Standard-lane task: usually 1 consolidated gate
- Deep-lane task: one scope gate; later gates require named new evidence or consequential authorization
- repeated unchanged scope: no duplicate confirmation
- every completion claim: fresh evidence
- debugging: no fix before evidence and hypothesis; architecture review after three failed hypotheses
