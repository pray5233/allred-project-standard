# 核心执行流程

This reference owns the shared workflow for every Allred project mode. Mode references contain only their differences.

## Objective

Keep engineering discipline internal and user interaction compact:

```text
路由定界 -> 读取证据 -> 内部方案 -> 必要决策 -> 连续执行 -> 新鲜验证 -> 交付沉淀
```

This is adapted from the strongest Superpowers patterns without importing its mandatory process chain. Allred does not require brainstorming for every task, spec approval, per-task commits, worktrees, subagents, or batch feedback checkpoints. TDD and Red-Green are not used as the execution order.

## Execution Lanes

Choose the lane from evidence; do not ask the user to select a level.

| Lane | Use when | User gates | Record depth |
| --- | --- | ---: | --- |
| Fast | exact scope, local/reversible change, known pattern | no ceremonial interaction; ask only for a real unresolved dependency or consequence | conversation + verification |
| Standard | non-trivial new project or material behavior choice | concentrated discovery and decisions as needed; combine stable scope/start | execution contract; durable card when useful |
| Deep | long-term, cross-module, shared data, device/system, high consequence | multiple concentrated rounds are allowed when dependency depth or consequence requires them | checkpoint, evidence, handoff |

The lane may change after inspection. State why only when the change affects user expectations or authorization.

## Mandatory Internal Stage Gate

For non-trivial new-project product work, maintain this internal state even when several stages complete within one response:

```text
INTAKE -> EVIDENCE -> DECISION -> READY -> EXECUTION
```

| Stage | Exit condition | Allowed | Forbidden |
| --- | --- | --- | --- |
| `INTAKE` | rough outcome, material state, user initial idea, and material missing basis are known | restate, inspect workspace, request the concentrated missing baseline as factual/open `Q` items | product `D` alternatives, complete first-version package, recommendation bundle, start gate, mutation |
| `EVIDENCE` | the smallest relevant materials/environment/basis were actually inspected or their absence was recorded | read-only inspection, factual feasibility findings, evidence gaps | converting evidence into user-visible behavior, final scope, start gate, mutation |
| `DECISION` | every blocking user-owned product/consequence decision is answered or explicitly deferred with a coherent result | one dependency-correct concentrated packet, evidence-backed recommendations | hidden defaults, sibling approval by omission, mutation |
| `READY` | product decisions are complete; read-only technical preflight and the internal execution record are complete; plain-language scope, data/effects, limits, acceptance, and no unresolved blocker can be shown in one final envelope | request one explicit scope/start authorization | file creation, dependency installation, development command, or other mutation before approval |
| `EXECUTION` | the READY envelope was explicitly approved, or an exact complete user instruction already supplied equivalent scope and start authority | approved implementation and verification | scope expansion or a new consequential effect without returning to the affected gate |

These are reasoning stages, not required conversation turns. A complete exact request may satisfy several exit conditions immediately; do not create ceremonial questions. Conversely, model confidence, a benchmark, a Windows host, or sample evidence cannot skip a missing user-owned condition.

The route context is part of the gate:

- load `intake` before initial new-project alignment
- load `evidence` before interpreting supplied materials as project evidence
- for a non-trivial new project, maintain the schema-1 state package from `references/阶段状态硬校验.md` under a session temporary directory
- validate `DECISION` and pass `-StatePath` when loading the new-project `decision` route
- validate `READY` before exposing the final scope/start envelope
- after exact approval, validate `EXECUTION` and pass `-StatePath` when loading the execution route

Do not display internal stage names to ordinary users. Before READY, progress wording may say `先读取/核对/整理`; it must not promise `直接搭出`, `开始实现`, or equivalent mutation.

A user-facing product decision or READY envelope needs a same-response successful transition validation. When the state package or validator is unavailable, remain in EVIDENCE and report the internal control blocker; do not substitute an unvalidated prose card.

Later evidence may preserve READY only when it adds technical facts without changing product meaning or significant effects. If it creates or changes visible behavior, delivery, data transmission, persistence, cost, acceptance, or a material limitation, invalidate only the affected READY items and return them to DECISION.

## Phase 1: Route And Bound

Determine:

- new project, feature, debugging, UI, acceptance, long-term continuation, or Skill improvement
- exact current outcome and non-goals
- project and write boundary
- whether the request is analysis-only, implementation, or external action
- whether the user already supplied a first-version idea or only a broad product label

Do not restart an existing project through new-project discovery. Do not treat beginner interaction as reduced project complexity.

## Phase 2: Inspect Evidence

Read the smallest set that can establish the current truth:

1. user-provided materials and initial idea
2. current project state, source, tests, logs, prior decisions, and recent diff
3. local known-good implementation or workflow
4. official maintained reference when local evidence is insufficient
5. external benchmark only for an unresolved design gap
6. installed capability inventory before new dependencies or Skills

Do not ask factual questions that files or tools can answer. Do not claim a file, source, benchmark, or capability was inspected until the read/tool event completed.

Evidence establishes current facts, feasibility, and technical constraints. It never chooses a user-visible workflow, delivery experience, transmission permission, persistence rule, scope, or acceptance meaning. A product consequence suggested by evidence remains a recommendation for DECISION.

When parsing or visual inspection needs generated previews, extracted text, screenshots, or logs, write disposable artifacts only under an isolated system temporary directory. Do not write them into the project before authorization. Record that write and keep the original evidence unchanged.

## Phase 3: Build The Internal Proposal

For product ambiguity, use `references/动态项目契约.md`. Internally derive:

- problem, user, constraints, non-goals, success criteria
- selected basis/benchmark and deliberate differences
- total scope and current scope when separation is useful
- execution lane, file/write boundary, rollback/checkpoint
- narrow verification and target-environment validation
- provenance and confidence: `U/E/R/D/X` plus `Confident`, `Likely`, or `Unclear`
- decision ledger: `confirmed`, `blocking`, `deferrable`, `conflicting`

Do not expose contract slots or method management as user questions. The user decides product meaning and risk boundaries; Codex selects technical method and verification by default. Before showing a card, rank unresolved items and expose only user-owned, high-impact decisions that cannot be answered through inspection.

Apply the recommendation admission filter before any `R` enters a visible contract. Remove convenience features and speculative future behavior that do not serve an approved outcome, proven risk, or required verification.

Do not build a complete first-version recommendation until the recommendation-readiness gate in `references/动态项目契约.md` passes. If it does not pass, stay in INTAKE/EVIDENCE and request only the missing user-owned basis in one concentrated packet.

For a non-trivial new project, update the temporary state package and run `scripts/invoke_validation_gate.ps1` with `-ToStage DECISION` before product `D` alternatives are shown. The aggregate gate checks readiness, conditional complexity communication, and the active decision frontier; it does not limit question count.

## Phase 4: Open A User Gate Only When Needed

Keep gate purpose distinct even when several interactions are needed.

### Product Decision Gate

Use when valid alternatives materially change scope, visible behavior, evidence meaning, delivery experience, cost, ownership, or acceptance. The item must also remain unresolved after safe inspection and be user-owned. Batch all currently knowable related choices; use another round only when dependencies make earlier presentation premature or new evidence changes the decision.

One decision ID owns one material axis. Do not bundle a delivery choice with feature scope, data transmission, update behavior, or acceptance merely to reduce turn count.

Before a decision packet is shown, update its proposed frontier and pass `scripts/invoke_validation_gate.ps1` with `-ToStage DECISION`. A child may wait for its parent and appear later; it may not be exposed early and then invalidated by the parent. Users may answer naturally without writing IDs.

Preserve user-named future decision topics across inspection. When the requested evidence arrives, expose every topic whose options and material impacts are now explainable in the same concentrated packet. A dependent child may be included with an exact parent-option dependency; postpone it only when the parent answer is needed to discover or formulate the child choices, not merely because it is dependent.

### Consequential Authorization Gate

Use immediately before an action involving destructive/shared writes, installation, credentials, cost, external upload, Git publication, deployment, device/system operation, or another irreversible consequence not already authorized.

Do not ask an unchanged start question again. Combine named scope/start only at READY, after the scope is stable and the decision route was loaded. An exact user instruction referring to that READY envelope authorizes it. `继续`, `按推荐`, or approval of an earlier decision packet advances only that packet and does not retroactively become development authority. An existing-project safe local change with exact behavior and acceptance proceeds unless a real unresolved dependency or consequence remains.

A user request to prepare the final card does not substitute for technical READY preflight. If the exact implementation path, dependencies/effects, write boundary, rollback, and promise proofs are not yet internally complete, announce only that read-only preflight is underway or name the real blocker. Do not show the final scope/start options in the same response that initiates or awaits preflight.

Before opening the gate, run the contract consistency lint from `references/动态项目契约.md`. Evidence does not authorize product meaning. A final combined gate may introduce a clearly labeled `R` item only when its approval envelope explicitly converts it to `D`; it may never present it as already confirmed.

Update the temporary state with the exact visible scope and semantic relation, technical conclusion levels, preflight, execution-record path, and write boundary. Run `scripts/invoke_validation_gate.ps1` with `-ToStage READY`; it owns all component validation and returns one result. Do not show the start option after a failed result.

When an approved contract exists, compare the next contract against it and label unchanged `U/D`, technical `E`, new `R`, and removed `X` separately.

## Phase 5: Create The Execution Contract

The contract may stay in the conversation for ordinary work. Persist it only for complex, long-term, shared, or handed-off work.

Include only what is needed:

- current objective and non-goals
- inputs and evidence basis
- output and user-visible behavior
- development-time, runtime, and external/system mutation ledger plus no-touch boundary
- command effects including network, dependencies, caches, processes, and generated files when relevant
- promise-by-promise acceptance ledger and target environment
- decision coverage from every active `U/D` item to implementation/document targets and acceptance Promise IDs
- rollback/checkpoint for every material mutation layer

Prepare the Codex execution record from `templates/Codex执行记录.md` before mutation. The user confirms product scope and significant effects in plain language; routine implementation detail stays Codex-owned and does not create another gate.

No new-project mutation begins until EXECUTION is active. Read-only workspace/material/benchmark/capability inspection may use disclosed disposable outputs only in the isolated session temporary directory. Creating project files, writing analysis artifacts into the project, installing dependencies, generating lock files, running commands that write project/runtime caches or outputs, and starting the App/tool implementation are mutation.

- Fast work may keep the record in the current conversation when scope, effects, proof, and rollback remain inspectable.
- Standard new-project work builds the complete record before the visible gate, then persists it immediately after the user authorizes start and before any other project mutation.
- Deep, long-term, shared, high-consequence, release, or handed-off work uses a durable record before substantive mutation.
- Follow an existing project ADR/task/debug-log convention. When none exists, use `.allred/execution/<record-id>.md` inside the authorized project boundary.
- Run `scripts/invoke_validation_gate.ps1` with `-ToStage READY` against the state package and its persisted execution record before showing the start envelope. A failed component check is an internal blocker, not another user question.
- Whenever active scope, implementation targets, or acceptance evidence changes, update the state and execution record, then rerun the aggregate gate. Missing decision coverage blocks closure.
- After the user approves the exact READY envelope, update its temporary authorization state and run `scripts/invoke_validation_gate.ps1` with `-ToStage EXECUTION` before the first project mutation.
- Update the same record version for technical-method changes that preserve product scope; create a new version when approved scope or consequential effects change.

The record must have one stable ID, an approved-scope reference, exact evidence IDs, exact files and commands, command effects, all three mutation layers, an explicit no-hidden-`R`/consequence reconciliation, one acceptance row per promise, rollback, and fresh execution results. `None` is a valid explicit value; an empty field is not.

Do not duplicate the same content into separate spec, design, plan, and memory documents. Add a separate decision record only when the decision is durable and reusable.

When a correction changes part of the contract, preserve unaffected decisions but present one complete replacement scope before mutation. Do not require the user to reconstruct the active scope from V1/V2/V3 fragments.

## Phase 6: Execute Continuously

- Make the smallest coherent change that advances the contract.
- Run narrow checks after each meaningful slice.
- Continue without approval while scope and risk remain unchanged.
- Give progress updates at meaningful checkpoints; updates are not questions.
- Do not introduce unrelated refactors, features, dependencies, or data writes.
- Stop when a real blocker appears; do not guess through it.
- For source-backed products, semantic relevance failure in the only core retrieval path is a blocker. Do not proceed to implementation as though transport success proved the outcome.

### Debugging Branch

1. reproduce or clearly establish the observed failure
2. collect logs, traces, diffs, inputs, and environment evidence
3. locate the failing boundary and compare with a working path
4. state one root-cause hypothesis and its evidence
5. run the smallest discriminating experiment
6. fix the root cause with the smallest compatible change
7. rerun the reproduction and relevant regression checks

Do not use TDD or Red-Green as the execution order. First analyze and discriminate the root cause, then implement, then add or run targeted regression checks according to risk. For a bug, retain a reproducible case when practical. If three distinct root-cause hypotheses fail, stop before a fourth patch and complete a read-only architecture review covering: component boundaries, shared-state ownership/lifecycle, requirement assumptions, environment differences, and missing instrumentation/evidence.

## Phase 7: Verify Before Claiming

Fresh evidence is mandatory before claims such as complete, fixed, usable, packaged, or ready.

1. identify the command, rendered check, device observation, or artifact that proves each promised item
2. run it now, not from memory
3. inspect exit status and relevant output
4. map evidence to the exact promised behavior
5. state unsupported items under `仍未验证`

For an acceptance request, reconstruct and show the exact promised-item ledger before the conclusion. If the approved scope cannot be found, report that acceptance is incomplete instead of substituting generic test/build status.

Passing a narrow test does not prove the target environment, live device, packaging, security, or full acceptance unless that exact layer was tested.

## Phase 8: Close Or Hand Off

Report:

- delivered result and changed boundary
- fresh verification evidence, preserving both method and material observation for each promise; do not replace hashes, field checks, sample values, explicit render checks, or target-environment observations with a generic success phrase
- remaining gaps and risk
- rollback/checkpoint when relevant
- smallest next action

Use `allred记忆` and `allred笔记` only when explicitly triggered. Do not automatically create project memory, a personal Vault, commits, pushes, releases, or deployments.

## Efficiency Acceptance

- no fixed interaction or decision-count target
- every round has a named information, decision, contradiction, dependency, or authorization purpose
- all independent currently knowable questions are batched instead of serialized
- dependent questions appear only after the parent answer makes them relevant
- clear exact work has no ceremonial interaction
- complex work may use additional concentrated rounds when they improve correctness or user control
- repeated unchanged scope: no duplicate confirmation
- unchanged Skill/project references in one task: no duplicate read unless freshness or newly routed detail requires it
- every completion claim: fresh evidence
- debugging: no fix before evidence and hypothesis; architecture review after three failed hypotheses
