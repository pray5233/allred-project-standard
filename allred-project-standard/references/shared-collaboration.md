# Shared Collaboration Overlay

Load this overlay only after current evidence or an explicit user choice confirms that multiple actors share authority over the same live project state. It is not activated by multiple departments, source files, readers, reviewers, training participants, or shared folders alone.

## Boundary And Activation

The activation test is behavioral:

- at least two actors can create, change, approve, close, delete, reconcile, or restore the same live records; or
- one actor's change controls what another actor may subsequently do; or
- the requested result requires shared authority, conflict handling, or accountable history.

Do not load this overlay for one-time consolidation, read-only reporting, independent departmental files, document audiences, or a single operator who imports several sources. If the sharing model is still a user-owned product choice, keep one parent decision on the normal frontier; load this overlay only after the shared branch is selected.

## Intake Handoff

Selecting the shared branch confirms only the collaboration direction. It does not settle how the future solution will govern people or data.

During INTAKE, ask only for current facts needed to inspect evidence: actual participants and today's responsibilities, current records/source/workflow, sensitive constraints, material location, and the useful result the user wants. Reuse facts already requested or answered in the immediately preceding packet; do not reopen them merely because the shared branch was selected.

If samples were promised but not supplied, acknowledge the shared choice, preserve every still-open current-fact cluster, and ask for the samples plus only unanswered current facts. Do not ask the user to design the future shared solution at this point. Future operating rules belong to DECISION after evidence.

Before those questions, explain once that current participants, workflow/source, sensitivity, materials, and useful result determine the shared update boundary, which evidence must be inspected, and later acceptance. Do not merely say that the questions remain unanswered.

## Evidence And Ownership

Inspect existing roles, source-of-truth rules, approval steps, file/database ownership, current conflict handling, sensitive fields, continuity expectations, and acceptance ownership before recommending a future model. Current facts are `Q`; future authority and product behavior are `D`.

Preserve literal evidence. `跨部门` does not define departments or roles. `多人使用` does not prove shared writes. `共享文件夹` does not prove a central source of truth.

At EVIDENCE, inspect the supplied samples against the preserved current-fact ledger. Report what the samples establish and what remains unknown before recommending a future model. A sample may reveal a current practice, but it does not approve future operating rules.

## Decision Packet

After the shared parent is confirmed, explain once why authority, conflict, operation, and acceptance are relevant. The active route guard owns the five-group rendering; this reference owns meaning.

Use ID-free headings and one why-now/basis line per group. Classify each suffix before rendering: `Q` records current reality; include/allow/do choices are `D`. Each suffix bullet includes its own `影响：...` and `回复：...`; later group text or examples never substitute. Before sending, pipe the exact draft through `scripts/validate_question_packet.ps1`; after PASS send it unchanged or re-lint. Recommend only from project evidence or a comparable benchmark, otherwise stay neutral. Accept one natural-prose reply for the packet, and never hide or default questions.

`Q` is current reality and `D` is future behavior. Unknown Q defers recommendations, not neutral D. Hosting is not availability; audit is not recovery. For discovery-only work, list every deferrable D and the exact later design, implementation, or acceptance work it blocks. Consequential questions are not automatically mandatory now.

## Conflict Audit And Recovery

Run option-compatibility lint before sending the packet:

- authority options distinguish submit/create, edit, approve/close, reopen, and delete; never combine `view or submit`
- any offline entry, temporary table, replay, reconciliation, or synchronization path binds exact conflict and audit choices
- `not applicable` binds the exact option that removes the behavior
- a deferred rule blocks only its dependent implementation or acceptance behavior; keep that exact consequence visible

Canonical audit evidence is: `actor`, `time`, `action`, `result`, `before/after`, `source/submission chain`, `failed actions`, `denied actions`, and `recovery evidence`.

- `none` excludes every audit label
- `basic` includes actor/time/action/result only
- `complete` includes every label

Audit evidence does not prove restore capability. Recovery is a separate behavior and must have its own authority, procedure, and verification.

## Verification

Verify the selected authority matrix, conflict path, denied actions, audit contents, recovery behavior, persistence, and acceptance ownership with representative roles and data. A role table or UI mockup does not prove enforcement. A history log does not prove recovery.
