# 阶段状态硬校验

Use this reference for non-trivial new-project transitions. It turns the existing stage, decision, and provenance rules into deterministic checks without imposing a question count or exposing internal bookkeeping to the user.

## State Package

Maintain one session-scoped JSON state package outside the project, preferably under:

```text
$env:TEMP\allred-project-standard\<unique-task-id>\project-state.json
```

Do not place it in the user's project, source tree, evidence folder, or deliverable. Update it after material evidence or a user answer changes the current contract. The package uses schema version `1` and contains:

- `intake`: outcome, material state, user initial idea/delegation, and recognizable useful result
- `user_sources`: exact user excerpts, normalized meanings, and `authority` (`requirement`, `explicit-exclusion`, `constraint`, `context`, `acceptance`, or `delegation`) for every `U` source used later
- `complexity`: current assessment, evidence-backed drivers, and whether concrete user impact was communicated
- `evidence`: observed, reported, inferred, or hypothetical claims with method, confidence, and limitations
- `discovery_coverage`: the three review methods, all current evidence IDs, six broad internal lenses, task-specific facet summaries, status/basis, linked decisions/scope, and exact deferral or not-applicable reasons
- `decisions`: one axis per `D`, exact dependencies, trigger, state, choice, approval source, semantic authority, and recommendation basis
- `scope`: one final-scope item per statement with `U/E/D/R/B` provenance and a semantic `relation` (`required`, `excluded`, `recommended`, `acceptance`, or `technical`)
- `technical_conclusions`: `candidate`, `verified`, or `unknown`, with named source, version/date, comparability, deliberate differences, method, and limitations
- `preflight`, including `execution_record.path`, plus `blocking_items`, `authorization`, and the user-reply interaction contract
- `write_boundary`: absolute project root, confirmation state, `U/D/R` provenance, recommendation prominence, allowed roots, protected inputs, planned paths, rollback, and READY visibility
- `change_control`: a candidate baseline for a new project, or a confirmed baseline plus the current delta for existing work; it also keeps only genuinely non-blocking later items with exact provenance and revisit conditions

The JSON is an internal control artifact. Do not show it or ask the user to maintain it.

## Stage Transition Gate

Before loading the `decision` route for a non-trivial new project, run:

```powershell
& scripts\invoke_validation_gate.ps1 -Path <temp-state> -ToStage DECISION
```

The gate accepts materials that are inspected, unavailable, or deliberately deferred. It accepts a user initial idea or an explicit delegation for Codex to draft alternatives. It does not require uploads, fixed questions, or a fixed number of turns.

For `non-simple` or still-`unknown` complexity, communicate the concrete effect inside a useful packet. Do not create a separate size ceremony. A simple project may mark complexity `simple` and collapse stages when every exit condition is already supported.

Before showing the final READY scope, run:

```powershell
& scripts\invoke_validation_gate.ps1 -Path <temp-state> -ToStage READY
```

The aggregate gate runs each component validator in an isolated child PowerShell process and returns one PASS/FAIL result. This avoids stale process exit state and prevents a model from skipping or reordering checks. For READY it includes `validate_stage_transition.ps1`, `validate_decision_frontier.ps1`, `validate_discovery_coverage.ps1`, `validate_execution_record.ps1`, `validate_decision_coverage.ps1`, `validate_ready_scope.ps1`, and `validate_change_traceability.ps1`.

After the exact READY envelope is approved and before mutation, update `authorization.state` and `approval_source`, then run:

```powershell
& scripts\invoke_validation_gate.ps1 -Path <temp-state> -ToStage EXECUTION
```

Do not work around a failure by weakening the state. Correct the missing evidence, dependency, provenance, or authorization, or remain in the current stage.

Do not manually chain the component validators. `invoke_validation_gate.ps1` is the public stage command; the individual scripts remain narrow implementation units and diagnostics.

The validation event belongs to the same response that exposes a product decision, READY scope, or starts execution. A prior generic route read is not enough. If the state package cannot be written or the validator cannot run, remain in EVIDENCE and state the internal blocker instead of generating an unvalidated packet.

## Decision Frontier Gate

`validate_decision_frontier.ps1` allows any number of rounds. It rejects structural decision defects:

- a child is exposed or retained before its exact parent choice is confirmed
- a confirmed child is invalidated by a later parent choice
- two active IDs claim the same material axis
- a confirmed choice has no exact user or envelope approval source
- a visible decision has no baseline, user, evidence, or parent-decision trigger
- a recommendation lacks exact `U/E/D` basis

Every dependency uses an exact parent ID and allowed choice list. A later round is valid when new evidence or an earlier answer makes the child meaningful. Do not invent a parent merely to combine questions, and do not mark a real dependency `None` to pass validation.

## Discovery Coverage Gate

`validate_discovery_coverage.ps1` runs for READY and EXECUTION. It does not count questions. It rejects:

- a missing or incomplete internal coverage review
- omission of contract-slot, evidence-gap, or counterexample review
- a missing workflow, information, lifecycle, operating-scale, delivery/effects, or acceptance lens
- an open or investigating consequential lens at READY
- a not-applicable lens without an evidence/user basis and reason
- a deferred lens without exact U/D provenance, consequence, and revisit condition
- current evidence that was not included in the latest review
- a confirmed/deferred decision or final scope item absent from every coverage lens

The lenses are broad internal safeguards, not visible questionnaire sections. A project may answer them from evidence and ask zero additional questions. Conversely, a non-simple project may require several dependency-ordered rounds. Do not weaken or falsify the coverage state to preserve a short conversation.

## READY Scope Gate

`validate_ready_scope.ps1` requires every final item to have provenance:

- `U`: directly supplied user requirement or boundary
- `D`: confirmed user-owned decision
- `E`: evidence supporting a fact or feasibility claim; it cannot authorize user-visible behavior by itself
- `R`: new Codex recommendation, prominently labeled and included in the exact final approval envelope
- `B`: benchmark basis for technical reasoning, not product authorization

It checks semantic direction through source `authority` and scope `relation`. `不能只有 A` preserves A and asks for an additional alternative; it never authorizes excluding A. Exclusion needs exact exclusion authority or a prominent pending recommendation.

READY exposes `write_boundary`: project root, allowed roots, protected inputs, planned paths, and rollback. An unconfirmed candidate root must be `recommended-pending`, carry `R` provenance, and be prominent in the same approval envelope; only exact approval changes it to `confirmed`. Wildcards, empty/out-of-root plans, or protected-input overlap fail.

Technical conclusions use:

- `verified`: the relevant behavior was actually tested with named evidence and method
- `candidate`: evidence supports trying the route, but implementation or integration proof remains
- `unknown`: evidence is insufficient and the limitation remains explicit

Package listings, installed runtimes, documentation, inspection artifacts, or one successful component check do not prove an integrated product path. Keep a candidate label until the promised end-to-end behavior is exercised, and do not promote one successful workflow to general coverage or target-environment acceptance without the matching tests.

## Baseline And Change Traceability Gate

`validate_change_traceability.ps1` adds no user question and no new visible stage. It connects the approved contract to later execution and memory:

- a new project uses `new-baseline`; its candidate baseline covers the exact authorization envelope without inventing a prior system
- existing or continued work uses `delta`; the prior baseline must already be confirmed
- every active scope item is either changed or explicitly preserved, never silently dropped
- `add`, `modify`, and `remove` items point to exact scope and provenance; removal maps to an explicitly excluded scope item
- a later item is non-blocking, has a revisit condition, and stays outside the authorization envelope
- `suggested` is not a user deferral; only exact `U/D` provenance may mark `confirmed-deferred`

The combined chain is: `U/D/E/R -> scope -> baseline/change coverage -> implementation target and Promise -> fresh verification`. Existing decision-coverage validation owns the implementation target and Promise portion; do not duplicate it in the visible conversation.

## Reply Ergonomics

Q/D IDs remain stable internal references and optional shortcuts. Always allow a normal sentence or paragraph. For a packet, say plainly:

```text
你可以直接用一段话回答，不必填写编号。
全部接受时回复“全部按推荐”；只修改某项时直接说明修改内容。
```

Map the user's natural language back to the internal IDs and restate the operative meaning. Do not force `Q1=... D1=...` syntax. A later packet is acceptable when it has a real dependency or new evidence; the validators do not count turns.

When a preflight-complete packet contains the traced core plus the only remaining prominent recommendations, it is the READY envelope, not a direction-only prelude. A natural reply that resolves those recommendations and explicitly starts the resulting scope must not be followed by another unchanged approval card.

## Temporary Evidence

Read-only evidence work may create disposable previews, transformed samples, screenshots, reports, or logs only when inspection needs them. Create the location with `scripts/new_evidence_temp.ps1`; write there, not in the project, future project root, `work`, `outputs`, source, evidence, deliverable, or original-material folders. Record the source, method, output location, evidence layer, and limitation. Never infer a source condition, root cause, required processing method, integrated behavior, or general suitability from one proxy without the matching structural, functional, integration, coverage, or target-environment evidence.

Temporary analysis artifacts are not project development, but they remain writes. Do not hide them, persist sensitive content longer than needed, or treat them as authorization to create project files.

Directly reading this reference or an individual validator is not a stage transition. A user-facing product decision packet, READY envelope, or execution start is valid only when `scripts/get_route_context.ps1 -StatePath <path>` or `scripts/invoke_validation_gate.ps1` runs the aggregate gate for that exact response and passes. If the gate is not run, stay in the current read-only stage.
