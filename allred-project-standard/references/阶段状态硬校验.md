# 阶段状态硬校验

Use this reference for non-trivial new-project transitions. It turns the existing stage, decision, and provenance rules into deterministic checks without imposing a question count or exposing internal bookkeeping to the user.

## State Package

Maintain one session-scoped JSON state package outside the project, preferably under:

```text
$env:TEMP\allred-project-standard\<unique-task-id>\project-state.json
```

Do not place it in the user's project, source tree, evidence folder, or deliverable. Update it after material evidence or a user answer changes the current contract. The package uses schema version `1` and contains:

- `intake`: outcome, material state, user initial idea/delegation, and recognizable useful result
- `user_sources`: exact user excerpts and normalized meanings for every `U` source used later
- `complexity`: current assessment, evidence-backed drivers, and whether concrete user impact was communicated
- `evidence`: observed, reported, inferred, or hypothetical claims with method, confidence, and limitations
- `decisions`: one axis per `D`, exact dependencies, trigger, state, choice, approval source, and recommendation basis
- `scope`: one final-scope item per statement with `U/E/D/R/B` provenance
- `technical_conclusions`: `candidate`, `verified`, or `unknown`, with named source, version/date, comparability, deliberate differences, method, and limitations
- `preflight`, `blocking_items`, `authorization`, and the user-reply interaction contract

The JSON is an internal control artifact. Do not show it or ask the user to maintain it.

## Stage Transition Gate

Before loading the `decision` route for a non-trivial new project, run:

```powershell
& scripts\validate_stage_transition.ps1 -Path <temp-state> -ToStage DECISION
```

The gate accepts materials that are inspected, unavailable, or deliberately deferred. It accepts a user initial idea or an explicit delegation for Codex to draft alternatives. It does not require uploads, fixed questions, or a fixed number of turns.

For `non-simple` or still-`unknown` complexity, communicate the concrete effect inside a useful packet. Do not create a separate size ceremony. A simple project may mark complexity `simple` and collapse stages when every exit condition is already supported.

Before showing the final READY scope, run:

```powershell
& scripts\validate_stage_transition.ps1 -Path <temp-state> -ToStage READY
```

This composes the decision-frontier and READY-scope validators. It also requires a completed read-only technical preflight and a valid internal execution record.

After the exact READY envelope is approved and before mutation, update `authorization.state` and `approval_source`, then run:

```powershell
& scripts\validate_stage_transition.ps1 -Path <temp-state> -ToStage EXECUTION
```

Do not work around a failure by weakening the state. Correct the missing evidence, dependency, provenance, or authorization, or remain in the current stage.

The validation event belongs to the same response that exposes a product decision, READY scope, or starts execution. A prior generic route read is not enough. If the state package cannot be written or the validator cannot run, remain in EVIDENCE and state the internal blocker instead of generating an unvalidated packet.

## Decision Frontier Gate

`validate_decision_frontier.ps1` allows any number of rounds. It rejects structural decision defects:

- a child is exposed or retained before its exact parent choice is confirmed
- a confirmed child is invalidated by a later parent choice
- two active IDs claim the same material axis
- a confirmed choice has no exact user or envelope approval source
- a visible decision has no baseline, user, evidence, or parent-decision trigger
- a recommendation lacks exact `U/E/D` basis

Every dependency uses an exact parent ID and allowed choice list. A later round is valid when new evidence or an earlier answer makes the child meaningful. Do not invent a parent merely to combine questions, and do not mark a real dependency `None` to pass validation.

## READY Scope Gate

`validate_ready_scope.ps1` requires every final item to have provenance:

- `U`: directly supplied user requirement or boundary
- `D`: confirmed user-owned decision
- `E`: evidence supporting a fact or feasibility claim; it cannot authorize user-visible behavior by itself
- `R`: new Codex recommendation, prominently labeled and included in the exact final approval envelope
- `B`: benchmark basis for technical reasoning, not product authorization

Technical conclusions use:

- `verified`: the relevant behavior was actually tested with named evidence and method
- `candidate`: evidence supports trying the route, but implementation or integration proof remains
- `unknown`: evidence is insufficient and the limitation remains explicit

Package listings, installed runtimes, documentation, or one successful component check do not prove an integrated product path. Keep a candidate label until the promised integration is exercised.

## Reply Ergonomics

Q/D IDs remain stable internal references and optional shortcuts. Always allow a normal sentence or paragraph. For a packet, say plainly:

```text
你可以直接用一段话回答，不必填写编号。
全部接受时回复“全部按推荐”；只修改某项时直接说明修改内容。
```

Map the user's natural language back to the internal IDs and restate the operative meaning. Do not force `Q1=... D1=...` syntax. A later packet is acceptable when it has a real dependency or new evidence; the validators do not count turns.

When a preflight-complete packet contains the traced core plus the only remaining prominent recommendations, it is the READY envelope, not a direction-only prelude. A natural reply that resolves those recommendations and explicitly starts the resulting scope must not be followed by another unchanged approval card.

## Temporary Evidence

Read-only evidence work may create disposable renderings, extracted text, screenshots, or logs only when inspection needs them. Write these to an isolated system temporary directory, not the project or original evidence folder. Record the source, method, output location, and limitation. Never describe a low-text page as scanned, corrupt, or OCR-dependent without the visual or structural evidence needed for that conclusion.

Temporary analysis artifacts are not project development, but they remain writes. Do not hide them, persist sensitive content longer than needed, or treat them as authorization to create project files.
