# 项目类型检查线索

Use this reference only after the route is known and current evidence has been inspected. It is a conditional checklist, not a catalog of fixed first questions, recommended product scopes, or small-version defaults.

For every project type:

1. extract facts from the user's description, files, code, screenshots, logs, and existing workflow
2. identify only the missing decision that changes output, data meaning, delivery, safety, or acceptance
3. combine related unresolved decisions into one card
4. do not turn the examples below into features, fields, or scope without `U` or `D` provenance

## Excel Or Table Automation

Inspect sample formats, field differences, status meanings, formulas, merged cells, data ownership, expected output, and whether originals must remain unchanged.

Ask only when evidence cannot determine a material choice such as:

- one format versus multiple incompatible formats
- business mapping for ambiguous fields or statuses
- overwrite versus separate output
- handling of unmatched or invalid rows

Acceptance should use representative real copies and confirm output meaning, original-file protection, and visible exception handling. Do not default to one file, one department, cleaning, deduplication, or export fields merely to make the project smaller.

## File Batch Processing

Inspect naming rules, collisions, directory depth, file types, volume, encoding, and rollback. Destructive operations require an explicit action boundary. Prefer a preview/dry run when it reduces irreversible risk, but do not invent a change log or output structure if the requested workflow does not need one.

## Internal Query Or Search

Inspect the actual corpus, access boundary, update frequency, required traceability, and whether the user wants lookup, filtering, or answer generation. Keyword search, classification, and natural-language answers are different product behaviors; expose a choice only when the user has not already defined the intended workflow.

Every displayed fact or answer must retain a source pointer appropriate to the project. Do not index folders, copy documents, or add AI answers without scope and data authority.

## Public Information Monitoring

Read `references/公开信息监测项目.md` and `references/外部内容安全.md`. This generic checklist does not select subjects, sources, fields, automation frequency, summaries, export, framework, or delivery. Validate real source relevance and access limits before promising automated retrieval.

## App Or Repeated-Use Tool

Inspect the operator's actual workflow, frequency, target computer, input/output, failure recovery, and distribution constraints. UI, desktop, web, local HTML, and script are delivery alternatives rather than project levels.

Ask about delivery only when operating constraints leave more than one materially different viable choice. Do not default to one main screen, import/export, command line, responsiveness, or packaging.

## Test Data, Logs, Or Technical Archive

Inspect existing naming, timestamps, project/device identifiers, retention, data volume, sensitive fields, and current directory conventions. Ask only for business meaning that cannot be inferred, such as the authoritative timestamp or retention owner. Preserve originals unless explicit authority says otherwise, and prove that the index points to the right source files.

## Knowledge Directory

Inspect current folders, document owners, update process, source links, duplicates, permissions, and how people expect to retrieve information. A directory, tags, full-text search, summaries, and question answering are separate capabilities. Do not choose among them from the word “knowledge base.”

## Shared Or Multi-Department Workflow

Inspect source ownership, identifiers, update authority, conflict rules, review/approval flow, server availability, backup, and handoff. Do not reduce the project to one department unless the user approves that validation strategy. A server proves technical availability, not that a shared web system is desired.

When the shared route is selected, reconcile these independently: participant roles, who may update which state, conflict/history behavior, authoritative source and audit trail, sensitive-data boundary, operating availability/owner, and acceptance. Batch all currently unresolved items; do not substitute platform selection for the business rules.

## Follow-Up Or Status Tracking

Inspect the events, states, owner transitions, aging rules, closure meaning, and source of truth. Do not invent “open/closed,” owner fields, reminders, or dashboards when existing records use different business rules. Acceptance must show that the agreed items can be found and their state remains traceable to source evidence.

## Anti-Patterns

- a copied first-question template chosen only from the project type
- a type-based scope default that silently becomes product behavior
- “start with one file/one department/one screen” without evidence or approval
- fixed option sets that omit the user's already stated workflow
- common convenience features admitted because they are easy to implement
- a technical feasibility fact used as delivery or product authorization
