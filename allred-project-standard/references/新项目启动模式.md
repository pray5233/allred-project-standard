# 新项目启动模式

Use after a new-project trigger or an explicit request to start a non-trivial project. Also read `references/核心执行流程.md`, `references/交互与确认规则.md`, and the conditional references named below.

## 1. Capture The Rough Requirement

If the user supplied only a trigger, ask once for a short non-technical description: intended user, problem, available input, and desired result. If the requirement is already present, restate it briefly and continue without asking for repetition.

Do not choose features, architecture, delivery, or project size from a broad label such as `管理工具`, `市场信息`, or `自动整理`.

## 2. Collect Materials And The User's Initial Idea

Use `references/资料收集与分析.md` when real files or process evidence may exist. Ask once for available materials and the user's current idea:

- sample files, screenshots, exports, logs, URLs, devices, interfaces
- current manual workflow, rules, templates, prior output
- the user's first-version idea, must-haves, and known non-goals

Inspect provided materials before factual questions. Keep `material availability` and `user initial idea` separate. `暂无资料` does not approve simulated capability, AI-invented fields, a reduced scope, or a delivery form.

## 3. Build The Project Brief Internally

Draft from user statements and inspected evidence:

```text
项目简述：
- 使用者和问题：
- 当前流程和痛点：
- 输入/证据：
- 期望输出：
- 约束与不做：
- 可观察成功标准：
- 已确认事实：
- 仍是假设：
```

If a missing choice changes the project's value, use one early product decision gate. For public-data or monitoring work, real-source validation and simulated UI are different evidence meanings; use `references/公开信息监测项目.md`.

## 4. Inspect Basis, Capability, And Delivery

Codex performs this read-only work without asking permission:

1. classify provisional complexity/current-round strategy from evidence using `references/项目级别问法.md`
2. select the closest local/official/external basis using `references/开发依据与能力复用.md`
3. inspect project and installed capabilities; use `find-skills` only for a real gap
4. inspect runtime and delivery implications using `references/运行环境与交付形态.md` when not obvious
5. identify concrete files, commands, write boundary, rollback, and verification

Ask only when evidence shows a user-owned tradeoff in behavior, delivery, cost, permission, maintenance, or acceptance.

## 5. Draft Total And Current Scope

Separate total scope from current scope only when useful:

- uncertainty or source feasibility must be proven first
- the project is cross-module, long-term, shared, or consequential
- a first round reduces meaningful risk

A bounded project with clear functions and evidence may implement all agreed functions in one round. Do not force every project into an MVP.

Keep future functions visible without letting the first round define the total product out of existence.

## 6. Use One Consolidated Gate When Needed

Show one named scope draft with `1-4` user-owned decisions. Include current goal, output, delivery, data/write boundary, acceptance, non-goals, files/commands after preflight, and rollback when consequential.

After all read-only preflight, use one combined named scope/start gate for a non-trivial new project. If the user already approved an equivalent displayed named scope and explicitly authorized start, skip the duplicate gate and proceed.

Do not use visible `grill-me` by default. Internal challenge questions may examine scope, source credibility, failure states, delivery, and acceptance; expose only blockers.

## 7. Execute And Verify

Follow the Standard or Deep lane in `references/核心执行流程.md`:

- implement coherent slices without repeated approval
- preserve original files and shared systems
- verify the core workflow, expected failures, persistence, restart behavior, packaging, and target environment as required by the confirmed delivery
- report fresh evidence and remaining gaps

Use a durable startup card, task breakdown, metrics table, or handoff only when project size, ownership, or continuation benefits from it. Do not fill every template.
