# 新项目启动模式

Use this reference after a user provides a new-project trigger or clearly asks to start a non-trivial project.

Also read:

- `references/交互与确认规则.md`
- `references/资料收集与分析.md` when files or real process evidence may exist
- `references/项目级别问法.md` when complexity or strategy matters
- `references/开发依据与能力复用.md` before non-trivial design
- `references/运行环境与交付形态.md` when delivery is not obvious

## 1. Capture The Rough Requirement

If the user supplied only a trigger, ask for a short non-technical description:

```text
请先用一两句话描述想做什么：给谁使用、要解决什么问题、已有输入是什么、希望得到什么结果。
不需要先决定技术方案。
```

If a rough requirement already exists, restate it briefly and continue. Do not ask the user to repeat information already present.

## 2. Collect Materials And The User's First Idea

Before Codex proposes features, ask once for the user's available materials and initial approach. Use `references/资料收集与分析.md`.

This gate may collect several things together:

- sample files, screenshots, exports, logs, historical outputs
- current manual workflow, rules, templates, or report style
- links, source lists, devices, interfaces, prior projects
- the user's first-version idea and known non-goals

If materials exist, inspect them before asking factual questions. If none exist, mark assumptions and choose a validation route; do not silently substitute simulated capability for the user's real goal.

`暂无资料` answers only the material question. It does not approve an AI-invented first version, sample-data substitution, preset brands, fields, features, delivery, or benchmark. If the user has not yet described an initial approach, include that gap in the next compact direction card rather than starting a serial questionnaire.

Use one neutral checkpoint instead of options that smuggle in a first-version strategy:

```text
在我整理需求前，请把目前已有的内容一次告诉我：
- 样例文件、截图、网址、旧工具或人工流程；
- 你已经考虑过的初版做法；
- 已知必须做或明确不做的内容。

没有资料也可以直接说“暂无资料”，再补一句你的初步想法；不需要先决定技术方案。
```

Do not offer `暂无资料，先做一个小版本` as the material answer. Scope strategy is decided later from uncertainty and evidence.

## 3. Define The Project Brief

Create a draft from the user's words and file-backed facts:

```text
项目简述：
- 使用者：
- 要解决的问题：
- 当前做法和痛点：
- 输入/证据：
- 期望输出：
- 约束：
- 明确不做：
- 可衡量的成功标准：
- 已确认事实：
- 仍是假设：
```

The success standard must describe observable behavior, not “looks good” or “runs successfully”.

Broad labels such as `市场信息`, `管理工具`, `自动整理`, `智能分析`, or `监测平台` are not yet a product identity. Do not expand them into a field list or feature set merely because those features are common. First distinguish the outcome categories that change sources and workflow. For example, `市场信息` may mean product/specification records, news/events, seller/price information, or an approved combination.

If the brief contains a direction-changing uncertainty, use the opening direction checkpoint in `references/交互与确认规则.md` before lengthy research or setup.

A direction answer approves only the displayed route. Before benchmark research, check whether the subject, user, evidence boundary, smallest proof, or runtime meaning is still missing. Resolve only the remaining blockers; do not infer them from the route choice.

For online search, market intelligence, or public-information monitoring, read `references/公开信息监测项目.md`. After the user chooses real-source validation, confirm the monitored subject and minimum validation definition before selecting data providers, features, framework, or delivery.

## 4. Classify Complexity And Strategy

Use `references/项目级别问法.md`.

Codex drafts the classification from workflow, data/system impact, uncertainty, integration/runtime, users/ownership, failure consequence, and maintenance. Do not ask the user to pick a vague level first.

Choose current-round strategy separately:

- complete the bounded scope
- validate a smaller slice
- plan or collect evidence first

Include classification in a compact decision card only if it changes the work.

Classification is normally an internal draft. Report its evidence and effect; do not create a separate user round merely to approve the label.

## 5. Select Development Basis / Benchmark

Use `references/开发依据与能力复用.md`.

Search after the project brief is defined:

1. local known-good project and user/company materials
2. official maintained documentation or reference implementations
3. strong external products/open source only when needed

Record comparability, reuse path, differences, and acceptance metrics. If no suitable benchmark exists, record the search gap and use an explicit hypothesis.

This is Codex-owned work unless the user already supplied a benchmark or the candidates create a real cost, permission, or product-direction tradeoff. Never ask a beginner to choose whether Codex should search for references.

## 6. Inspect Existing Capabilities

Inspect relevant project conventions, Skills, plugins, MCP servers, scripts, libraries, templates, and previous files before adding a dependency or custom mechanism.

Use `find-skills` only for a real capability gap. Follow higher-priority environment rules about external search, browser, Superpowers, installation, and tool access.

## 7. Confirm Runtime And Delivery When Needed

Use `references/运行环境与交付形态.md` when the target user environment or delivery form changes feasibility.

Do not assume employee computers have Python, Node.js, Git, terminals, admin permissions, or local servers. Do not ask about delivery if the user already specified it and it is feasible.

Delivery is part of acceptance: test the packaged executable, deployed URL, local HTML, workbook/template, script command, or document workflow that the user will actually receive.

## 8. Draft Requirements Before Asking More

Codex internally checks:

- main user flow
- input and output
- business rules and exceptions
- data/source boundaries
- safety/privacy/write boundaries
- delivery and validation
- handoff or maintenance when relevant

Then produce a draft and one compact decision card following `references/交互与确认规则.md`.

Before showing that card, apply the decision-round compression gate. Search target/input, trigger or schedule, output, evidence region, and delivery are separate dimensions, but decisions already knowable at the same time belong in the same card. Do not ask each dimension in a new turn, and do not silently reinterpret one answer as another dimension.

The full lifecycle must not become a questionnaire. Materials may justify the opening checkpoint; benchmark search, capability inspection, classification, and technical preflight proceed internally; user-owned scope, delivery, evidence, and acceptance decisions are consolidated after that work.

Use `references/项目类型问题库.md` only for a domain-specific decision that changes the next step. Do not walk through the whole question bank.

Visible `grill-me` is optional, not the default. Use it only when explicitly requested or when high-consequence ambiguity cannot be safely compressed.

## 9. Separate Total And Current Scope

Use four buckets when scope separation adds value:

| Bucket | Meaning |
| --- | --- |
| Total scope | complete product/task direction |
| Current round | work to implement and accept now |
| Future retained | valid later work, not part of this acceptance |
| Removed | explicitly not part of the project |

For a bounded small or low-risk medium project, current round may equal all confirmed functions. For uncertain or complex work, current round should be the smallest slice that proves the risky assumption or completes a useful loop.

After drafting the current scope, explicitly ask whether anything is missing or unnecessarily included. Combine this with the decision card; do not create another ceremonial question.

## 10. Plan Evidence And Work

Create only the records justified by the project:

- `templates/项目启动卡.md` for medium/complex/uncertain/shared work
- `templates/任务分解表.md` for dependent tasks
- `templates/关键指标表.md` when several metrics matter
- `references/证据等级说明.md` for evidence-sensitive conclusions
- `references/写入边界说明.md` for original/shared/device/system writes

Each current-round task needs an input, output, owner when relevant, and verification method. Metrics need a target and evidence source.

## 11. Preflight And Confirm

Perform read-only inspection first when planned files, commands, or no-touch boundaries are not known.

Then use the start confirmation in `references/交互与确认规则.md`. The card must make clear that implementation has not started and list concrete planned mutations.

Do not introduce new product requirements in this card. If the card is the first place the user sees preset topics, automatic refresh, favorites, filters, AI summaries, responsive targets, export, or another product behavior, move them back to a decision card or future scope.

A direct user instruction to implement a previously displayed exact scope counts as confirmation. Broad approval does not authorize unrelated installs, Git operations, external publication, deployment, or device/system writes.

## 12. Execute, Verify, Review

After confirmation:

1. implement the smallest coherent step
2. verify it against the agreed acceptance and benchmark
3. report progress and changed assumptions
4. continue inside scope without repeated approvals
5. stop when a new user-owned decision or unsafe boundary appears
6. close with `templates/本轮验收卡.md` or `references/本轮验收与复盘.md` when useful

Do not claim completion from code generation, build success, packaging, or simulated output alone.
