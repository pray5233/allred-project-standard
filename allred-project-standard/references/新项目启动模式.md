# 新项目启动模式

If the user supplies only the trigger (`allred新项目`, `新项目`, or the beginner equivalent), ask only: `请先用一两句话说明你想解决什么问题、给谁使用、希望得到什么结果。` Do not display the baseline packet yet.

Use after a new-project trigger or an explicit request to start a non-trivial project. `references/核心执行流程.md` is already the shared owner; do not reread it here. Load only the conditional references that the current evidence requires.

## 1. Capture The Rough Requirement

If the user supplied only a trigger, ask once for a short non-technical description: intended user, problem, available input, and desired result. If the requirement is already present, restate it briefly and continue without asking for repetition. When the request visibly spans multiple subsystems or could mean either a bounded proof or a complete operational system, say so before the first packet and include that outcome choice in the packet; do not silently enter the most comprehensive route. Name the actual drivers and what they change in evidence, decision order, delivery, or acceptance; `可能成为大系统` alone is not a useful complexity explanation.

Do not choose features, architecture, delivery, or project size from a broad label such as `管理工具`, `市场信息`, or `自动整理`.

## 2. Collect Materials And The User's Initial Idea

Use `references/资料收集与分析.md` when real files or process evidence may exist. Ask for available materials and the user's current idea in the same concentrated packet as all other currently independent baseline unknowns, not as the first item in a serial questionnaire:

- sample files, screenshots, exports, logs, URLs, devices, interfaces
- current manual workflow, rules, templates, prior output
- the user's first-version idea, must-haves, and known non-goals

Inspect provided materials before factual questions. Keep `material availability` and `user initial idea` separate. `暂无资料` does not approve simulated capability, AI-invented fields, a reduced scope, or a delivery form.

Q1-Q4 are a sufficiency model, not a completion checklist. After material inspection, do not re-ask user/workflow, non-goals, or acceptance merely because a slot is blank when the user's stated behavior and evidence already support one bounded, reversible, testable scope recommendation. Show that recommendation with its assumptions and exclusions, let the user correct or approve it, and ask only an exact missing fact that changes the recommended product behavior or proof.

When promised samples are missing, request their location in the same compact packet as any unanswered workflow, first-version boundary, and useful-result facts. Ask only for the location/sample for one exact read-only inspection or when those facts are known. After the read, do not restart Q1-Q4: continue preflight and use one combined scope/start gate. Every sample-exposed output rule remains a named recommendation or visible unknown, never a silent default.

## Recommendation Readiness Gate

Before presenting a complete first-version package or recommending a product path, establish all four items:

1. rough outcome and intended user or use situation
2. material state: available and inspected, unavailable, or deliberately deferred
3. the user's initial idea, must-have behavior, or explicit request for Codex to draft alternatives from scratch
4. at least one observable result the user would recognize as useful or acceptable

The initial message may already answer some or all items. Do not ask for repetition. `I do not know; propose options` is a valid user-owned direction, but the resulting proposal remains `R` until approved.

Maintain an intake ledger across turns. Update only answered items and carry the rest forward. A request for Codex to recommend closes item 3 only; it does not supply items 1, 2, or 4. Never infer item 4 from a product label or model preference.

If the gate is incomplete, stay in INTAKE/EVIDENCE. Ask missing independent items once and state what each group changes; intake is not a decision card. Pending materials block evidence-dependent recommendations, not independent readiness facts. Do not announce development, present a complete package, or request start authorization.

Before readiness passes, ask only factual/open `Q` items about materials, current use, the user's initial idea, must-haves, and recognizable useful result. Do not offer model-created product `D` alternatives such as prototype versus complete system, desktop versus web, online versus local processing, or feature packages. The user may volunteer any of those decisions; record them without reopening them.

Passing this gate authorizes recommendation work only. It does not authorize the recommended behavior or development.

When all four items are already present and the user explicitly asks to compare or decide a parent route, enter DECISION and answer that request now. Do not postpone it behind non-blocking facts that can be gathered later; missing facts may defer a recommendation, not the requested neutral comparison.

## Discovery Coverage Before READY

Recommendation readiness proves that Codex has enough basis to investigate and recommend. It does not prove that the project has been explored deeply enough to stop asking. After material analysis and before the final READY envelope, run the internal discovery-coverage review from `references/动态项目契约.md`.

Review the current task through six broad lenses: workflow, information/relationships, lifecycle/exceptions, operating scale/frequency, delivery/effects, and acceptance. These are internal review lenses, not six mandatory questions. Derive task-specific facets from the user's words, inspected materials, contradictions, evidence limitations, and plausible counterexamples.

For every relevant facet, record one current state: user-confirmed, evidence-resolved, user-deferred with consequence and revisit condition, evidence-backed not applicable, or open/investigating. A facet that was discovered earlier cannot disappear merely because it was not converted into a `D`. An open or investigating facet blocks READY when it can change the promised behavior, working set, data relationship, exception handling, delivery, significant effect, or acceptance claim.

Ask another concentrated round whenever the review exposes currently answerable user-owned gaps. Batch independent gaps; preserve real dependencies; allow as many rounds as the dependency depth requires. Do not ask evidence-resolvable facts, repeat settled facets, or create questions merely to fill a lens. A simple, fully evidenced task may close all lenses internally and proceed without another question.

## 3. Build The Dynamic Project Contract Internally

When product behavior, evidence meaning, delivery, or acceptance is not stable, read `references/动态项目契约.md`. Otherwise draft the brief directly from the complete user statement and inspected evidence without loading another workflow reference. Use only relevant slots:

```text
项目简述：
- 使用者和问题：
- 当前流程和痛点：
- 输入/证据：
- 期望输出：
- 约束与不做：
- 可观察成功标准：
- 已确认事实：
- 仍是假设：
```

Generate assumptions and confidence internally. Safe read-only inspection may proceed under clearly provisional assumptions. Use an early product decision gate only when one unresolved user-owned choice is genuinely required to make the inspection meaningful, safe, or proportionate; do not ask merely to select architecture before evidence. When external/public information is an actual input or product behavior, load the `external-source` overlay; real-source validation and simulated UI remain different evidence meanings.

Do not ask fixed lifecycle questions. For example, a working-set boundary matters only when changing that set changes behavior or evidence; an `App` label does not approve web, desktop, mobile, or local HTML.

## 4. Inspect Basis, Capability, And Delivery

Codex performs this read-only work without asking permission:

1. classify provisional complexity/current-round strategy from evidence using `references/项目级别问法.md`
2. select the closest local/official/external basis using `references/开发依据与能力复用.md`
3. inspect project and installed capabilities; use `find-skills` only for a real gap
4. inspect runtime and delivery implications using `references/运行环境与交付形态.md` when not obvious; if delivery experience is a material user-owned ambiguity, include actual alternatives in the compact alignment card before selecting architecture. Do not ask the user to choose Electron, Tauri, Python, a framework, or another technical path when the user-facing consequences are already settled
5. identify concrete files, commands, write boundary, rollback, and verification

Ask only when evidence shows a user-owned tradeoff in behavior, delivery, cost, permission, maintenance, or acceptance.

Do not ask whether to enable a visual companion, planning helper, or another process aid before a current decision needs it. Use safe internal aids directly when they do not change user-visible behavior or require consequential authorization; otherwise surface only the concrete consequence, not the tool preference.

## 5. Draft Total And Current Scope

Separate total scope from current scope only when useful:

- uncertainty or source feasibility must be proven first
- the project is cross-module, long-term, shared, or consequential
- a first round reduces meaningful risk

A bounded project with clear functions and evidence may implement all agreed functions in one round. Do not force every project into an MVP.

Keep future functions visible without letting the first round define the total product out of existence.

## 6. Use Concentrated Interaction Without Duplicate Gates

Show a readable user-facing scope with unresolved user-owned decisions or clearly labeled recommendations. Batch every currently knowable independent item; split only when a later decision depends on an earlier answer. State exactly which recommendations are accepted and whether the same reply starts work. Include current goal, visible behavior, delivery meaning, user-relevant data handling, important limitations, non-goals, acceptance, and significant effects after preflight.

If preflight is complete and only visible recommendations remain, make this packet the complete READY scope/start envelope. Do not first ask the user to select recommendations and then repeat the unchanged scope in another start card. A natural reply that accepts or rejects the named recommendations, preserves the traced core, and explicitly says to start is exact authorization for that resulting envelope.

Load the `decision` route stage before showing this packet. Each decision ID owns one material axis; do not combine delivery, data transmission, translation/processing granularity, feature scope, update behavior, or acceptance into one option merely to shorten the conversation.

When the first version contains preselected visible items, name them and their inclusion basis in the user-facing confirmation. Do not replace concrete scope with a count such as `两项` or `若干默认内容`.

Run the recommendation admission filter first. Do not propose export, filters, scheduling, persistence, accounts, or other standard-looking features unless the user requested them, evidence proves they are required, or they are necessary for safe/testable operation.

Keep the user's literal behavior granularity. Do not expand `筛选` into combined filters, clear-filter controls, persistence, or settings behavior; do not expand `来源追溯` into file positions or metadata fields. Extra observable behavior is a separate prominent `R`, even when it looks like an implementation detail.

After scope is stable, enter READY and show one complete named scope/start gate when no separate consequence requires its own authorization. Use the exact start semantics from `references/交互与确认规则.md`. If the user already approved an equivalent displayed READY scope whose option explicitly authorized start, skip the duplicate gate and proceed.

Render an unconfirmed Codex-selected root as `建议项目根目录（待你确认）`; bare `项目根目录` fails READY. Approve the recommendation in the same final option.

Run consistency lint first. Reconcile every earlier decision: a missing reply, partial reply, or approval of another item leaves that decision unresolved. Never infer it from evidence or model preference. A final gate must not present new behavior or delivery as approved; it may add a labeled `R` only if that envelope approves it. If correction changes the path, show one full replacement scope. Sample submission or later preflight never upgrades an earlier direction approval into start authorization.

Before mutation, prepare exact technical details in the Codex execution record. Do not require the user to approve files, SDKs, commands, caches, or test mechanics. Surface only the effects that change user scope, data, permissions, cost, external systems, or safety.

Do not use visible `grill-me` by default. Internal challenge questions may examine scope, source credibility, failure states, delivery, and acceptance; expose only blockers.

## 7. Execute And Verify

Follow the Standard or Deep lane in `references/核心执行流程.md`:

- implement coherent slices without repeated approval
- preserve original files and shared systems
- verify the core workflow, expected failures, persistence, restart behavior, packaging, and target environment as required by the confirmed delivery
- report fresh evidence and remaining gaps

Use a durable startup card, task breakdown, metrics table, or handoff only when project size, ownership, or continuation benefits from it. Do not fill every template.
