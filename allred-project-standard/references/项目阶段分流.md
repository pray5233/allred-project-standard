# 项目阶段分流

Use for existing projects or mixed requests. Shared workflow and confirmation rules come from `references/核心执行流程.md` and `references/交互与确认规则.md`.

## Route From Evidence

| Evidence/signal | Route | Read |
| --- | --- | --- |
| error, crash, wrong result, failed test | 功能调试 | `references/功能调试.md` |
| new capability outside the current promise | 新增功能 | `references/新增功能.md` |
| function works but layout/flow/usability is weak | 界面优化 | `references/界面优化.md` |
| completion, delivery, review, next-round decision | 验收/复盘 | `references/本轮验收与复盘.md` |
| multi-round evidence/conclusion work | 长期任务 | `references/长期任务模式.md` |
| unclear product with no established scope | 新项目 | `references/新项目启动模式.md` |

Do not ask the user to choose a route when the request and project evidence make it clear. If mixed:

1. fix a current-scope Bug before adding dependent features
2. preserve requested future features in the roadmap
3. separate UI polish from behavior correctness
4. run acceptance only against the approved current scope

Ask one routing decision only when valid orders imply materially different outcomes or cost.

## Beginner Overlay

Beginner mode changes language and defaults, not the routed engineering process. Exiting beginner mode continues the same project and stage.

## Method Reuse

Reuse lightweight method principles internally without invoking a heavy framework unless explicitly requested:

| Route | Keep | Do not import |
| --- | --- | --- |
| Debugging | reproduce, evidence, root cause, one hypothesis, minimal fix, fresh verification | mandatory TDD or speculative patch chains |
| Feature | acceptance and regression impact before implementation | mandatory brainstorming/spec approval |
| UI | rendered current state, target flow, focused changes, screenshots | full redesign without evidence |
| Acceptance | exact promise-to-evidence reconciliation | forced Git/branch options |
| Long-term | review depth, evidence state, current objective, handoff | restart the whole project each round |
