# 项目阶段分流

Use this reference when the user says `继续项目` or when the request may belong to an ongoing project rather than a new project.

The goal is to route the request to the right mode before asking detailed questions or editing files.

If beginner mode is active, keep this routing. Beginner mode changes how questions are asked; it does not change the project stage.

When beginner mode is active:

- 功能调试: ask for the visible problem, operation path, screenshots, sample input, actual output, and expected output in plain language
- 新增功能: ask whether the idea belongs to the current round or later, using simple choices
- 界面优化: ask which step is confusing or hard to use, not which component or layout system to change
- 本轮验收/复盘: classify feedback as "没达到承诺 / 能用但不顺手 / 想加新功能 / 不要了"
- 长期任务推进: first do lightweight review, then confirm the current-round objective, evidence, result form, and validation

If the user says `退出新手模式`, `切换标准模式`, `不用新手模式`, `按标准流程`, `按标准模式`, `我已经熟悉了`, or `用专业模式`, exit beginner mode and continue the same routed stage under the standard workflow.

## Stage Options

```text
当前项目处于哪个阶段？
1. 功能调试（推荐）：已有功能出错、结果不对、按钮没反应，先复现和找根因。
2. 新增功能：已有项目上增加能力，先判断是否进入本轮范围。
3. 界面优化：功能基本可用，主要改善页面、操作流程或视觉体验。
4. 本轮验收/复盘：检查本轮是否完成，并决定下一步。
5. 长期任务推进：已有长期项目或分阶段任务，需要先回顾再确定本轮目标。
6. 新项目启动：还没有明确范围，需要重新启动项目流程。

请回复数字，也可以直接写自定义阶段。
```

## Routing Rules

| User signal | Route to | First reference |
| --- | --- | --- |
| 报错、崩溃、结果不对、按钮没反应、测试失败 | 功能调试 | `功能调试.md` |
| 再加一个、能不能支持、增加字段、增加导出 | 新增功能 | `新增功能.md` |
| 页面不好看、布局乱、按钮不明显、移动端错位 | 界面优化 | `界面优化.md` |
| 做完了、验收一下、下一步、交付、复盘 | 本轮验收/复盘 | `本轮验收与复盘.md` |
| allred长期任务、继续长期任务、长期任务复盘、长期任务调试、长期任务资料分析、长期任务验证 | 长期任务推进 | `长期任务模式.md` |
| 只有想法、还没项目、重新开始 | 新项目启动 | main Required Workflow |

If one user message contains multiple stage signals, classify first:

```text
你这条反馈里包含多个类型，我先拆开：
1. 先处理 Bug/功能调试（推荐）：保证本轮承诺功能稳定。
2. 先做界面优化：适合功能已稳定但不好用。
3. 先规划新增功能：适合本轮已经验收通过。

请回复数字，也可以直接写自定义优先级。
```

Default order:

1. Bug or failed acceptance item
2. Safety or data-loss risk
3. Usability optimization inside current scope
4. New feature
5. Roadmap planning
6. Long-term review or handoff when the task depends on accumulated evidence

## Benchmark Reuse

For each routed stage, record the benchmark or reused Skill:

| Stage | Benchmark | Reuse | Do not copy |
| --- | --- | --- | --- |
| 功能调试 | `systematic-debugging` | reproduce, root cause, one hypothesis, minimal fix | rigid external tooling or Superpowers invocation unless requested |
| 新增功能 | `test-driven-development`, `prd-generator` | acceptance criteria, testable requirement, scope boundary | large PRD or strict TDD when the project is a low-risk office tool and user did not ask |
| 界面优化 | `frontend-testing-debugging`, `redesign-existing-projects` | target flow, rendered evidence, focused diagnosis | redesign-from-scratch or style rules that conflict with local app |
| 验收收尾 | `finishing-a-development-branch`, local acceptance card | verify first, then numbered next-step options | git merge/PR actions unless user asks |
| 长期任务推进 | local `长期任务模式.md` and `长期任务回顾卡.md` | review gate, evidence separation, current-round objective, handoff discipline | treating assumptions as conclusions or restarting the whole project each round |

## Shared Output

For an ongoing project, start with:

```text
项目阶段：
当前请求分类：
对标/复用方法：
当前承诺范围：
本次处理范围：
暂不处理：
需要的证据：
验证方式：
建议下一步：
```

Then wait for confirmation when the action changes scope, touches shared files, or affects delivery.
