# 本轮验收与复盘

Use to assess an approved current scope. Do not treat a request for acceptance as proof that the result is usable.

## Promised-Item Ledger

Reconstruct the exact approved behavior from user statements, inspected requirements, approved drafts, and authorized changes. Keep each independently promised item separate; never replace exact rows with a broader label.

Show the ledger in the acceptance response before stating the conclusion. If the approved scope or one promised branch cannot be recovered, mark acceptance incomplete and name the missing record; generic `tests passed` or `build passed` cannot replace it.

For every item record:

| Promised item | Evidence required | Fresh evidence | Result |
| --- | --- | --- | --- |
| exact behavior/state | command, artifact, rendered flow, target environment, or user observation | observed output/path | passed / failed / unverified |

## Exact Evidence Reconciliation

- Run the relevant verification now.
- Tool/test evidence supports only the branch and environment it exercised.
- Static analysis is not live validation.
- Packaging success is not target-machine usability.
- A user screenshot or report is evidence only for what it visibly shows.
- Missing planned branches remain under `仍未验证`.

Classify the result at the strongest supported level:

- `代码与自动化验收通过`
- `目标环境验证通过`
- `有条件通过`
- `未通过`

Reserve unconditional closure for evidence covering every promised item and required manual/target-environment check.

## Feedback Classification

- promised behavior failed: Bug
- works but is awkward: UI/experience optimization
- new capability requested: new feature/roadmap
- no longer wanted: explicit scope removal

Do not turn all feedback into new current-scope work automatically.

## Output

```text
验收结论：
已验证：
仍未验证：
失败/差距：

```

Default to reporting the acceptance result and stop. Ask for next-round priority only when the user explicitly asks to continue planning or when the current request includes a next-step decision. Git merge, push, PR, release, cleanup, or discard actions require explicit request; acceptance does not imply them.
