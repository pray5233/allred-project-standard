# 本轮验收与复盘

Use this reference when the current development scope has been delivered, tested, or the user asks how to continue.

The goal is to close the current scope before expanding the project.

## Acceptance Rule

Do not say the current scope is complete only because code runs, files are generated, or packaging succeeds.

Use the acceptance card:

- whether it runs
- whether original files are protected
- whether sample input passes
- whether output matches expectation
- whether invalid data has a clear response
- whether usage instructions exist
- whether the user confirms it is usable

## Exact Evidence Reconciliation

Reconcile every promised behavior against the exact completed evidence before claiming success. Use two explicit lists:

```text
已验证：
- 行为/分支：对应的测试、工具事件、文件或人工证据

仍未验证：
- 行为/分支：缺少什么证据，以及是否阻塞本轮验收
```

- Claim only the branches named by completed evidence. `状态测试通过` does not prove every possible status, and a successful output file does not prove every exception path.
- If a planned branch is absent from the test or tool result, list it under `仍未验证`; do not infer it from nearby cases.
- Keep automated evidence, clean-machine evidence, visual/manual checks, and real-user usability confirmation distinct.
- A user message such as `本轮验收` requests a review; it is not proof that the result is usable.
- Do not say `没有遗留缺口`, `全部通过`, or `本轮完成` while any promised behavior, usage instruction, target environment, or user acceptance remains unverified, unless the user explicitly accepts the listed condition.

Before writing the acceptance response, build a promised-item ledger from the approved scope draft and start-confirmation card. Check every field rule, formula, status value, ordering rule, failure branch, usage instruction, delivery behavior, environment claim, and no-touch boundary. For each item, record one of:

- `verified`: cite the exact completed evidence that names the behavior
- `unverified`: state the missing evidence and whether it blocks technical, product, or user acceptance
- `out of scope`: only when it was never promised in the approved round

Create at least one ledger row for every numbered item or bullet in the approved scope, and split a bullet when it contains several independently testable claims. Preserve the exact promised wording. For example, `未匹配订单保留` does not cover `shipped_qty=0`, `remaining_qty=ordered_qty`, `latest_ship_date 留空`, and a specific status value; each needs its own evidence or `unverified` row. Never use a broader ledger label than the approved rule.

Do not collapse the ledger into broad labels such as `合并规则通过`, `导出测试通过`, or `状态测试通过` when the approved scope contains more specific behaviors. A test event that names `required columns` does not prove column order; `partial/full status` does not prove every other status value; a build does not prove UI operation or that a real user can use the result.

Every acceptance response, including a narrow existing-project feature, must preserve the `已验证 / 仍未验证` distinction. Use `代码与自动化验收通过`, `目标环境验证通过`, or `有条件通过` when that is the highest supported level. Reserve an unconditional `本轮验收通过并关闭` for evidence covering all promised acceptance items, including any required manual/user confirmation.

## Feedback Classification

Classify each item before acting:

| Type | Meaning | Default Treatment |
| --- | --- | --- |
| Bug | Current scope promised it, but it does not work | fix before new feature work |
| Optimization | Works, but is hard to use or fragile | batch into a small polish pass |
| New feature | Not promised in the current scope | put into the next-round roadmap |
| Remove | User no longer wants it | remove from total scope after confirmation |

Do not treat every new request as a bug.

Do not treat every inconvenience as a new feature.

## Low-Interruption Rule

Acceptance and review should summarize first and ask one priority decision.

- do not ask separate questions for every bug, optimization, and new feature
- classify feedback into Bug / Optimization / New feature / Remove, then recommend the next priority
- put minor open items under `待确认但不阻塞`
- ask only whether to follow the recommended next step or change priority
- do not start next-round planning until the user approves the direction

## Review Question

After summarizing acceptance results, ask:

```text
本轮复盘后，下一步怎么处理？
1. 先修复本轮 Bug（推荐）：先让已承诺功能稳定可用。
2. 做少量体验优化：本轮功能可用，但需要更顺手。
3. 规划下一轮功能：本轮已闭合，开始处理后续路线图。
4. 暂停开发，整理交接材料。

请回复数字，也可以直接写自定义安排。
```

## Next-Round Planning

Only start next-round planning when:

- current-scope acceptance is passed or explicitly accepted with conditions
- remaining bugs are listed
- new features are separated from bugs
- user confirms the next priority

When planning the next round, update:

- total function map
- future roadmap
- key metrics
- validation method
- write boundaries if new files, systems, devices, or shared trackers are involved

## Handoff Option

If the user pauses development after the current scope, produce a short handoff:

- current version
- what works
- what does not work
- known issues
- evidence path
- how to run
- how to validate
- next recommended task
