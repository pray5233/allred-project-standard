# Internal Record Construction

This is an internal authoring aid, not another interview or authorization gate.
Ordinary discovery uses the cumulative record below; load the schema details
only when an existing state needs updating or the final start envelope is ready.

## Cumulative Discovery Record

Keep one evolving record of the user's requirements and initial idea, exact
source excerpts for material choices, observed evidence and limitations,
confirmed decisions or delegation, recommendations, pending facets, and the
current versus total scope when they differ. These are information categories,
not required questions, files or template sections.

After a material answer or observation, retain its meaning and unresolved parts.
A partial answer closes only its answered part; a combined answer need not become
independent user decisions. Keep changed or rejected choices and their reasons.

Keep each unsettled meaning as narrow as its source. An undecided format or
proof method does not reopen an established deliverable or goal. Distinguish
what the user explicitly cannot answer from what has not been investigated;
a statement about one fact supplies no answer about a related fact. Attribute
Codex recommendations and interpretations to Codex, not to the user, and do not
turn possible future topics into required decisions.

Apply delegation at the level actually granted. Permission to choose a design
detail can coexist with a prohibition on building the product; preserve both
without asking again for the delegated choice.

Use conversation for simple discovery. When choices, unaccepted alternatives and
partial answers coexist, keep a small Markdown note in the authorized task/evidence
location or a session-unique temporary directory before project write approval.
Persist before handoff or likely interruption. No JSON, IDs or validation command
is required.

When updating a persisted note:

1. Read its current content and the new source. Patch affected meanings in place;
   keep each current requirement or open question in one location. Preserve the
   source quotation or inspected-file reference for a material claim, including
   later user corrections; the initial file is not the source of later answers.
2. Keep replaced choices only as clearly superseded history. The current note
   itself is the handoff: a request to summarize or hand off updates that content,
   not a second "current state" or "next-time recap" inside the file. Put a short
   recap in the user reply, with a link to the current note when useful.
3. Read back the changed entries and any retained recap against source words.
   Preserve qualifiers, certainty and time boundaries in the note and every
   reply. Dates need a supplied source or clock observation, not a folder name;
   omit unnecessary dates. Resolve contradictions and duplicate current entries
   internally before handoff. Explain only a real uncertainty or consequence.

A stale note never overrides the conversation. Preserve unaccepted alternatives
as proposals, without manufacturing extra user-owned blockers.
No new trigger, memory Skill invocation or write for an unchanged question is required.

At READY, project the accumulated information into the existing schema once.
Compare it back to the source notes before calling validators. If a state already
exists, update only affected entries using the same updater; the conversational
notes remain the interpretation basis, not a second independently edited ledger.
Record-format repair never settles a substantive unknown or authorizes work.

## Structured State At Handoff

Use the existing state schema; never copy the fictional passing test fixture.
Use `scripts/update_project_state.ps1` for pre-approval updates; it loads
`templates/project-state.draft.json` internally. Supply only supported changes,
not a repeated full state. Keep the cumulative state in a session-specific
temporary directory. The draft
is deliberately incomplete for aggregate diagnostics and READY/EXECUTION. No business choice,
inspection, coverage review, or approval is supplied by the template.
The updater creates session-unique state/baseline IDs. Select the actual route;
it does not choose software over document work.

## Incremental Patch Input

The patch is an internal JSON object, never a form for the user. New states and
later replies use the same input. Omitted fields/rows stay unchanged; an empty
upsert array does not erase a ledger. Rows merge by their stable ID. A supplied
array within a row replaces only that array; use explicit lifecycle states to
retain rejected/deferred/superseded work, not deletion.

For decisions, `id` and its established `axis` identify the same question across
updates. Keep `axis` unchanged, including when improving wording; optional
`label` holds a clearer displayed title. A different question gets a new ID.
Adding a question or answering one facet never replaces another open decision.
Use the same stable-ID discipline for tracked factual Q rows. Give a new Q an
`axis` for its factual meaning and use `label` for wording. An existing Q without
an axis remains compatible. Keep `remaining_facets` only for genuinely unanswered
parts of an open/investigating item; a confirmed, unknown or not-applicable item
cannot simultaneously contain unanswered parts. Separate independent facts
before closing one. When removing a recorded facet from Q or D, add one
`facet_resolutions` entry for that facet in the same item patch:

```json
{"facet":"exact previous facet key","status":"answered","source":"U5","quote":"exact relevant words from U5"}
```

`unknown` and `not-applicable` also need a source. U sources require an exact
quote; E sources require `reason`, and a confirmed parent D can justify only
`not-applicable`. To move a still-unanswered facet, use
`{"facet":"exact previous facet key","status":"transferred","target":"D6"}`
and retain that key in the pending target's `remaining_facets`. Keep unanswered
parts open rather than clearing them to pass. Unchanged facets need no receipt;
one clear answer may support several receipts without asking again. Check what
each quote actually establishes; a related sentence is not a complete answer.
Do not leave `remaining_facets` on a `confirmed` D. Resolve its answered facets
in the same patch using the existing answer; keep partially answered D items
open. An old inconsistent snapshot can be repaired through the updater without
rewriting history or asking the user to repeat information already supplied.
These are internal patch fields, not another questionnaire or command round.
The updater and parent guard check recorded continuity and literal source text,
not omitted facts or semantic truth. Existing unversioned history retains its
old checks; new updater transitions carry `authoring.facet_accounting_version: 1`.
When the user genuinely replaces a question, retain the old axis, mark it
`superseded`, and record `resolution_source: U-id`, `reason`, and
`superseded_by: [new-D-id]`. This records an existing answer, not another approval
request. Deferral/rejection also needs the exact U source and reason;
`not-applicable` may instead cite relevant E evidence or a confirmed parent D.
Keep a decision-backed blocker linked and pending while that decision remains
unresolved; add a new blocker for a new issue rather than repurposing the old one.
The updater resolves an explicitly typed `kind: decision` blocker only when all
its source links identify confirmed decisions with literal user authority and
no recorded remaining facets. It marks this derived closure with
`resolution_mode: confirmed-decisions` and reopens it if a prerequisite reopens.
Mixed evidence links, missing links, conflicts and manual lifecycle resolutions
are not automatically closed. Keep evidence work or unanswered facets separate;
this bookkeeping does not validate the meaning of an answer or authorize work.

```text
{
  "set": {"intake": {...}, "complexity": {...},
          "discovery_coverage": {...}, "preflight": {"status": "complete"},
          "execution_plan": {...}},
  "upsert": {"user_sources": [...], "evidence": [...], "decisions": [...],
             "questions": [...], "scope": [...], "technical_conclusions": [...],
             "blocking_items": [...]},
  "prepare_ready": {
    "scope_ids": ["S1", "S2"],
    "root": {"path": "product", "authority": "recommendation"},
    "read_only_inputs": ["materials/brief.md"],
    "rollback": "actual bounded checkpoint and restoration plan"
  }
}
```

This is a field shape, not filled evidence. Omit operations that are not yet
needed. `prepare_ready` proposes an envelope, not approval or stage completion.
Only set coverage/preflight complete after the actual review/checks. Use the row
shapes below for semantics; the updater does not infer missing facts or choices.

- `set` merges the listed object sections. Only `preflight.status` is authored;
  record validity, authorization and baseline bookkeeping are not editable here.
- `upsert` accepts the existing U/E/D/Q/S/T IDs. User `meaning` may be omitted
  when the exact quote already expresses it; then the quote is preserved verbatim.
- Scope rows may carry `execution: {target, proof}`. The updater derives
  `execution_plan.scope_steps`, so no second scope/Promise mapping is needed.
- `prepare_ready.scope_ids` supplies the proposed scope selection once. The
  updater derives its authorization and candidate-baseline lists and visible
  selected-scope flags. It does not hide unselected requirements to pass a gate.
- Root authority `recommendation` creates a prominent pending R marker. For an
  already user-chosen exact root use `authority: user, source: U-id`; for a
  confirmed root decision use `authority: decision, source: D-id`. A scope ID
  is never authority. The caller must show the root in the final start envelope.
- Root paths and protected input paths resolve against `WorkspaceRoot`.
  Use absolute planned file paths, or set `execution_plan.file_path_base` to
  `project-root` or `workspace` for relative `files[].path` values. An omitted
  base retains root-relative compatibility only when unambiguous. With root
  `product`, `artifact.txt` is root-relative; `product/artifact.txt` needs an
  explicit base, otherwise the updater rejects rather than duplicating `product`.
  Allowed/planned write paths are generated; originals accumulate rather than
  disappearing during an update. No product directories are created.
- A changed contract invalidates its cached record and opens coverage/preflight
  unless reviewed in that same patch. A no-op preserves settled work. Wrong
  references are reported together without saving; unresolved substantive facts
  remain drafts and are still checked by the unchanged stage gates.

```powershell
# First update, potentially a complete patch when the evidence already suffices:
& scripts/update_project_state.ps1 -PatchPath <patch> -Route <actual-route> -WorkspaceRoot <workspace> -EvidenceRoot <authorized-evidence-directory>
# Later update against the returned snapshot and hash:
& scripts/update_project_state.ps1 -PatchPath <changed-facets> -StatePath <state> -ExpectedSha256 <hash> -EvidenceRoot <authorized-evidence-directory>
# When the current scope is ready to be proposed:
& scripts/build_start_record.ps1 -StatePath <returned-state> -EvidenceRoot <authorized-evidence-directory>
& scripts/get_route_context.ps1 -Route <actual-route> -Stage ready -StatePath <builder-returned-state>
```

Outputs are new snapshots, not overwrites. Continue from the latest returned
state. Approved/delta projects retain their established editing path; this
helper cannot approve, erase history or migrate them. It adds no user keyword,
question round or preliminary approval. Direct schema-v1 editing remains
compatible when needed; preserve existing parent path/hash. The frontier gate
checks that recorded transition too. Keep its parent snapshot available; a
missing or changed parent is unverifiable, not permission to delete the link or
restart the state. The updater rejects an already broken input transition too;
recover from its last valid parent and replay the actual unanswered user input,
retaining the rejected snapshot as evidence. A legacy root without parent metadata remains readable but
does not prove prior decision continuity. Do not copy test fixtures as defaults.

## State Field Guide

Use exact excerpts, stable IDs, and actual observations. The following are row
shapes, not evidence or default answers. Empty arrays are valid when no such
items exist; do not invent decisions merely to populate them.

```text
user_sources: {id: U1, quote, meaning, authority}
  authority: requirement | explicit-exclusion | constraint | context | acceptance | delegation
intake: each {status, source: U/E ID}
  outcome/useful_result: confirmed
  materials: inspected | unavailable | deferred
  initial_idea: confirmed | delegated
complexity: {assessment: simple|non-simple|unknown, drivers: [], communicated: bool, user_impact}
evidence: {id: E1, claim, claim_type: observed|reported|inferred|hypothesis,
  confidence: verified|supported|provisional|unknown, method, supports: [], limitations}
decisions: {id: D1, axis, status, choice, authority, depends_on: [], exposed: bool,
  trigger, approval_source, recommendation: null}
  axis: stable internal identity; optional label: current human-readable wording
  retirement: resolution_source, reason; superseded also requires superseded_by: [D IDs]
  status: open | waiting | investigating | proposed | confirmed | deferred | rejected | conflict | superseded | not-applicable
  authority: required | explicit-exclusion | constraint | acceptance | recommendation-approval
  dependency: {id: D-parent, choices: [exact-parent-choice]}
  trigger: baseline | user:U1 | evidence:E1 | decision:D1=choice
  recommendation: {option, basis: [U/E/D IDs]}
  waiting/investigating/conflict: include reason; proposed: include scope_ids
  confirmed: approval_source must name the exact U/C approval; never infer it
  the updater's newly authored confirmations pair choices with literal U quotes;
  review them with Frontier Round, not the model-authored meaning field.
  A printout or valid source ID does not certify interpretation or authorize work.
decision-backed blocking_items: {id: B1, kind: decision, status: open|resolved,
  statement, source_ids: [D IDs], blocks: [READY, EXECUTION]}
  retain every unresolved decision link; the reader also checks legacy basis/source
  links and missing kind, so field normalization cannot erase a pending meaning
scope: {id: S1, statement, category, relation, provenance: [], visible: bool,
  approval_required: bool, recommendation_prominent: bool}
  category: behavior | delivery | data | effect | non-goal | acceptance | technical
  relation: required | excluded | recommended | acceptance | technical
  non-goal pairs with excluded; acceptance and technical pair with their names
  provenance: U/E/D/R/B IDs; E/B cannot authorize product behavior
discovery_coverage: {status, review_methods: [], evidence_ids_reviewed: [], areas: []}
  complete only after contract-slots, evidence-gaps, counterexample-sweep reviews
  area: {id, status: resolved|not-applicable|deferred|open|investigating, summary,
    basis: [U/E/D IDs], open_item_ids: [], decision_ids: [], scope_ids: [],
    reason, consequence, revisit_condition}
  area IDs: workflow, information, lifecycle, operating-scale, delivery-effects, acceptance
technical_conclusions: {id: T1, statement, status: candidate|verified|unknown,
  evidence: [E/B IDs], method, basis_source, version_or_date, comparable_because,
  deliberate_differences, limitations}
write_boundary: all project_root, allowed_write_roots, read_only_inputs, and
  planned_paths values must be absolute paths, including each planned file.
  Generate paths from the actual workspace/root using Join-Path or a path API;
  do not use relative paths or hand-escape Windows separators twice.
  project_root_status: confirmed | recommended-pending
  root provenance: exact U/D, or a prominent pending R recommendation
change_control (new project): mode=new-baseline, change=null,
  baseline={id: BASE-task-id, status: candidate, scope_ids: [exact envelope S IDs]}
  preserved_scope_ids=[], later_items=[] unless there are actual later items
authorization: {envelope_id: C1, scope_ids: [exact envelope S IDs], state: pending,
  starts_execution: true only for a start envelope, approval_source: null}
```

Use `questions` only for factual questions that need tracking, with their exact
source and unresolved facets. The existing phase reference owns its lifecycle.
Do not mark coverage complete or complexity communicated because a field exists.
Keep pending recommendations visible. Populate authorization and baseline scope
IDs from the exact proposed envelope; `pending` remains pending until the user
approves that envelope. `starts_execution: true` describes the proposed choice,
not permission already granted. Keep preflight open until technical checks are
actually sufficient. The generator does not change these fields.

## Execution Plan Input

Before READY, add `execution_plan` to the same state. Write implementation and
verification information once; the renderer reuses exact state statements,
scope provenance, decisions, evidence, changes, and rollback in the ledgers.

```json
{
  "target_environment": "actual environment to verify",
  "scope_steps": [{"scope_id": "S1", "target": "exact implementation target", "proof": "observable check and expected result"}],
  "files": [{"path": "absolute planned path", "action": "create", "purpose": "purpose", "scope_ids": ["S1"]}],
  "commands": [{"command": "exact command or None", "effect": "actual effect or None", "proof": "expected observation"}],
  "mutations": [
    {"layer": "Development-time", "target": "exact target", "effect": "planned effect", "basis": ["U1"], "rollback": "exact undo boundary"},
    {"layer": "Runtime", "target": "exact target or None", "effect": "planned effect or None", "basis": ["U1"], "rollback": "undo boundary or Not applicable"},
    {"layer": "External/system", "target": "exact target or None", "effect": "planned effect or None", "basis": ["U1"], "rollback": "undo boundary or Not applicable"}
  ],
  "effects_review": {"complete": false, "hidden_recommendations": [], "hidden_behaviors": [], "hidden_effects": [], "surfaced": "plain-language effects to include in the start envelope"}
}
```

Supply one step per scope item, including limits and recommendations, and at
least one exact file and command row (`None` is an explicit no-command plan).
`effects_review.complete` becomes true only after actually reconciling effects
against the scope. A renderer cannot judge the truth of that review.

```powershell
& scripts/build_start_record.ps1 -StatePath <temp-state>
& scripts/get_route_context.ps1 -Route <route> -Stage ready -StatePath <returned-state-path>
```

If the workspace explicitly assigns a writable internal evidence directory,
pass `-EvidenceRoot <that-directory>` to the builder. Relative command arguments
are resolved against the current directory, then checked against protected
paths. Otherwise it uses system temp. This selects an already authorized location; it grants no new write
permission. A unique child is created in either case, never an overwritten file.

If evidence and user statements already settle all consequential choices and
no decision question packet is needed, proceed directly to the actual READY
route/gate. It includes the intake-transition and decision-frontier validators;
a separate DECISION call just before it duplicates those checks and is not
needed. Missing intake, coverage, preflight, provenance or authorization still
blocks the same stage. Load DECISION when a product decision packet is needed.

The builder creates a new temporary state snapshot and Markdown record. It
never overwrites the input, runs planned commands, changes project files, fills
missing evidence, or approves anything. It supports pending `new-baseline`
packets only; existing deltas and post-approval records retain their established
editing path. It checks record formatting/coverage before marking only that
record valid. It does NOT pass READY: the unchanged aggregate gate must run on
the returned state. On subsequent replies update that state, preserving all
unaffected information. The generator's status messages stay internal.
