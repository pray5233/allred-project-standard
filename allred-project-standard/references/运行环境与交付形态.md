# 运行环境与交付形态

Use this reference when the choice between app, web, script, and file-based delivery is unclear. For confirmed company office constraints, load `company-office-delivery.md` in addition to this generic reference.

Core rule:

- Development environment is where Codex builds the tool.
- Runtime environment is where the employee actually uses the tool.
- A tool is not truly delivered until it works in the runtime environment.

Do not infer target runtime capabilities from the development machine. Inspect or record the actual target constraints before formal delivery.

Do not present a React/Vite development server, `npm run dev`, or a localhost URL as an employee-ready delivery unless the runtime and startup responsibility are explicitly accepted. It may be a development proof; label it that way and keep final delivery open.

For browser-based tools, assume any API key embedded in frontend JavaScript is visible. A public/test key may support a labeled feasibility test when provider terms allow it, but formal delivery requires an approved key strategy, backend/proxy, or keyless source. Never treat a client-exposed key as a production secret design.

## Runtime And Delivery Axes

Do not ask the vague question `使用者电脑一般能打开什么`. It mixes preference, capability, and development environment, and options such as `浏览器和 Office` versus `不能安装，只能使用浏览器和 Office` overlap.

Keep these axes separate and inspect what is already known:

- desired interaction: double-click, browser, file workflow, command line, shared URL, device console, or another explicit experience
- installation and permission: admin rights, portable preference, allowed runtimes, security policy
- network and sharing: offline, approved public access, intranet, hosted service, multi-user ownership
- validation boundary: development proof, target-like test, pilot, or formal delivery

These are candidate axes, not a fixed four-question card. Put only currently unresolved high-impact blockers in the consolidated project contract and omit everything already answered or safely inspectable.

A request such as `像普通软件一样双击打开` confirms desired experience only. It does not prove that installation, admin rights, background services, network access, or automatic updates are allowed.

Runtime does not determine delivery by itself. `普通办公电脑` does not automatically approve a desktop executable, local HTML, Excel workflow, or hosted web app. It only constrains what can run. When more than one feasible delivery form would materially change installation, maintenance, permissions, packaging, or user workflow, include the actual alternatives in the consolidated decision card rather than creating another conversation round.

`App`, `工具`, or `系统` is also not a delivery decision. Before implementation, the active delivery form must trace to an explicit user statement or an approved contract. If the user approves only a development proof, label it as a proof and do not present its interface as the final App.

Select WPF, WinUI, Python, React, local HTML, Excel, or another technical path only after the delivery meaning is stable and the required environment was actually inspected. A development-machine capability is evidence of feasibility, not user approval of that delivery form.

## Runtime Persistence Boundary

Delivery analysis must include where the running tool writes settings, records, logs, caches, exports, and temporary files. Distinguish project/build output from user-runtime data and external/system effects. A local or desktop tool is not write-free merely because it has no server.

Before implementation, name the intended runtime paths or state that persistence remains an unapproved `R`. Include creation, update, deletion, restart, cleanup, and rollback behavior when they affect the user. Do not claim `只修改项目目录` when the program will write `%LocalAppData%`, a registry key, another user folder, or an external location.

For packaging and restore commands, inspect the actual SDK/tool version and disclose target/runtime packs, provider endpoints, environment overrides, lock-file behavior, isolated versus global caches, generated output, and offline behavior. A self-contained executable is not necessarily an offline build.

Do not infer `Web` solely from “多人使用” or “有内网服务器”. Confirm hosting owner, account/permission approach, backup, network availability, and whether the current round is a development proof, test deployment, or formal internal delivery.

## Delivery Mode Decision Table

| Delivery Mode | Best For | Advantages | Risks / Costs | Beginner Fit |
| --- | --- | --- | --- | --- |
| Single HTML / local web file | small import/export tools, simple calculators, local reports | no install, opens in browser, easy to share | browser file permissions, limited local filesystem access | high |
| Excel/template/file workflow | spreadsheet cleanup, tracking tables, simple reporting | familiar to office users, low training cost | macros may be blocked, complex logic can become fragile | high |
| Desktop app / executable | local files, offline work, repeated operator workflow, device-related UI | user-friendly once packaged, can access files more naturally | packaging, antivirus warnings, updates, Windows compatibility | medium |
| Web app / hosted service | multi-user shared data, permissions, dashboards, unified updates | one deployment, everyone uses same version | server, login, backup, network, maintenance, data security | medium |
| Script / command line | batch jobs, technical users, automation by IT | fast to build, easy to version, powerful | requires runtime and terminal confidence | low for beginners |

## App Versus Web

Choose desktop app when:

- users work mainly on one Windows computer
- data files are local or sensitive
- offline use matters
- the tool needs direct file access, device access, serial/USB, or local dialogs
- packaging and update responsibility are acceptable

Choose web app when:

- multiple users need the same data
- central permissions, audit, or shared status matter
- the company can host and maintain the service
- network access is reliable
- backups and data ownership are clear

Choose local HTML or file-based tool when:

- the project is small
- no installation is preferred
- data can be imported/exported as files
- the user only needs one-person or occasional use

Choose script when:

- the user is technical
- the workflow is batch-oriented
- the script will be wrapped later into a UI or scheduled by IT

## Validation Requirements

For no-install delivery:

- test that the file opens in the confirmed target environment
- test sample input and output
- include visible instructions or a short README

For desktop apps:

- test the packaged executable, not only source code
- test on a clean or ordinary user environment when possible
- record dependencies, antivirus warnings, data folders, and update method

For web apps:

- test local development and deployed environment separately
- record hosting, login, data storage, backup, and owner
- do not call it delivered until a real user can access it through the intended URL

For scripts:

- record runtime version
- provide exact command
- include sample input/output
- consider wrapping the script if the target user is a beginner

## Consequential Delivery Blockers

Use the product or consequential gate in `references/交互与确认规则.md` before relying on a delivery choice when:

- the chosen delivery mode requires installation but the target user may not have permission
- a web app is requested but hosting, data storage, or owner is unclear
- a desktop app is requested but packaging and user-machine validation are not in scope
- a script is requested for a beginner without a wrapper or clear run instruction
- the tool must handle sensitive or shared business data but storage/security is unclear
