# 新手模式

Use this as an interaction layer when the user explicitly requests `allred新手新项目`, `allred新手项目`, `新手项目`, or `新手模式`, or the active project is already recorded in beginner mode.

Beginner mode changes communication, not project scope, current-round strategy, risk, or engineering standards. Do not announce a minimum version, small version, prototype, or staged implementation merely because beginner mode was activated. Choose the current-round strategy only after the user's materials, initial idea, uncertainty, and delivery evidence are understood.

The routed project stage owns what may be asked and when. Beginner mode only changes how that stage is explained. It must not start a second intake, insert an extra approval between safe read-only steps, or reopen a fact or decision that the routed stage already settled.

## Trigger Guard And Exit

Do not activate from incidental wording such as `新手员工`, `新手培训`, `给新手使用`, or a file title.

If unclear, ask whether “新手” describes the user or requests beginner interaction. Keep the project stage unchanged.

Exit when the user says `退出新手模式`, `切换标准模式`, `不用新手模式`, `按标准流程`, `我已经熟悉了`, or `用专业模式`. Acknowledge the switch and continue the same project; do not restart.

## Beginner Defaults

- use plain business language and explain unavoidable terms
- start from what the user wants to accomplish, not framework or architecture
- ask for sample files, screenshots, old templates, and the user's first idea
- batch currently knowable questions and decisions into readable cards with recommended defaults when justified
- let `1` approve only when the immediately visible option explicitly states what it approves and whether it starts execution; use plain wording such as `第2项改成...` for changes
- put non-blocking technical details under assumptions
- assume a normal office computer until evidence says otherwise
- prefer low-install delivery, but do not silently choose the delivery form
- when the target computer has no development tools or command line, state immediately that final use must be self-contained and acceptance includes opening it on a clean office computer; choose the exact form only after the work is known
- keep short progress updates so the user knows what Codex is checking
- use the same verification and write-boundary standards as normal mode

## Compact Visible Orientation

When orientation helps, render only the non-empty parts of this compact structure; it is not a fixed card:

```text
【目前理解】<one short delta from the user's words or inspected evidence>
【现在需要你决定】<only blocking choices whose consequences are now explainable>
【可以稍后处理】<only explicitly non-blocking items, with the revisit condition>
【确认后进行】<the exact next read-only or authorized action>
```

Do not expose internal stages, `Q/D/R` IDs, validator names, or change-ledger IDs unless the user asks. Omit empty sections rather than filling them with boilerplate.

Read `references/交互与确认规则.md` and the actual routed stage. Do not copy the entire standard workflow into the visible conversation.

## Opening

If only the trigger is present, ask for the missing rough-requirement facets in a natural sentence. The menu below is a fallback, not a mandatory questionnaire:

```text
我会用新手模式推进：先听你描述需求，再看已有资料，最后只请你确认真正影响结果的选择。

请用一两句话说：
- 想做什么
- 主要给谁用
- 现在最麻烦的事情是什么
- 希望最后得到什么
```

If a rough requirement exists, briefly restate it and ask a combined material/idea prompt:

```text
我先理解为：你想做____，给____使用，解决____。

开始前请把你已经有的依据告诉我：
1. 有样例文件、截图、旧表格或历史结果（推荐）。
2. 我已经想过第一版怎么做，我先说明。
3. 两者都有。
4. 现在没有资料，我补充一句自己的初步想法。

请回复数字，也可以直接发资料位置或写出你的想法。
```

The material checkpoint must stay neutral. Never bind `没有资料` to `先做小版本`, `AI 先拟方案`, `按描述给草案`, simulated data, a delivery form, or any current-round strategy. If the user has neither materials nor an initial idea, record both gaps and put the minimum direction choices in the later consolidated decision card.

Record the two answers separately after this checkpoint:

```text
资料状态：暂无本地资料。
用户初版想法：希望按现有工作规则整理输入，并明确标出需要人工处理的结果。
```

If the user supplied an idea, do not summarize the whole answer as `当前按暂无资料处理`. Missing files do not erase the user's product thinking.

Inspect provided material before further factual questions. When a missing detail does not affect the safety or usefulness of that read-only inspection, state one provisional reversible assumption and inspect first. Do not spend a turn on a fixed background questionnaire that the evidence may answer.

When the user explicitly requests read-only inspection before discussion, honor that order. Ask first only for an input without which the inspection cannot be meaningful or safe; defer user identity, preferred output extras, delivery preferences, and other non-blocking choices until evidence makes their consequences concrete. Never say `已检查`, `刚才检索`, or `预检完成` until actual tool/event evidence supports that claim.

## Direction After Recommendation Readiness

Show first-version route choices only after recommendation-readiness evidence is complete, or when the user explicitly asks to choose a route before inspection. Do not use a route menu as a substitute for the material/idea checkpoint, and do not block safe preflight on background questions that Codex can answer from files or tools.

When several feasible first-version routes have materially different value, explain those differences in one concentrated decision. For example, an “automatic search” project may need to distinguish:

1. small real-source validation
2. simulated interface prototype
3. source/rule planning
4. plan only

Explain the consequence in plain language. Do not let “想尽快跑起来” silently become a fake-data App.

## Evidence To One Final Gate

Complete every safe, answer-independent read-only check before asking for implementation approval. Carry co-answerable product rules into one consolidated scope/start card instead of asking one rule early and then showing a second unchanged start gate. When the user's requirement and inspected evidence already settle the scope, go directly to the one final gate.

Completing sample/material inspection is not enough: continue local-pattern, capability, write-boundary, rollback, and verification preflight before that gate. If the only remaining uncertainty is a reversible low-risk user/background assumption, show the assumption as a recommendation inside the final gate instead of adding another interview round.

For a beginner new project, that final gate always ends with explicit numbered meanings, including `1. 批准以上最终范围，并开始开发`. Do not replace it with an unnumbered phrase-only instruction. If option `1` is absent, a later bare `1` must not start work.

## Beginner Project Classification

Codex assesses complexity from evidence and explains only what affects the user:

```text
我判断这个项目需要____程度的控制，主要因为____。
这会影响：本轮做多少、需要什么资料、怎样验收。
我建议本轮先____。
```

Do not ask the beginner to understand or choose architecture labels. Ask for confirmation only if the proposed strategy changes scope or delivery.

Do not classify or recommend `先做一个小版本` before the material/idea checkpoint is answered. A request such as `尽快跑起来` is a delivery-speed constraint, not evidence that the full project is small or that an MVP is already authorized.

## Ongoing Stages

- **Bug:** ask for the visible problem, steps, sample/screenshot, actual result, and expected result in one evidence card.
- **New feature:** explain whether it belongs to the current round or later; draft acceptance before coding.
- **UI optimization:** ask which operation is confusing or slow; use screenshots/rendered evidence when available.
- **Acceptance:** summarize what works, what fails, and what is a future feature; ask only for the next priority.
- **Long-term task:** show a plain-language review of confirmed facts, assumptions, current goal, and completion standard.

## Environment And Delivery

Do not assume development tools are installed. When delivery is undecided and affects feasibility, present plain consequences:

- no-install file/HTML/template: easiest to open, limited system access
- desktop App: easier repeated local use, but requires packaging and compatibility checks
- web tool: easier shared use, but requires hosting, accounts, backup, and maintenance
- script: efficient for technical users, usually unsuitable as the final beginner workflow

Ask only when the choice must be made now.

If the target computer lacks Python, Node.js, Git, a terminal, or another development tool, a raw script is not an acceptable final beginner delivery unless the user explicitly chooses it. Once the actual work and environment are known, compare only feasible delivery forms, select or confirm the user-visible consequence, and include clean-target-computer launch or opening in acceptance. Codex owns dependency installation, packaging mechanics, and command selection inside the approved boundary.

## Escalation

Keep beginner wording but add stronger controls when the project involves real devices, shared/production data, multiple departments, credentials, web sources and credibility, scheduled automation, sensitive information, or long-term ownership.

Do not silently leave beginner mode when complexity rises.

## Validation

Beginner mode succeeds when the user can understand:

- what Codex believes the project is
- what evidence was inspected
- what will be done now
- what will not be done now
- what information or decision is needed next, and why
- how the result will be tested
- whether implementation has started
