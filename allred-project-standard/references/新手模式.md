# 新手模式

Use this as an interaction layer when the user explicitly requests `allred新手新项目`, `allred新手项目`, `新手项目`, or `新手模式`, or the active project is already recorded in beginner mode.

Beginner mode changes communication, not project scope, current-round strategy, risk, or engineering standards. Do not announce a minimum version, small version, prototype, or staged implementation merely because beginner mode was activated. Choose the current-round strategy only after the user's materials, initial idea, uncertainty, and delivery evidence are understood.

## Trigger Guard And Exit

Do not activate from incidental wording such as `新手员工`, `新手培训`, `给新手使用`, or a file title.

If unclear, ask whether “新手” describes the user or requests beginner interaction. Keep the project stage unchanged.

Exit when the user says `退出新手模式`, `切换标准模式`, `不用新手模式`, `按标准流程`, `我已经熟悉了`, or `用专业模式`. Acknowledge the switch and continue the same project; do not restart.

## Beginner Defaults

- use plain business language and explain unavoidable terms
- start from what the user wants to accomplish, not framework or architecture
- ask for sample files, screenshots, old templates, and the user's first idea
- use one compact card with recommended defaults
- let `1` approve all recommendations; use codes such as `D2=...` for changes
- put non-blocking technical details under assumptions
- assume a normal office computer until evidence says otherwise
- prefer low-install delivery, but do not silently choose the delivery form
- keep short progress updates so the user knows what Codex is checking
- use the same verification and write-boundary standards as normal mode

Read `references/交互与确认规则.md` and the actual routed stage. Do not copy the entire standard workflow into the visible conversation.

## Opening

If only the trigger is present:

```text
我会用新手模式推进：先听你描述需求，再看已有资料，最后只请你确认真正影响结果的选择。

请用一两句话说：
- 想做什么
- 主要给谁用
- 现在最麻烦的事情是什么
- 希望最后得到什么
```

If a rough requirement exists, briefly restate it and ask one combined material/idea gate:

```text
我先理解为：你想做____，给____使用，解决____。

开始前请把你已经有的依据告诉我：
1. 有样例文件、截图、旧表格或历史结果（推荐）。
2. 我已经想过第一版怎么做，我先说明。
3. 两者都有。
4. 现在没有资料，我补充一句自己的初步想法。

请回复数字，也可以直接发资料位置或写出你的想法。
```

The material checkpoint must stay neutral. Never bind `没有资料` to `先做小版本`, `AI 先拟方案`, `按描述给草案`, simulated data, a delivery form, or any current-round strategy. If the user has neither materials nor an initial idea, record both gaps and put the minimum direction choices in the later consolidated decision card.

Record the two answers separately after this checkpoint:

```text
资料状态：暂无本地资料。
用户初版想法：关注主流厂家的最新动态、专利更新和公开销售线索。
```

If the user supplied an idea, do not summarize the whole answer as `当前按暂无资料处理`. Missing files do not erase the user's product thinking.

Inspect provided material before further factual questions.

## Direction Before Background Work

When several first-version routes have different value, ask early. For example, an “automatic search” project should distinguish:

1. small real-source validation
2. simulated interface prototype
3. source/rule planning
4. plan only

Explain the consequence in plain language. Do not let “想尽快跑起来” silently become a fake-data App.

## Beginner Project Classification

Codex assesses complexity from evidence and explains only what affects the user:

```text
我判断这个项目需要____程度的控制，主要因为____。
这会影响：本轮做多少、需要什么资料、怎样验收。
我建议本轮先____。
```

Do not ask the beginner to understand or choose architecture labels. Ask for confirmation only if the proposed strategy changes scope or delivery.

Do not classify or recommend `先做一个小版本` before the material/idea checkpoint is answered. A request such as `尽快跑起来` is a delivery-speed constraint, not evidence that the full project is small or that an MVP is already authorized.

## Ongoing Stages

- **Bug:** ask for the visible problem, steps, sample/screenshot, actual result, and expected result in one evidence card.
- **New feature:** explain whether it belongs to the current round or later; draft acceptance before coding.
- **UI optimization:** ask which operation is confusing or slow; use screenshots/rendered evidence when available.
- **Acceptance:** summarize what works, what fails, and what is a future feature; ask only for the next priority.
- **Long-term task:** show a plain-language review of confirmed facts, assumptions, current goal, and completion standard.

## Environment And Delivery

Do not assume development tools are installed. When delivery is undecided and affects feasibility, present plain consequences:

- no-install file/HTML/template: easiest to open, limited system access
- desktop App: easier repeated local use, but requires packaging and compatibility checks
- web tool: easier shared use, but requires hosting, accounts, backup, and maintenance
- script: efficient for technical users, usually unsuitable as the final beginner workflow

Ask only when the choice must be made now.

## Escalation

Keep beginner wording but add stronger controls when the project involves real devices, shared/production data, multiple departments, credentials, web sources and credibility, scheduled automation, sensitive information, or long-term ownership.

Do not silently leave beginner mode when complexity rises.

## Validation

Beginner mode succeeds when the user can understand:

- what Codex believes the project is
- what evidence was inspected
- what will be done now
- what will not be done now
- what one decision is needed next
- how the result will be tested
- whether implementation has started
