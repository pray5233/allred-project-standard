# 长期任务模式

Use for work spanning multiple rounds, accumulating evidence or conclusions, or requiring checkpoints and handoff. Shared behavior comes from `references/核心执行流程.md`. Maintenance of the Allred Skill itself belongs to the explicitly invoked `allred-project-lab` Skill.

## State Model

Keep distinct:

| State | Meaning |
| --- | --- |
| confirmed | supported by recorded evidence or explicit acceptance |
| assumption | plausible, not established |
| rejected | tested or deliberately excluded, with reason |
| current round | one outcome this round will close |
| future work | valid but outside current acceptance |
| blocker | missing evidence, authority, environment, or decision |

A prior conversation is not evidence by itself. Preserve source, date/version, evidence level, and owner when material.

## Review Depth

Use lightweight review when visible context is current:

```text
已确认：
尚未验证：
当前最大问题：
本轮目标/不做：
完成标准：
```

Use full review when context is missing, work was handed over, evidence conflicts or changes meaning, ownership changed, or the next action affects a final conclusion, shared tracker, device/system, or consequential handoff. Use `templates/长期任务回顾卡.md` only when a durable record helps.

After a new-evidence event triggers full review, report the complete available review now: prior confirmed scope, new observations, competing explanations, exact evidence level, current conclusion limit, current-round result boundary, and whether any project/original files were written. Do not call it a `首轮核对` and defer an analysis that the supplied event already supports.

Match the label to the completed review depth. Do not frame a complete available review as `初步`, `预判`, `首轮`, or a partial/incremental check merely because the evidence supports only a limited conclusion. Put uncertainty in the evidence level and conclusion limit; do not misstate the completeness of the review itself.

Fill review fields from evidence. Do not ask them one by one. An exact read-only request continues after preflight without ceremonial approval.

## Current-Round Contract

Define route, exact objective/non-goals, evidence basis, result form, write boundary, owner, verification level, rollback/checkpoint, and only the tasks needed this round.

Use concentrated product-decision interaction when necessary. Use a consequential authorization gate immediately before shared records, final conclusions, installs, device/system actions, or external writes. Do not ask again after every small step, but do not suppress newly meaningful dependent decisions.

## Execute And Update State

- preserve original evidence unless a write scope is explicit
- never upgrade static/offline evidence to live/product conclusions
- execute coherent slices and verify each meaningful checkpoint
- update confirmed/assumption/rejected/current/future states only from evidence
- close the round without reopening the entire project

## Round Closure

```text
本轮完成：
新鲜验证证据：
新确认/关闭结论：
仍未验证：
新风险或阻塞：
未来任务变化：
推荐下一轮：
```

Use `templates/交接卡.md` when pausing or changing owner. Use `allred记忆` only when explicitly triggered; long-term mode does not automatically write project memory.
