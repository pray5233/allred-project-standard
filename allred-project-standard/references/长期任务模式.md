# 长期任务模式

Use this reference for work that spans multiple rounds, accumulates evidence or conclusions, or needs checkpoints and handoff. It applies to long-running apps/tools, device investigation, data/log analysis, documentation, knowledge work, and Skill/process improvement.

Also read `references/交互与确认规则.md`. Read `references/Skill流程优化模式.md` when the product being improved is a Skill or workflow.

## Activation

Explicit triggers include `allred长期任务`, `长期任务启动`, `开始长期任务`, `继续长期任务`, `长期任务复盘`, `长期任务调试`, `长期任务资料分析`, `长期任务验证`, and `长期任务优化`.

Do not activate merely because a title or quoted text contains `长期任务`. If the single phrase is ambiguous, ask whether to enter the mode, review an existing task, or only discuss the method.

## State Model

Keep these states separate:

| State | Meaning |
| --- | --- |
| Confirmed conclusion | supported by recorded evidence or explicit acceptance |
| Unverified assumption | plausible but not established |
| Rejected direction | tested or deliberately excluded, with reason |
| Current-round objective | the one outcome this round will close |
| Future work | valid but outside current acceptance |
| Blocker | missing authority, evidence, environment, or decision that prevents progress |

A previous conversation is not evidence by itself. Preserve source, date/version, evidence level, and owner where relevant.

## First Start

If no background exists, ask for a short description: total goal, current state, available materials/equipment, current biggest problem, and desired result for this round.

Then collect existing materials and the user's current hypothesis in one gate. Inspect materials before detailed questions. Do not replace the user's hypothesis; restate it and compare it with evidence.

## Review Gate

Every round starts with review, but review depth varies.

Use **lightweight review** when the same task continues with visible context. New files or logs explicitly supplied as this round's read-only input still use lightweight review unless they invalidate context or change a consequential boundary:

```text
轻量回顾：
- 已确认：
- 尚未验证：
- 当前最大问题：
- 建议本轮只解决：
- 完成标准：
- 待确认但不阻塞：
```

Use **full review** when:

- a new conversation begins or context is missing
- the task was paused or handed over
- new evidence makes prior context incomplete, conflicts with a conclusion, or changes the interpretation boundary
- ownership changed
- the next action affects a final conclusion, shared tracker, device, system, or handoff

Use `templates/长期任务回顾卡.md` for a durable full review.

Do not ask each review field separately. Fill from evidence, show the draft, and ask only about incorrect or direction-changing items.

An exact read-only request authorizes analysis after preflight when the evidence is complete and the no-write boundary is preserved. Do not announce that the user must confirm `继续分析`, and do not stop for a ceremonial approval. Ask only when preflight exposes a contradiction that requires the user to choose an interpretation, changes the requested result, or requires a new write/action boundary.

When there is no such blocker, end the review message with an active execution statement such as `没有新增阻塞，我现在按上述边界继续只读分析`. Then continue to the analysis/tool step in the same task flow. Do not end with `建议继续`, `可以继续`, `等你确认`, or another phrase that makes the already authorized analysis appear paused.

## Current-Round Design

After review:

1. classify this round: analysis, debugging, validation, implementation, organization, documentation, acceptance, or handoff
2. define the exact objective and non-goals
3. select the development basis/benchmark using `references/开发依据与能力复用.md` when design is involved
4. define the result form
5. define evidence level and validation
6. define write boundary and owner
7. inspect existing capabilities
8. decompose only the tasks needed for the round
9. confirm consequential execution
10. execute, verify, and update task state

Normal rounds should use one compact decision card. Ask more only when safety, evidence, final conclusions, ownership, or write boundaries cannot be deferred.

## Evidence And Write Boundary

Use `references/证据等级说明.md` and `references/写入边界说明.md` when applicable.

Rules:

- a guess never silently becomes a confirmed conclusion
- static analysis does not claim live device/system validation
- offline validation supports only an offline stage conclusion
- changing a shared tracker, final conclusion, original data, device, or system requires explicit authority
- keep original evidence read-only unless a write scope is confirmed
- record a rollback/checkpoint before consequential writes

## Start Confirmation

Use `【开始执行前确认】` from `references/交互与确认规则.md` before a round that mutates project artifacts, conclusions, shared records, systems, devices, or installs/tools.

Include:

- review type and evidence basis
- current objective and non-goals
- result form
- planned files/records/commands
- write/no-touch boundaries
- validation and evidence level
- checkpoint/rollback

A direct `继续，按这个本轮目标执行` counts when it clearly approves an already displayed card. Do not ask again after every small step inside the approved round.

## Skill Or Workflow Improvement

Treat the Skill/workflow as the product:

- user feedback and observed behavior are evidence
- one failed prompt is a reproduction case, not automatically a universal rule
- architecture changes need a recorded basis
- keep entry routing light and conditional detail in references
- validate structure plus realistic behavior
- sync release/distribution only when in scope

Use `references/Skill流程优化模式.md` and `references/Skill测试验收.md`.

## Round Closure

At the end, record:

```text
本轮结果：
- 已完成：
- 验证证据：
- 新确认结论：
- 仍未验证：
- 新发现风险：
- 未完成/阻塞：
- 更新后的未来任务：
- 推荐下一轮：
```

Do not reopen the entire project automatically. Recommend the smallest next round that reduces the most important remaining uncertainty or closes the next useful outcome.

Use `templates/交接卡.md` when pausing or changing owner.
